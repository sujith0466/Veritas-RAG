# F5.2 — Folder Rename / Soft Delete Architecture

**Epic:** 5 — Document & Folder Management
**Feature:** F5.2 — Folder Rename / Soft Delete
**Version:** 1.0 — Architecture Frozen
**Status:** ⏳ PENDING APPROVAL

---

## 1. Executive Summary

F5.2 extends the folder entity (defined in F5.1) with two critical lifecycle operations:
1. **Rename** — Updates a folder's display name and slug with conflict detection, optimistic locking, breadcrumb cache invalidation, and an immediate audit trail.
2. **Soft Delete** — Marks a folder (and all its descendants) as `is_deleted = TRUE` using a safe, bounded, background Celery worker to prevent synchronous timeout on large subtrees. Documents within deleted folders become invisible but remain physically present in S3/Qdrant.

Neither operation physically removes data. Both are fully reversible via the restore flow.

## 2. Operation 1: Rename

### 2.1 Rename Flow

```
PATCH /api/v1/workspaces/{ws_id}/folders/{folder_id}
Body: { "name": "New Name", "version": <current_version> }

Step 1 — RBAC Guard
    └── Require Permission.FOLDERS_UPDATE

Step 2 — Load & Lock Folder
    ├── FolderRepository.get_by_id_in_workspace(folder_id, workspace_id)
    ├── Assert is_deleted == False
    └── Reject 404 if not found

Step 3 — Optimistic Lock Check
    ├── Assert request.version == folder.version
    └── Reject 409 (ETag Conflict) if version mismatch
        Response header: X-Current-Version: <server_version>

Step 4 — Name Conflict Detection
    ├── Normalise: new_name.strip().lower()
    ├── Skip check if normalised new_name == normalised current name (no-op rename)
    ├── Query: SELECT COUNT(*) FROM folders
    │         WHERE workspace_id=? AND parent_id=? AND lower(name)=? AND is_deleted=FALSE AND id != folder_id
    └── Reject 409 if count > 0

Step 5 — Compute New Slug
    ├── new_slug = slugify(new_name)
    └── Collision suffix if unique index violation (append "-2", "-3"...)

Step 6 — Atomic Write
    ├── UPDATE folders SET name=?, slug=?, version=version+1, updated_at=now()
    │   WHERE id=? AND version=<expected_version>   [DB-level optimistic lock]
    └── If 0 rows updated → Reject 409 Conflict

Step 7 — Cache Invalidation (Immediate, Before Response)
    ├── DEL "ws:{ws_id}:folder:{folder_id}"
    ├── DEL "ws:{ws_id}:folder:{parent_id}:children:*"  (all pages)
    └── DEL "ws:{ws_id}:folder:{folder_id}:breadcrumbs"
        └── Also invalidate breadcrumbs of all descendants:
            ├── Load descendant IDs from folder.path prefix scan (FolderRepository.get_subtree_ids)
            └── DEL "ws:{ws_id}:folder:{child_id}:breadcrumbs" for each

Step 8 — Audit Log
    └── AuditLog(action="folder.renamed", details={old_name, new_name, folder_id})

Step 9 — Domain Event
    └── dispatcher.publish(FolderRenamedEvent(workspace_id, folder_id, old_name, new_name, actor_id))

Return 200 FolderResponse with updated name, slug, version
```

### 2.2 Descendant Breadcrumb Invalidation Bound

The number of descendant folders is bounded by `depth ≤ 10` and the subtree is materialized via `path`. Subtree ID retrieval uses:

```sql
-- Recursive CTE (bounded by depth <= 10, safe for production):
WITH RECURSIVE subtree AS (
    SELECT id FROM folders WHERE id = :folder_id
    UNION ALL
    SELECT f.id FROM folders f
    JOIN subtree s ON f.parent_id = s.id
    WHERE f.is_deleted = FALSE
)
SELECT id FROM subtree;
```

**Worst case:** 10 levels × unbounded siblings → bounded by total workspace folder count. Redis DEL operations are batched in a pipeline (single round trip per 100 keys).

## 3. Operation 2: Soft Delete

### 3.1 Two-Phase Soft Delete Architecture

Soft delete is split into two phases to avoid synchronous timeout on large subtrees:

```
Phase 1 — Synchronous (HTTP Request)
    Mark root folder as DELETED (immediate, returns to client)

Phase 2 — Asynchronous (Celery Background Worker)
    Cascade soft-delete to all descendants
```

### 3.2 Phase 1 — Synchronous Root Mark

```
DELETE /api/v1/workspaces/{ws_id}/folders/{folder_id}
Body: { "version": <current_version> }

Step 1 — RBAC Guard
    └── Require Permission.FOLDERS_DELETE

Step 2 — Load & Validate Folder
    ├── Assert is_deleted == False
    └── Reject 404 if not found

Step 3 — Optimistic Lock
    └── Assert request.version == folder.version → else 409

Step 4 — Check for Last Active Parent
    ├── If folder has a parent_id → no special handling needed
    └── If folder is ROOT (parent_id is NULL):
        ├── Check if any documents exist in this folder tree
        └── Emit WARNING in audit log details (non-blocking)

Step 5 — Mark Root Folder DELETED
    ├── UPDATE folders SET is_deleted=TRUE, deleted_at=now(), deleted_by_user_id=actor_id,
    │       version=version+1 WHERE id=? AND version=<expected>
    └── 0 rows updated → 409 conflict

Step 6 — Enqueue Background Worker
    └── Celery: cascade_soft_delete_subtree.delay(
                    folder_id=folder_id,
                    workspace_id=workspace_id,
                    deleted_by_user_id=actor_id,
                    deleted_at=now_utc_iso
                )

Step 7 — Immediate Cache Invalidation
    ├── DEL "ws:{ws_id}:folder:{folder_id}"
    └── DEL "ws:{ws_id}:folder:{parent_id}:children:*"

Step 8 — Audit Log
    └── AuditLog(action="folder.soft_deleted",
                 details={folder_id, cascade_pending=True, worker_enqueued=True})

Step 9 — Domain Event
    └── dispatcher.publish(FolderSoftDeletedEvent(workspace_id, folder_id, actor_id, cascade_pending=True))

Return 202 Accepted (not 204, because cascade is asynchronous)
    Body: { "status": "deletion_queued", "folder_id": "...", "cascade_pending": true }
```

### 3.3 Phase 2 — Celery Worker: `cascade_soft_delete_subtree`

```python
# Task signature (design only — no implementation)
@celery_app.task(
    name="folders.cascade_soft_delete_subtree",
    bind=True,
    max_retries=5,
    default_retry_delay=30,
    acks_late=True,
    reject_on_worker_lost=True,
)
async def cascade_soft_delete_subtree(
    self,
    folder_id: str,
    workspace_id: str,
    deleted_by_user_id: str,
    deleted_at: str,
    batch_size: int = 200,
) -> None:
    ...
```

**Worker Algorithm:**

```
1. Open AsyncSession
2. Fetch subtree IDs via recursive CTE (depth-bounded ≤ 10 levels)
   └── Exclude already-deleted folders
3. Batch-process in chunks of 200:
   ├── UPDATE folders SET is_deleted=TRUE, deleted_at=?, deleted_by_user_id=?
   │   WHERE id IN (...batch...) AND is_deleted=FALSE
   └── Flush (no commit between batches — single transaction)
4. Commit single transaction
5. Batch-invalidate Redis:
   └── pipeline DEL "ws:{ws_id}:folder:{id}" for each deleted id (100 per pipeline)
6. Emit FolderChildrenSoftDeletedEvent(workspace_id, root_folder_id, deleted_count)
7. Write audit log:
   └── AuditLog(action="folder.cascade_deleted",
                details={root_folder_id, deleted_count, worker_task_id})
```

**Failure & Retry:**
- `acks_late=True` ensures no lost tasks if worker dies mid-execution.
- `reject_on_worker_lost=True` requeueing on SIGKILL.
- Idempotency: `WHERE is_deleted=FALSE` in UPDATE prevents double-deletion on retry.
- Exponential backoff: retry delays 30s, 60s, 120s, 240s, 480s.
- Dead letter queue after 5 retries; alert raised to ops team.

## 4. Document Visibility Rules

### 4.1 When Folder is Soft-Deleted

| Object | Behavior |
|---|---|
| Deleted folder itself | Hidden from all API list/get responses |
| Deleted folder's children | Hidden after cascade worker completes |
| Documents in deleted folder | Invisible in `/documents` list (query filters `folder.is_deleted = FALSE`) |
| Documents in S3 | **Physically preserved** — no S3 deletion |
| Vectors in Qdrant | **Preserved** — no Qdrant deletion |
| Document metadata in DB | **Preserved** with `folder_id` FK retained |

### 4.2 Document Query Impact

All document list queries must join-filter on folder status:

```sql
-- Document visibility rule (enforced in DocumentRepository):
SELECT d.* FROM documents d
JOIN folders f ON d.folder_id = f.id
WHERE d.workspace_id = :ws_id
  AND d.is_deleted = FALSE
  AND f.is_deleted = FALSE  ← This filter makes documents invisible when folder is deleted
```

## 5. Restore Behavior

### 5.1 Restore Flow

```
POST /api/v1/workspaces/{ws_id}/folders/{folder_id}/restore

Step 1 — RBAC Guard
    └── Require Permission.FOLDERS_RESTORE  [OWNER/ADMIN only]

Step 2 — Load Deleted Folder
    ├── SELECT * FROM folders WHERE id=? AND workspace_id=? AND is_deleted=TRUE
    └── Reject 404 if not found

Step 3 — Parent Validation (Critical Edge Case)
    ├── If parent_id IS NULL → restoring root folder, no parent check needed
    └── If parent_id IS NOT NULL:
        ├── Load parent folder
        ├── CASE A: Parent is ACTIVE → normal restore, proceed
        ├── CASE B: Parent is SOFT-DELETED:
        │   └── Policy: CANNOT restore child into a deleted parent
        │       Response: 409 { "error": "parent_deleted", "parent_id": "...",
        │                        "suggestion": "Restore parent folder first" }
        └── CASE C: Parent no longer exists (hard-purged) → impossible (FK CASCADE)
            └── This case cannot occur; parent FK SET NULL on purge

Step 4 — Depth Re-Validation After Restore
    ├── Recompute parent.depth + 1
    └── Reject 422 if depth > 10 (parent tree was restructured during deletion period)

Step 5 — Restore Root Folder (Synchronous)
    └── UPDATE folders SET is_deleted=FALSE, deleted_at=NULL, deleted_by_user_id=NULL,
            version=version+1 WHERE id=? AND is_deleted=TRUE

Step 6 — Enqueue Cascade Restore Worker
    └── Celery: cascade_restore_subtree.delay(folder_id, workspace_id, actor_id)

Step 7 — Cache Invalidation
    ├── DEL "ws:{ws_id}:folder:{folder_id}"
    └── DEL "ws:{ws_id}:folder:{parent_id}:children:*"

Step 8 — Audit Log & Domain Event

Return 202 Accepted: { "status": "restore_queued", "cascade_pending": true }
```

### 5.2 Cascade Restore Worker

Mirror of cascade delete worker but sets `is_deleted=FALSE`:
- Fetches all direct descendant IDs of root folder where `is_deleted=TRUE`.
- Batch-updates in chunks of 200.
- Idempotent: `WHERE is_deleted=TRUE` in UPDATE.

### 5.3 Selective Restore Limitation

Only the **root deleted folder and its descendants** are restored in a single operation. Documents' visibility is automatically restored once their folder's `is_deleted` becomes `FALSE`.

## 6. Last Active Parent Handling

When deleting a root-level folder that is the **only folder in a workspace**:

1. The deletion still proceeds without blocking.
2. A `WARNING` flag is set in the audit log: `last_root_folder_deleted: true`.
3. Frontend shows a confirmation modal: _"This is the last top-level folder. Deleting it will hide all contained documents. Continue?"_
4. Workspace retains the ability to create new root folders at any time.

## 7. Cache Invalidation Strategy (Rename & Delete)

### 7.1 Invalidation Matrix

| Operation | Keys Invalidated | Method |
|---|---|---|
| Rename | `folder:{id}`, `folder:{parent_id}:children:*`, `folder:{id}:breadcrumbs`, all descendant breadcrumbs | Synchronous pipeline DEL before HTTP response |
| Soft Delete (Phase 1) | `folder:{id}`, `folder:{parent_id}:children:*` | Synchronous pipeline DEL in HTTP handler |
| Soft Delete (Phase 2) | `folder:{child_id}` for each cascade-deleted child | Batched pipeline DEL in Celery worker |
| Restore (Phase 1) | `folder:{id}`, `folder:{parent_id}:children:*` | Synchronous |
| Restore (Phase 2) | `folder:{child_id}` for each restored child | Batched in Celery worker |

### 7.2 Write-Invalidate Ordering

All cache invalidations happen **before the HTTP response is returned** for synchronous operations. This prevents a race where:
1. Thread A deletes folder and returns 202.
2. Thread B immediately reads stale cache and returns the folder as active.

## 9. Failure Recovery

### 9.1 Partial Cascade Failure Scenarios

| Scenario | Recovery |
|---|---|
| Worker dies after deleting 50/200 folders | `acks_late + reject_on_worker_lost` requeues task; idempotent `WHERE is_deleted=FALSE` prevents double-deletion |
| Redis pipeline fails during cache invalidation | Cache TTL (300s) serves as natural expiry; stale entries self-expire |
| DB commit fails mid-cascade | Transaction rollback; folder subtree reverts to consistent state; worker retried |
| Worker retries exhausted | Dead-letter queue + ops alert; folder root marked deleted but children still visible (partial state) → Admin can re-trigger via API `POST /folders/{id}/cascade-retry` |

### 9.2 Partial State Detection

A folder with `is_deleted=TRUE` but having active children (the window between Phase 1 and Phase 2 completion) is a valid transient state. The API `GET /folders/{id}` returns:

```json
{
  "is_deleted": true,
  "cascade_status": "pending"   ← Set if worker not yet completed
}
```

## 10. API Design

### 10.1 Endpoints (F5.2 Scope)

```
PATCH  /api/v1/workspaces/{ws_id}/folders/{folder_id}
    Body: { "name": "New Name", "version": N }
    → 200 FolderResponse       [FOLDERS_UPDATE]
    → 404 Not found
    → 409 Version conflict | Name conflict
    Header: X-Current-Version: N   (on conflict)

    Body: { "version": N }
    → 202 DeletionQueuedResponse   [FOLDERS_DELETE]
    → 404 Not found
    → 409 Version conflict

POST   /api/v1/workspaces/{ws_id}/folders/{folder_id}/restore
    Body: { "version": N }
    → 202 RestoreQueuedResponse    [FOLDERS_RESTORE]
    → 404 Not found (must fetch deleted items via include_deleted=true)
    → 409 Parent is also deleted

GET    /api/v1/workspaces/{ws_id}/folders?include_deleted=true
    → 200 Page[FolderSummaryResponse]   [FOLDERS_READ + ADMIN/OWNER only for deleted]
```

### 10.2 Response Schemas

**DeletionQueuedResponse:**
```json
{
  "status": "deletion_queued",
  "folder_id": "uuid",
  "cascade_pending": true,
  "worker_task_id": "celery-task-uuid"
}
```

**Rename conflict (409):**
```json
{
```

**Version conflict (409):**

## 13. Frontend Workflow

### 13.1 Rename Interaction

1. User double-clicks folder name or selects "Rename" from context menu.
2. Inline text input appears, pre-filled with current name.
3. On Enter: `PATCH /folders/{id}` fires with `version` from cached folder data.
4. **Optimistic UI:** Folder name updates immediately.
5. On success: Update local cache with new `name`, `slug`, `version`.
6. On 409 (name conflict): Revert optimistic update, show inline error.
7. On 409 (version conflict): Revert, show toast "Folder was updated elsewhere. Refreshing...". Reload folder data.

### 13.2 Delete Interaction

1. User selects "Delete" from context menu.
2. Confirmation dialog shows:
   - Folder name
   - Child folder count
   - Document count
   - Warning: "This will hide all documents inside."
3. On confirm: `DELETE /folders/{id}` fires.
4. **Optimistic UI:** Folder immediately removed from tree.
5. On 202 Accepted: Show toast "Folder deleted. Children are being processed."
6. On error: Revert tree, show error toast.

### 13.3 Restore Interaction (Admin Only)

1. Admin navigates to "Deleted Folders" view (admin panel).
2. Selects folder for restore.
3. If parent is also deleted: Show blocking message "Restore parent folder first."
4. On confirm: `POST /folders/{id}/restore`.
5. On 202: Show toast "Folder restore is in progress."

## 14. Performance Considerations

| Concern | Mitigation |
|---|---|
| Large subtree cascade (10k folders) | Async Celery worker; batch 200 rows/UPDATE; single transaction per batch |
| Recursive CTE for subtree ID fetch | Depth bounded at 10 → max recursion depth 10; safe for production; add `LIMIT 50000` as safety guard |
| Descendant breadcrumb invalidation on rename | Bounded by workspace folder count; Redis pipeline batching |
| Restore of large deleted subtree | Identical worker pattern to delete; fully idempotent |
| `document_count` accuracy on delete | Counter decremented atomically in document delete transaction; no separate pass needed |

## 15. Principal Engineer Review

### 15.1 Race Conditions

| Risk | Scenario | Mitigation |
|---|---|---|
| **R1 — Rename + Delete simultaneous** | Rename and delete fire concurrently; rename commits after delete | DB-level optimistic locking on `version` field: second writer gets 0-row UPDATE → 409 conflict. Client retries. |
| **R2 — Cascade worker starts while restore queued** | Delete of folder enqueues cascade worker; user immediately triggers restore; cascade worker processes descendants after restore | Worker's `WHERE is_deleted=FALSE` skip condition prevents re-deletion of already-restored children |
| **R3 — Parent deleted while child rename in-flight** | Cascade worker marks parent deleted; child rename succeeds; child is now orphaned under deleted parent | Child rename only validates parent state at start of request; post-rename the parent's `is_deleted` state doesn't invalidate existing children (valid transient state until cascade catches them) |
| **R4 — Double soft-delete via parallel cascade** | Two cascade workers dispatched for same subtree (replay scenario) | `WHERE is_deleted=FALSE` in UPDATE makes cascade idempotent; duplicate runs are no-ops |
| **R5 — Version conflict under optimistic lock** | Two admins rename same folder concurrently | DB `UPDATE ... WHERE version=<expected>` succeeds only for first writer; second receives 409 with `X-Current-Version` header |

### 15.2 Scalability Issues

| Risk | Mitigation |
|---|---|
| **S1 — Rename triggers O(n) descendant breadcrumb invalidation** | Bounded by workspace folder count; use Redis pipeline; async breadcrumb invalidation (non-blocking for response) |
| **S2 — Subtree recursive CTE on large trees** | Depth ≤ 10 hard limit + `LIMIT 50000` safety clause; if limit hit, log alert and process in two passes |
| **S3 — Cascade worker memory on huge subtrees** | Streaming cursor-based fetch in batches of 200 IDs; never loads full subtree into memory |

### 15.3 Security Gaps

| Risk | Mitigation |
|---|---|
| **SEC1 — Unauthorized restore** | `FOLDERS_RESTORE` requires ADMIN/OWNER; enforced before any DB access |
| **SEC2 — Tenant isolation during cascade** | Celery worker uses `workspace_id` in every UPDATE query |
| **SEC3 — Version forgery** | Client-supplied `version` is validated against DB `version` via `WHERE version=<expected>`; no trusting of client-provided version |
| **SEC4 — Task forgery (Celery)** | Tasks are enqueued internally only; no public API to trigger workers directly |

### 15.4 Caching Issues

| Risk | Mitigation |
|---|---|
| **C1 — Stale `include_deleted` cache** | `include_deleted=true` responses are **never cached** — always served fresh from DB |
| **C2 — Descendant cache not invalidated after cascade** | Cascade worker performs Redis pipeline DEL per batch of 100 keys after each DB batch commit |
| **C3 — Race: cache read between Phase 1 and Phase 2** | Phase 1 deletes root folder cache; descendants still in cache but with `is_deleted=false` (transient). Child queries will show children until cascade completes — this is the defined transient state. Document queries JOIN-filter on folder state, so documents are immediately invisible once their immediate folder's cache entry is removed |

### 15.5 Restoration Edge Cases

| Edge Case | Handling |
|---|---|
| Restore folder whose parent is deleted | 409 with `parent_deleted` error; client must restore parent first |
| Restore folder into parent that has moved subtrees (depth violation) | Depth re-validation at Step 4; reject 422 if would exceed depth 10 |
| Restore when cascade-delete worker not yet finished | Restore Phase 1 marks root ACTIVE; cascade-restore worker then marks all descendants ACTIVE; cascade-delete worker is already past those folders (idempotent) |
| Restore a folder that was never cascaded (worker failed) | `WHERE is_deleted=TRUE` in cascade-restore worker catches all deleted descendants regardless of how they were deleted |

### 15.6 Recursive Delete Edge Cases

| Edge Case | Handling |
|---|---|
| Folder tree has gaps (some already deleted folders mid-tree) | Recursive CTE `WHERE is_deleted=FALSE` naturally skips already-deleted nodes; idempotent |
| Cascade exceeds 50,000 folders | `LIMIT 50000` in CTE + alerting; second pass scheduled as new Celery task with updated root_id |
| DB failure during cascade batch commit | Full rollback of that batch; task retried; `WHERE is_deleted=FALSE` ensures idempotency |

### 15.7 Hierarchy Corruption Risks

| Risk | Mitigation |
|---|---|
| **H1 — Orphaned children** | FK `parent_id → folders.id ON DELETE SET NULL`; purge path sets parent_id=NULL on hard delete; children become root-level orphans rather than dangling references |
| **H2 — Stale `path` column** | `path` is only written at creation and move (F5.3); rename does NOT change path → no corruption risk |
| **H3 — Depth mismatch** | `depth` is written at creation; rename/delete does not change depth; only move (F5.3) would recompute depth |
| **H4 — Circular reference via restore** | Restore does not change `parent_id`; circular reference is structurally impossible in adjacency list with enforced parent validation at creation |
