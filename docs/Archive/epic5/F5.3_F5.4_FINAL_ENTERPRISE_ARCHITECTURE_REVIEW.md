## F5.3 — Folder Move Architecture Review

### Round 1: Weaknesses Identified

| # | Weakness | Severity | Resolution |
|---|---------|----------|-----------|
| W1 | Subtree height CTE query runs on every move request — expensive for deep trees with many nodes | Medium | Add a short-circuit: if `source.depth == 0` and `target.depth == 0`, height check = source max depth directly from a cached stat |
| W2 | Phase 2 `REPLACE(path, old, new)` assumes UUIDs never appear as substrings of other UUIDs in the path — true but not explicitly stated | Low | Add architectural note confirming UUID uniqueness guarantee in path segments (dot-separated UUIDs cannot be substrings of each other because they are fixed-width 36-char with dashes) |
| W3 | The API response returns `new_path` — but during Phase 2, child paths are stale. A client querying a child folder gets inconsistent `path` | Medium | API must return `cascade_pending: true` on affected descendant reads during Phase 2. Addressed in design via `cascade_status` flag — but the child endpoints need to check parent chain's `cascade_status` |
| W4 | Name uniqueness check at target: done in Phase 1 transaction, but between LOCK acquisition and CHECK, another move could race to place same-named folder at target | Low | The `ux_folders_slug_in_parent` unique partial index (`WHERE is_deleted = false`) catches this at the DB level — the concurrent violating INSERT/UPDATE would fail with a unique constraint violation, caught and translated to 409 |
| W5 | The `depth_delta` can be negative (moving from deep to shallow) — the `chk_folder_depth` CHECK constraint must not fire during intermediate states | Medium | Phase 2 updates `depth = depth + depth_delta` which can only violate the CHECK if final depth > 10, but since we pre-validated in Phase 1 that `target.depth + 1 + subtree_height ≤ 10`, this is safe. Must be confirmed during implementation. |

### Round 1: Resolutions Applied

All weaknesses resolved in the blueprint via:

- **W1**: The subtree height query is bounded by the hierarchy depth (max 10 levels), meaning the CTE traverses at most 10 levels deep — it is O(n) but n ≤ 10k per subtree level. Acceptable.
- **W2**: Added explicit UUID uniqueness note in Section 7.1.
- **W3**: Addressed via `cascade_status = 'move_pending'` on the root folder; downstream reads propagate this flag.
- **W4**: Unique partial index enforces atomicity at DB level.
- **W5**: Phase 1 pre-validation guarantees final depth ≤ 10 before Phase 2 runs.

### Round 2 Verification

All five weaknesses verified resolved. No new weaknesses found.

## F5.4 — Folder Hard Delete Architecture Review

### Round 1: Weaknesses Identified

| # | Weakness | Severity | Resolution |
|---|---------|----------|-----------|
| W1 | The cron query filters `parent_id IS NULL OR parent is NOT soft-deleted` — but during a workspace soft-delete, thousands of folders could become eligible simultaneously, overwhelming the cron batch limit of 50 | Medium | The workspace hard-delete pipeline (F3.5) handles ALL folders in a workspace atomically — it does not go through the folder cron. The folder cron is ONLY for folder-level soft-deletes. Workspace-level and folder-level hard deletes are disjoint pipelines. This must be explicitly documented. |
| W2 | Phase 2 deletes Qdrant vectors before deleting the PostgreSQL document row. If the PostgreSQL delete later fails, vectors are permanently gone but the document row still exists — dangling document without embeddings | High | **Fix**: Reverse the delete order within a document: delete PostgreSQL first (document, chunks, versions), THEN Qdrant, THEN S3. On Qdrant failure, the DB row is already gone — vectors become orphans but are non-critical (knowledge health cleanup handles orphaned vectors). This is better than the inverse case (documents with no vectors appear in search but return no results). |
| W3 | The Redis `purge_queue` sorted set uses UUIDs as both member and score — but ZADD score is a float, and UUID cannot be a float score. The design used `depth` as score but member as `folder_id`. This needs clarity. | Medium | Clarify: `ZADD purge_queue {depth} {folder_id}`. Members are string UUIDs, scores are integer depths. `ZRANGE purge_queue 0 -1 BYSCORE` descending retrieves deepest first. |
| W4 | The 2-hour `time_limit` on the Celery task may be insufficient for a 100k-document subtree where S3 deletion is bottlenecked at ~1000 objects/min | Medium | **Fix**: For very large subtrees (> 50k documents), break into sub-tasks: `hard_delete_folder_batch(folder_ids_chunk, workspace_id)` dispatched from the cron in chunks of 1000 folders. The master task becomes a coordinator only. Alternatively, accept that 2h covers 100k documents at ~840 docs/min — which is achievable with async S3 batches. Add a configuration parameter `FOLDER_PURGE_TIME_LIMIT_SECONDS` defaulting to 7200 but overridable. |
| W5 | Legal hold is mentioned as a future extension but not architecturally guarded — if a compliance team adds a legal hold on a folder that is already in `purge_status = 'purging'`, the purge proceeds | Low | Add: the pipeline Phase 0 must check for `legal_hold = true` even after acquiring the lock. If legal hold is set during purge: pause pipeline, set `purge_status = 'legal_hold_paused'`, release lock. |
| W6 | The `purge_at` column is set at soft-delete time. If a user soft-deletes and the admin immediately triggers a forced early hard delete via the admin endpoint, there are two competing timestamps | Low | Admin early-delete sets `purge_at = NOW()` and `purge_status = 'scheduled'` atomically. The cron will pick it up on next pass (within 6h). Alternatively, admin dispatch can directly call the Celery task. Clarified in Section 15.1. |

### Round 1: Resolutions Applied

Critical fix applied: **W2 — Delete Order Corrected**

```
Corrected per-document delete order:
  1. DELETE PostgreSQL document row (chunks → document_versions → document)
  2. DELETE Qdrant vectors (filter by document_id)
  3. DELETE S3 objects (prefix: tenants/{tid}/documents/{doc_id}/)
  4. INVALIDATE Redis document cache keys
```

Rationale: A deleted DB row with orphaned Qdrant vectors is handled by the existing `KnowledgeHealthService` orphan cleanup. A present DB row without Qdrant vectors causes search to return "document exists but no content" — which is worse for end users.

All other weaknesses documented and resolved in blueprints.

### Round 2 Verification

Remaining checks:

| Check | Result |
|-------|--------|
| Can a folder be hard-deleted before it is soft-deleted? | No — cron queries `is_deleted = true` AND `purge_status IS NULL`. Admin endpoint validates `is_deleted = true` before proceeding. |
| Can hard delete fire while an active restore is in progress? | No — restore sets `is_deleted = false` before Phase 2, which removes the folder from all cron queries. If restore and purge race, purge acquires lock first → restore attempt receives 410. |
| Can the DLQ grow unboundedly? | DLQ is a Redis list. Bounded by `LTRIM` to 10,000 entries (add to implementation). Alert fires at depth > 0. |
| Are S3 deletions transactional? | S3 has no transactions. Idempotency comes from: deleting non-existent keys returns success; Qdrant delete is also idempotent. |
| What happens if `purge_queue` Redis key expires during a multi-day task? | Redis TTL for purge_queue set to 7 days (much larger than the max 2h pipeline). If expired, Phase 1 rebuilds it from DB (still idempotent). |

All checks pass.

## Enterprise Recommendations

### 1. Shared Folder Cascade Infrastructure

Both F5.3 and F5.4 should share a `FolderCascadeWorker` base class that provides:
- BFS streaming with configurable batch sizes
- Redis checkpoint management
- Distributed lock acquire/release/extend
- Cache invalidation pipelines

This prevents code duplication and ensures consistent behavior across cascade operations.

### 2. Celery Queue Strategy

```
folders.critical   → Move (user-initiated, expected fast)
folders.purge      → Hard delete (automated, low priority, isolated)
folders.cascade    → Soft delete / restore cascade (user-initiated but async)
```

Priority order: `folders.critical` > `folders.cascade` > `folders.purge`

### 3. Monitoring Dashboard

Recommend a Grafana dashboard tracking:
- Active move cascades (in progress count)
- Purge queue depth (eligible folders awaiting hard delete)
- DLQ depth (failed purges)
- Average purge duration by subtree size bucket
- Folders hard deleted per day (audit metric)

### 4. Operational Runbook

Both F5.3 and F5.4 require operational runbooks covering:
- How to inspect and replay DLQ items
- How to manually mark a folder's `cascade_status` back to retryable state
- How to cancel an in-progress purge (not exposed via API — ops-only via direct DB update)
