# F5.5 — Document Archive & Restore Architecture

## 1. Overview
The Document Archive & Restore feature provides a non-destructive state transition for documents. Archiving a document hides it from normal retrieval, search, and RAG pipelines while preserving the physical artifacts in storage (S3/MinIO) and maintaining its structural relationships in the database.

## 2. Database & Entity Architecture

### 2.1. Model Changes (`Document`)
The `DocumentStatus` enum will be expanded, or we utilize the existing statuses and rely on a new `is_archived` boolean. However, keeping with the state machine approach, we will introduce an `ARCHIVED` status.
- Add `DocumentStatus.ARCHIVED` to the `DocumentStatus` Enum.
- Add `archived_at` (DateTime) and `archived_by_user_id` (UUID) to track who archived the document.

```python
# In backend/document/models/status.py
class DocumentStatus(str, Enum):
    # ... existing statuses ...
    ARCHIVED = "ARCHIVED"

# In backend/document/models/document.py
class Document(BaseModel):
    # ...
    archived_at: Mapped[datetime.datetime | None] = mapped_column(DateTime(timezone=True), nullable=True)
    archived_by_user_id: Mapped[uuid.UUID | None] = mapped_column(
        UUID(as_uuid=True), ForeignKey("users.id", ondelete="SET NULL"), nullable=True
    )
```

### 2.2. Folder Dependency Validation
- **Archive Action**: Can archive a document anytime, regardless of folder state.
- **Restore Action**: If a document is restored but its parent `Folder` is `is_deleted = True`, the document should ideally be restored into the root (parent_id = None) or the restore action should be rejected until the folder is restored. We will enforce a strict rule: **Reject restore if parent folder is soft-deleted** with a specific error code (`DOC_004_FOLDER_DELETED`), requiring the user to either restore the folder first or specify a new folder destination during the restore call.

## 3. Service & Repository Layer

### 3.1. `DocumentRepository` Updates
- `archive_document(document_id, tenant_id, user_id)`: Transitions status to `ARCHIVED`, sets `archived_at` and `archived_by_user_id`.
- `restore_document(document_id, tenant_id, user_id)`: Transitions status back to `PROCESSED` (or previous known stable state, though returning to `READY`/`PROCESSED` is standard).
- `list_documents(...)`: Ensure that queries filter out `ARCHIVED` documents by default unless an `include_archived=True` or `status=ARCHIVED` flag is explicitly passed.

### 3.2. `DocumentService` Additions
- `archive_document(document_id, tenant_id)`
  1. Acquire lock on the document.
  2. Validate current status (cannot archive if `status in [DELETED, ARCHIVED]`).
  3. Update database state.
  4. Emit `DOCUMENT_ARCHIVED` domain event.
  5. Enqueue background Celery task to purge vectors from Qdrant.
- `restore_document(document_id, tenant_id, target_folder_id=None)`
  1. Check folder dependencies (ensure folder is not deleted).
  2. Update database state.
  3. Emit `DOCUMENT_RESTORED` domain event.
  4. Enqueue background Celery task to re-index the document's latest version into Qdrant.

## 4. Vector DB (Qdrant) Handling & Workers

Archiving a document must exclude it from RAG pipelines to save RAM and ensure accuracy.

### 4.1. Archiving (Vector Removal)
- Task: `remove_archived_document_vectors`
- Worker uses `VectorStorageService.delete_document_points(document_id, tenant_id)` to scrub points from the active Qdrant collections.
- The PostgreSQL `ChunkEmbedding` records remain intact, preserving the vectors on disk! Only Qdrant is purged. This makes restoration extremely fast as we do not need to re-run the LLM embedding pipeline.

### 4.2. Restoring (Vector Re-sync)
- Task: `restore_archived_document_vectors`
- Worker uses `VectorStorageService.sync_document_vectors(document_id, latest_version_id, tenant_id)` to push the existing `ChunkEmbedding` arrays back into Qdrant.

## 5. Bulk Archive Support
- Introduce a new API endpoint `POST /documents/archive/bulk`.
- Request body accepts a list of `document_ids`.
- The service processes the state transition in a single database transaction (using `UPDATE ... WHERE id IN (...)`).
- Emits bulk events or individual events.
- Enqueues a single batch vector removal task to minimize Celery overhead.

## 6. Event Architecture
- **`DOCUMENT_ARCHIVED`**: Dispatched synchronously. Triggers audit logging and vector removal.
- **`DOCUMENT_RESTORED`**: Dispatched synchronously. Triggers audit logging and vector re-indexing.

## 7. API Architecture
- `POST /v1/documents/{document_id}/archive`
- `POST /v1/documents/{document_id}/restore`
- `POST /v1/documents/bulk-archive` (accepts `{"document_ids": [...]}`)

## 8. Cache Invalidation
- Archiving or restoring invalidates `rg:v2:{tenant}:document:{id}`.
- List endpoints for documents should clear their paginated cache tags if caching is applied at the list level.

## 9. Security Model & RBAC Matrix
- **Security Model**: Archive/Restore endpoints strictly validate `tenant_id` namespace matching the document. All operations enforce the user's role via the `PermissionRegistry`.
- **RBAC Matrix**:
  - `OWNER`, `ADMIN`: Allowed to archive, restore, and bulk archive.
  - `MEMBER`, `ENGINEER`, `ANALYST`: Allowed to archive/restore if they possess the explicit `DOCUMENT_ARCHIVE` or `DOCUMENT_UPDATE` permission.
  - `VIEWER`, `EXTERNAL`: Denied.

## 10. Frontend Architecture
- Add `Archive` and `Restore` actions to the Document contextual menu (three dots) in the UI.
- Introduce a "Show Archived Documents" toggle in the list view, modifying the `GET /documents?status=ARCHIVED` query parameter.
- Display a visual badge (gray or distinct icon) for archived documents.
- Bulk selection checkboxes should enable a "Bulk Archive" action button.

## 11. Performance & Scalability
- **Performance**: Database state transitions are instantaneous. The `bulk-archive` API operates efficiently by doing an `IN` query.
- **Scalability**: Vector removal is deferred to a Celery background worker, preventing large documents (with thousands of chunks) from causing API gateway timeouts.

## 12. Failure Recovery & Multi-Tenancy
- **Failure Recovery**: If a worker fails to delete Qdrant points during archiving, the Celery exponential backoff will automatically retry the operation. Qdrant payload deletions are idempotent.
- **Multi-Tenancy**: All DB updates and Qdrant operations include `tenant_id` scoping to prevent cross-tenant data corruption.

## 13. Observability & Monitoring
- **Observability**: Structured logs injected with `tenant_id` and `document_id`. Audit logs record the timestamp and `user_id` performing the archive.
- **Monitoring**: Datadog metrics tracking `document.archived.count` and tracking Celery worker queues for the `remove_archived_document_vectors` task to monitor latency.

## 14. Future Extensibility
- **Legal Hold**: The architecture supports a future `legal_hold` flag. A document on legal hold cannot be hard-deleted or modified, but can be archived.
