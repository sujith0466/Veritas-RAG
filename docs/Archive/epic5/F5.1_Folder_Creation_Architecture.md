# F5.1 — Folder Creation Architecture

**Epic:** 5 — Document & Folder Management
**Feature:** F5.1 — Folder Creation
**Version:** 1.0 — Architecture Frozen
**Status:** ⏳ PENDING APPROVAL

---

## 1. Executive Summary

F5.1 implements the core folder hierarchy backbone for RAGuard V2's multi-tenant document management system. Folders use an **Adjacency List** model with a **depth-stamped column** for O(1) depth validation, complemented by a **Closure Table** for efficient subtree queries. The design supports unlimited siblings, maximum depth of 10, strict tenant isolation, and full compatibility with the existing `BaseRepository` / `BaseModel` / `EventDispatcher` infrastructure.

---

## 2. Domain Model

### 2.1 Entity: `Folder`

```
folders
├── id                  UUID PK (BaseModel)
├── workspace_id        UUID FK → workspaces.id (CASCADE)  — tenant partition key
├── parent_id           UUID FK → folders.id (SET NULL)    — adjacency list self-ref; NULL = root
├── name                VARCHAR(255)                        — display name
├── slug                VARCHAR(255)                        — URL-safe, scoped per parent within workspace
├── depth               SMALLINT NOT NULL DEFAULT 0         — materialised depth (root = 0)
├── path                TEXT NOT NULL                       — materialised path: "<root_id>/<child_id>/..."
├── document_count      INTEGER NOT NULL DEFAULT 0          — denormalised counter for UI performance
├── is_deleted          BOOLEAN NOT NULL DEFAULT FALSE       — BaseModel soft-delete flag
├── deleted_at          TIMESTAMPTZ                         — BaseModel soft-delete timestamp
├── deleted_by_user_id  UUID FK → users.id (SET NULL)
├── created_by_user_id  UUID FK → users.id (SET NULL)
├── version             INTEGER NOT NULL DEFAULT 1          — optimistic locking
├── created_at          TIMESTAMPTZ (BaseModel)
└── updated_at          TIMESTAMPTZ (BaseModel)
```

**Key design decisions:**
- `depth` is **materialized** alongside parent_id. Updates are atomic within a single write; no recursive query required for depth checking.
- `path` stores the full ancestry chain as a `/`-delimited UUID string (e.g., `"<ws_id>/<root_id>/<child_id>"`). This enables fast prefix-scan subtree detection and circular-reference detection in O(n) string search.
- `slug` is scoped to `(workspace_id, parent_id, slug)` — unique only within the same parent level, not globally.

### 2.2 Indexes

```sql
-- Primary lookup: all root folders for a workspace
CREATE INDEX ix_folders_workspace_root
    ON folders (workspace_id, parent_id)
    WHERE is_deleted = FALSE;

-- Children of a specific folder
CREATE INDEX ix_folders_parent
    ON folders (parent_id)
    WHERE is_deleted = FALSE;

-- Slug uniqueness within parent scope
CREATE UNIQUE INDEX ux_folders_slug_in_parent
    ON folders (workspace_id, parent_id, slug)
    WHERE is_deleted = FALSE;

-- Depth-bounded subtree scans
CREATE INDEX ix_folders_path
    ON folders USING GIST (path gist_trgm_ops);

-- Soft-deleted retention queries
CREATE INDEX ix_folders_deleted_at
    ON folders (workspace_id, deleted_at)
    WHERE is_deleted = TRUE;
```

### 2.3 Invariants & Constraints

| Invariant | Enforcement Layer |
|---|---|
| `depth <= 10` | Service-layer validation + DB CHECK constraint |
| `parent_id` belongs to same workspace | Service-layer validation |
| No circular reference | Path-prefix check during service creation |
| Unique name within parent (case-insensitive) | DB partial unique index + service validation |
| Deleted parent cannot receive children | Service-layer: parent must have `is_deleted = FALSE` |
| `document_count >= 0` | DB CHECK constraint |

## 3. Architecture: Service Layer

### 3.1 `FolderService` — Operations

```
FolderService
├── create_folder(workspace_id, actor_id, name, parent_id=None) → Folder
├── list_root_folders(workspace_id, actor_id, cursor, limit) → Page[FolderSummary]
├── list_children(workspace_id, folder_id, actor_id, cursor, limit) → Page[FolderSummary]
├── get_folder(workspace_id, folder_id, actor_id) → Folder
└── get_folder_breadcrumbs(workspace_id, folder_id, actor_id) → list[FolderBreadcrumb]
```

### 3.2 Creation Flow (F5.1 Only)

```
POST /api/v1/workspaces/{ws_id}/folders

Step 1 — RBAC Guard
    ├── Resolve actor membership via WorkspaceMemberRepository
    ├── Require Permission.FOLDERS_CREATE
    └── Reject 403 if insufficient

Step 2 — Workspace Validation
    ├── Load workspace → must be ACTIVE and PROVISIONING_STATUS=READY
    └── Reject 409 if workspace is SUSPENDED/ARCHIVED/DELETED

Step 3 — Parent Validation (if parent_id provided)
    ├── Load parent folder by (folder_id, workspace_id)
    ├── Assert parent.workspace_id == request.workspace_id  [Tenant Isolation]
    ├── Assert parent.is_deleted == False
    ├── Assert parent.depth <= 9  (child would be depth 10, which is the max)
    └── Reject 422 if any assertion fails

Step 4 — Circular Reference Guard
    ├── This is a new folder — circular reference cannot occur at creation
    └── (Reserved for F5.2 move operation; no-op here)

Step 5 — Duplicate Name Check
    ├── Normalise: name.strip().lower()
    ├── Query: SELECT COUNT(*) FROM folders
    │         WHERE workspace_id=? AND parent_id=? AND lower(name)=? AND is_deleted=FALSE
    └── Reject 409 if count > 0

Step 6 — Materialized Fields Computation
    ├── depth = parent.depth + 1  (or 0 if root)
    ├── path = parent.path + "/" + new_id_placeholder
    └── slug = slugify(name)  [URL-safe, collision suffix if needed]

Step 7 — Optimistic Lock Write
    ├── INSERT INTO folders (...) with computed depth, path, version=1
    └── Flush & Refresh

Step 8 — Audit Log
    └── AuditLog(action="folder.created", user_id=actor_id,
                resource_type="folder", resource_id=str(folder.id),
                details={name, parent_id, depth, workspace_id})

Step 9 — Domain Event
    └── dispatcher.publish(FolderCreatedEvent(...))

Step 10 — Cache Write-Through
    ├── Invalidate: "ws:{ws_id}:folders:root_list" (if root folder)
    ├── Invalidate: "ws:{ws_id}:folder:{parent_id}:children" (if child)
    └── Write:     "ws:{ws_id}:folder:{folder_id}" → FolderSummaryDTO (TTL 300s)

Return 201 Created with FolderResponse
```

```
FolderRepository
├── get_by_id_in_workspace(id, ws_id) → Folder | None
├── get_children(parent_id, ws_id, cursor, limit) → Page[Folder]

├── get_ancestors(folder_id, ws_id) → list[Folder]
│   └── [Uses iterative path parse — no recursive SQL]
├── increment_document_count(folder_id, delta: int = 1) → None
│   └── [UPDATE ... SET document_count = document_count + delta, version = version + 1]
└── get_subtree_ids(folder_id, ws_id) → list[UUID]
    └── [Recursive CTE — used only by F5.2 cascade operations]
```

> **Rule:** All repository methods filter by `workspace_id` at the SQL layer. No cross-tenant data is ever returned.

## 8. Redis Cache Strategy

### 8.1 Cache Keys

| Key Pattern | Content | TTL | Invalidation Trigger |
|---|---|---|---|
| `ws:{ws_id}:folders:root_list:{cursor}` | Page[FolderSummary] root level | 300s | Any root folder created/deleted |
| `ws:{ws_id}:folder:{folder_id}:children:{cursor}` | Page[FolderSummary] children | 300s | Child created/deleted/renamed |
| `ws:{ws_id}:folder:{folder_id}` | FolderSummary single entity | 300s | Folder updated/deleted/renamed |
| `ws:{ws_id}:folder:{folder_id}:breadcrumbs` | list[BreadcrumbDTO] | 600s | Any ancestor renamed/deleted |

### 8.2 Cache Strategy

- **Read pattern:** Cache-aside (check cache → DB fallback → write-through on miss).
- **Write pattern:** Invalidate then write-through on successful creation.
- **Prefix-scoped invalidation:** On workspace delete/suspend, invalidate `ws:{ws_id}:folders:*` via Redis SCAN + DEL pattern. Bounded by workspace ID prefix.
- **No stampede risk:** All cache writes use `SET NX PX` (set only if not exists, with TTL) to prevent concurrent hydrations from overwriting newer data.

## 9. Pagination

- **Cursor-based pagination** (consistent with Epic 3 workspace list patterns).
- Default `limit=20`, maximum `limit=100`.
- Cursor encodes `(created_at, id)` tuple, base64-encoded opaque token.
- Response includes `next_cursor: str | null` and `has_more: bool`.

## 10. Search Strategy

- **Phase 1 (F5.1 scope):** Name prefix search via `ILIKE 'query%'` within a workspace and optional parent scope. Index: `ix_folders_workspace_root` + runtime filter.
- **Phase 2 (future):** Full-text search via `tsvector` on `name` + `path` columns with `GIN` index. Compatible with existing `path` column structure.

**Search endpoint:**
```
GET /api/v1/workspaces/{ws_id}/folders/search?q=legal&parent_id=<uuid>
→ 200 list[FolderSummaryResponse]  (max 50 results, no cursor)
```

### 11.2 Creation Interaction

1. User clicks "New Folder" or context menu "New Subfolder".
2. Inline text input appears at target level.
3. On Enter or blur: `POST /api/v1/workspaces/{ws_id}/folders` fires.
4. Optimistic UI: folder appears immediately with loading state.
5. On success: replace optimistic node with real data (id, slug, version).
6. On 409 (duplicate): show inline error "A folder with this name already exists."
7. On 422 (max depth): show toast "Maximum folder depth of 10 reached."

## 12. Performance Considerations

| Concern | Mitigation |
|---|---|
| Deep hierarchy reads (breadcrumbs) | Materialized `path` → O(n) string parse, no recursive SQL |
| Large sibling lists (10k+ folders) | Cursor pagination; index on `(workspace_id, parent_id)` |
| `document_count` accuracy | Denormalized counter with `UPDATE ... SET count = count + delta` in same transaction as document create |
| Cold cache on workspace load | Prefetch root folders on workspace selection; hydrate L2 cache proactively |
| Subtree count queries | `SELECT COUNT(*) ... WHERE path LIKE '<prefix>%'` with `ix_folders_path` GIST index |

## 13. Future Compatibility — Document Inheritance

The `path` column is the forward-compatibility hook for document inheritance:
- Documents will store an `effective_folder_id` and `inherited_settings: JSONB`.
- Folder-level settings (search index scope, retention policy, access tags) will be resolved by walking the `path` array from leaf to root, applying first-match precedence.
- No schema changes required: documents reference `folder_id → folders.id` and use the folder's existing `path` for ancestry resolution.

## 14. Principal Engineer Review

### 14.1 Race Conditions

| Risk | Scenario | Mitigation |
|---|---|---|
| **R1 — Duplicate creation race** | Two concurrent requests for same name in same parent | DB partial unique index `ux_folders_slug_in_parent` + serialized `INSERT` + DB-level uniqueness constraint ensures exactly one succeeds; loser receives 409 |
| **R2 — Depth violation race** | Parent at depth 9; two concurrent children try to create a grandchild | `depth` is a computed field written atomically on INSERT; no read-then-write on depth — the child's INSERT fails DB CHECK if `depth > 10`; additionally service validates `parent.depth + 1 <= 10` under shared lock |
| **R3 — Parent soft-delete race** | Parent is deleted concurrently with child creation | Child creation `SELECT ... FOR UPDATE` on parent row; if parent's `is_deleted` is flipped to TRUE between service check and DB flush, the partial unique index prevents orphan creation; additional FK `ON DELETE CASCADE` on soft-deleted purge path |

### 14.2 Scalability

| Risk | Mitigation |
|---|---|
| **S1 — Workspace with millions of folders** | `(workspace_id, parent_id)` composite index; cursor pagination; GIST index on `path` for subtree scans |
| **S2 — High-concurrency folder creation** | No global lock; per-parent uniqueness at DB layer; Redis per-parent rate limiting: max 10 concurrent creates per parent per second |
| **S3 — Cache invalidation fan-out** | Cache keys are scoped per `(workspace_id, folder_id)` — no global cache to invalidate; parent invalidation at max 2 keys per creation operation |

### 14.3 Security

| Risk | Mitigation |
|---|---|
| **SEC1 — Cross-tenant folder access** | `workspace_id` enforced at every repository query — no query omits tenant filter |
| **SEC2 — Path traversal via parent_id** | Parent validation explicitly checks `parent.workspace_id == request.workspace_id` before accepting the reference |
| **SEC3 — Name injection** | Names are stored as-is and rendered HTML-escaped in the frontend; slugs are sanitized via `slugify()` |
| **SEC4 — Privilege escalation** | RBAC guard is the first step in every service method before any DB read |

### 14.4 Caching

| Risk | Mitigation |
|---|---|
| **C1 — Stale folder count** | `document_count` is updated in the same DB transaction as document create/delete; never stale at persistence level. Cache TTL 300s is acceptable for UI counters |
| **C2 — Stale children list** | `children` cache is invalidated on every child create/delete/rename before DB write (write-invalidate) |
| **C3 — Breadcrumb stale on ancestor rename** | Breadcrumb cache key includes `folder_id`; ancestor rename invalidates all descendant breadcrumb keys via path-prefix scan in Redis |
