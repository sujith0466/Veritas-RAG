## Review Area 1: Folder Move Readiness

### Finding
F5.1/F5.2 mention "F5.3 move operation" but do not formally commit to a move-compatible schema contract. If path/depth recomputation is not architected now, a future move feature will require a migration that touches every folder row in every affected subtree simultaneously — a dangerous operation in production.

### Refinements Required

**1.1 — Explicit Move Contract Committed in F5.1 Schema**

The `path` and `depth` columns must be formally documented as **move-mutable** fields. The following update protocol is locked now:

```
FUTURE MOVE OPERATION (F5.3 — Architecture Contract, Not Implementation):

When folder X is moved from parent A to parent B:
  1. BEGIN TRANSACTION
  2. SELECT FOR UPDATE on folder X AND new parent B
  3. Validate:
     - B.workspace_id == X.workspace_id  [tenant isolation]
     - B.depth + subtree_height(X) <= 10  [depth preservation]
     - X.id NOT IN ancestor chain of B   [circular reference prevention]
  4. Compute:
     - new_depth = B.depth + 1
     - depth_delta = new_depth - X.depth
     - old_path_prefix = X.path
     - new_path_prefix = B.path + "/" + X.id
  5. Atomic batch UPDATE:
     UPDATE folders
     SET path = REPLACE(path, old_path_prefix, new_path_prefix),
         depth = depth + depth_delta,
         version = version + 1,
         updated_at = now()
     WHERE path LIKE old_path_prefix || '%'
       AND workspace_id = X.workspace_id  [MUST include tenant guard]
  6. Update X.parent_id = B.id
  7. COMMIT
  8. Cache invalidate: all path-overlapping keys
```

**1.2 — Circular Reference Prevention Already Proven Safe**

Current architecture: `path` encodes full ancestry chain. Before move, check:
```
assert B.id NOT IN X.path.split("/")
```
This O(depth) string check prevents any circular reference without a recursive DB query. ✅

**1.3 — `REPLACE(path, ...)` Index Impact**

Add explicit note to F5.1: The `ix_folders_path` GIST index on `path` will require re-indexing of all moved subtree rows. For large moves, the index update is the bottleneck. Mitigation: moves are serialized per subtree root via distributed lock `lock:ws:{ws_id}:folder:{folder_id}:move` (Redis SETNX, TTL 30s).

**Assessment: REFINEMENT APPLIED — Move contract is now formally locked into the schema design.**

## Review Area 2: Transaction Boundaries

### Finding
F5.2 states "Flush (no commit between batches — single transaction)" for the cascade worker processing up to 50,000 rows in a single transaction. This is **incorrect for production**: a 50,000-row transaction holds DB locks for an extended duration, blocks VACUUM, and risks OOM on the session.

### Refinements Required

**2.1 — Corrected Transaction Model: Per-Batch Commit**

Replace the original single-transaction cascade with per-batch commit with a cursor:

```
CORRECTED Worker Algorithm:

1. Fetch ALL subtree IDs via recursive CTE (read-only, no lock held):
   └── Returns list[UUID] — in-memory, bounded by depth ≤ 10

2. Chunk into batches of 200 IDs

3. For EACH batch:
   BEGIN TRANSACTION (scoped to this batch only)
     UPDATE folders SET is_deleted=TRUE, deleted_at=?, deleted_by_user_id=?
     WHERE id IN (...200 ids...) AND is_deleted=FALSE AND workspace_id=?
   COMMIT  ← Releases lock immediately; no long-held transaction
   DEL Redis keys for this batch (pipeline)
   Sleep 10ms  ← Yield to other DB operations between batches

4. After all batches: emit FolderChildrenSoftDeletedEvent + AuditLog
```

**Idempotency is preserved:** `WHERE is_deleted=FALSE` still prevents double-deletion on retry.
**Lock duration bounded:** Maximum lock time = time to UPDATE 200 rows ≈ 5–20ms.

**2.2 — Explicit Transaction Boundary Table (F5.1 + F5.2)**

| Operation | DB Transaction Scope | Celery Begins |
|---|---|---|
| Folder Create (F5.1) | Single TX: INSERT folder + AuditLog (same flush) | Never |
| Folder Rename (F5.2) | Single TX: UPDATE name/slug/version + AuditLog | Never |
| Folder Delete Phase 1 (F5.2) | Single TX: UPDATE is_deleted=TRUE (root only) + AuditLog | After COMMIT |
| Folder Delete Phase 2 (F5.2) | Per-batch TX (200 rows each): UPDATE + per-batch AuditLog | Entire Phase 2 is Celery |
| Restore Phase 1 (F5.2) | Single TX: UPDATE is_deleted=FALSE (root only) + AuditLog | After COMMIT |
| Restore Phase 2 (F5.2) | Per-batch TX (200 rows each): UPDATE + per-batch AuditLog | Entire Phase 2 is Celery |

> **Rule:** Celery is NEVER enqueued inside a DB transaction. The enqueue happens immediately AFTER the HTTP-handler transaction commits. This prevents a scenario where Celery picks up the task before the transaction commits, causing it to find no data.

**2.3 — AuditLog Placement in TX**

AuditLog rows for Phase 1 are written inside the Phase 1 transaction (same DB session, same flush). This ensures the audit trail is atomic with the mutation: if the mutation rolls back, the audit log is never written.

**Assessment: CRITICAL REFINEMENT APPLIED — Per-batch commit replaces single-transaction cascade.**

### Scenario Matrix

| Scenario | Behavior | Verdict |
|---|---|---|

## Review Area 4: Recursive Delete Safety

### Finding
The original design fetches ALL subtree IDs into memory before batching. For a workspace with 50,000 descendants, this results in a list of 50,000 UUIDs in Python memory before any processing begins.

### Refinement: Streaming Cursor-Based Traversal

Replace the upfront full-fetch pattern with a streaming cursor BFS traversal:

```
REFINED Worker Algorithm (Streaming BFS):

state = queue of folder_ids to process, initialized with [root_folder_id]
total_deleted = 0

WHILE state is non-empty:
  current_batch_parents = state.pop(200)  ← Process at most 200 parents at a time

  BEGIN TRANSACTION
    -- Step A: Soft-delete this batch of parents
    UPDATE folders SET is_deleted=TRUE, deleted_at=?, deleted_by_user_id=?
    WHERE id IN (...current_batch_parents...)
      AND is_deleted=FALSE
      AND workspace_id=?  [TENANT GUARD]
    rows_deleted = rowcount

    -- Step B: Fetch their direct children (next level to process)
    next_children = SELECT id FROM folders
                    WHERE parent_id IN (...current_batch_parents...)
                      AND is_deleted=FALSE
                      AND workspace_id=?  [TENANT GUARD]
                    LIMIT 1000  [safety cap per level]
  COMMIT

  -- Step C: Enqueue children for next iteration
  state.extend(next_children)
  total_deleted += rows_deleted

  -- Step D: Cache invalidation for this batch
  DEL pipeline for current_batch_parents (100 per pipeline)

  -- Step E: Yield
  await asyncio.sleep(0.01)  ← 10ms yield between batches

-- End: emit FolderChildrenSoftDeletedEvent(deleted_count=total_deleted)
```

**Benefits of streaming BFS:**
- **Never loads full tree into memory.** At any point, only current batch + next children live in memory.
- **Bounded by depth ≤ 10 levels.** Maximum 10 outer loop iterations even for infinite siblings.
- **Interruptible & resumable.** If worker dies, retry resumes from the next unprocessed batch (but since per-parent rows are committed, already-deleted rows are skipped).
- **Child fetch bounded:** `LIMIT 1000` per level per batch prevents overwhelming the result set.

**Maximum batch_size = 200.** This is the architectural constant. Never configurable at runtime to prevent operator error.

**Assessment: CRITICAL REFINEMENT APPLIED — Full-fetch replaced with streaming BFS.**

## Review Area 5: Document Consistency

### Finding
The JOIN-filter rule in Section 4.2 of F5.2 is correct but underspecified. The rule must be formalized as an **inviolable architectural contract** that all document-accessing repositories must honour.

### Refinements

**5.1 — Document Visibility Contract (Formally Defined)**

```
DOCUMENT VISIBILITY CONTRACT (Must be honoured by ALL future document queries):

A document is VISIBLE if and only if:
  1. document.is_deleted = FALSE
  2. document.folder_id IS NULL           [un-filed document, always visible]
     OR folder.is_deleted = FALSE         [filed document in active folder]
  3. document.workspace_id = :ws_id       [tenant isolation, always]

SQL enforcement (DocumentRepository base query):
  SELECT d.* FROM documents d
  LEFT JOIN folders f ON d.folder_id = f.id
  WHERE d.workspace_id = :ws_id
    AND d.is_deleted = FALSE
    AND (d.folder_id IS NULL OR f.is_deleted = FALSE)
```

> **Note:** `LEFT JOIN` (not `INNER JOIN`) is required because some documents may have `folder_id = NULL` (filed at workspace root, no folder). An INNER JOIN would invisibilise unfiled documents.

**5.2 — Document Orphan Prevention on Folder Delete**

Current: FK `document.folder_id → folders.id ON DELETE SET NULL`.
Assessment: Correct. When a folder is hard-purged (future retention flow), documents become unfiled (`folder_id = NULL`) and remain visible — they do NOT disappear. This is the correct enterprise behavior (consistent with Google Drive: deleted folder → documents appear in "My Drive" root).

**5.3 — Document Count Consistency During Cascade**

When cascade delete marks 1,000 child folders as deleted, the `document_count` on those folders becomes irrelevant (folders are invisible). However, the parent folder's `document_count` does NOT include child folder document counts (it's a per-folder counter). This is correct and requires no additional action.

**5.4 — Folder Delete During Active Upload**

New edge case (not covered in original):
- User begins uploading to folder X. Upload is a multi-step operation (presigned URL, then metadata write).
- Admin deletes folder X during upload.
- Upload's metadata write sets `document.folder_id = X`.
- X is now `is_deleted=TRUE`. Document is written but invisible.

**Resolution:**
- Document API must validate `folder.is_deleted = FALSE` before accepting a document write to that folder.
- If folder is deleted at document-write time → 409 `folder_deleted` error.
- Upload presigned URL generation also validates folder status. Both gates must be enforced.

**Assessment: CRITICAL REFINEMENTS APPLIED — LEFT JOIN rule, unfiled documents, upload-during-delete gate.**

## Review Area 6: Cache Consistency

### Finding
The original F5.2 cache invalidation strategy is largely correct but missing two gaps: (a) `document_count` counter cache and (b) the exact ordering of DB-commit vs. cache-DEL.

### Refinements

**6.1 — Precise Invalidation Ordering (Write-Invalidate-Then-Respond Protocol)**

```
CANONICAL ORDERING for ALL mutating operations:

1. BEGIN DB TRANSACTION
2. Perform mutation (INSERT/UPDATE)
3. Write AuditLog row (same session)
4. COMMIT DB TRANSACTION
5. Publish Domain Event (in-process, async)
6. DEL Redis cache keys (pipeline, synchronous before HTTP response)
7. Return HTTP response

NEVER: cache-DEL before DB commit (stale reads on rollback)
NEVER: cache-DEL after HTTP response (client reads stale cache before invalidation)
```

**6.2 — `document_count` Cache Entry**

Missing in original: If folders expose a `document_count` cache entry, it must be invalidated when documents are added/removed. This is a F5.1 gap:

```
Cache key: "ws:{ws_id}:folder:{folder_id}:doc_count"
TTL: 60s (shorter — counts are more stale-sensitive)
Invalidation: On document create/delete within this folder
Write: Cache-aside; DB-authoritative on cache miss
```

**6.3 — Stale Breadcrumb Window (Rename)**

The original design invalidates descendant breadcrumb caches AFTER the DB write. There is a window where:
1. DB is updated (rename committed).
2. Descendant breadcrumb caches still contain old name.
3. Reads between step 1 and step 2 get stale breadcrumbs.

This is an **acceptable enterprise trade-off** (Google Drive has this same eventual-consistency window for renamed folders in breadcrumbs). However, it must be formally documented:

> **Eventual Consistency Contract:** Breadcrumbs for descendants of a renamed folder may lag by up to 300s (cache TTL) or until next cache miss + reload. This is acceptable UX (breadcrumbs are supplementary navigation, not authoritative folder state).

**6.4 — Workspace-Level Cache Flush**

On workspace SUSPEND or SOFT-DELETE (existing Epic 3 behavior), all folder caches for that workspace must be flushed. Add to F5.1:

```
Workspace suspension handler must:
SCAN "ws:{ws_id}:folder*" → bulk DEL all matching keys
(Uses Redis SCAN in batches of 100, not KEYS which blocks Redis)
```

**Assessment: REFINEMENTS APPLIED — Per-batch commit ordering, doc_count cache key, workspace flush.**

### Audit Results

Every repository method must include `workspace_id` in the WHERE clause. Current state assessment:

| Method | Has ws_id Filter | Worker Has ws_id Filter | Assessment |
|---|---|---|---|
| `get_by_id_in_workspace` | ✅ Required | — | Correct |

| `exists_name_in_parent` | ✅ Required | — | Correct |
| `get_ancestors` | ✅ Path parse uses folder.path which is ws-scoped | — | Correct |
| `increment_document_count` | ✅ Required | — | Correct |
| `get_subtree_ids` | ✅ Must include `AND workspace_id=?` | — | **Refinement needed** |
| Worker: cascade DELETE | — | ✅ Must include `AND workspace_id=?` | **Verify explicitly** |
| Worker: cascade RESTORE | — | ✅ Must include `AND workspace_id=?` | **Verify explicitly** |

### Refinement 8.1 — Explicit CTE Tenant Guard

The recursive CTE in `get_subtree_ids` must include `workspace_id` in BOTH the anchor and recursive terms:

```sql
-- CORRECTED CTE with tenant guard in BOTH clauses:
WITH RECURSIVE subtree AS (
    -- Anchor: must be in this workspace
    SELECT id, parent_id FROM folders
    WHERE id = :folder_id AND workspace_id = :ws_id  ← EXPLICIT
    UNION ALL
    -- Recursive: must remain in same workspace
    SELECT f.id, f.parent_id FROM folders f
    JOIN subtree s ON f.parent_id = s.id
    WHERE f.workspace_id = :ws_id  ← EXPLICIT in recursive term
      AND f.is_deleted = FALSE
)
SELECT id FROM subtree LIMIT 50000;
```

> **Why this matters:** A corrupted `parent_id` value that accidentally references a folder in a different workspace would traverse into that workspace's folder tree without the tenant guard. The EXPLICIT guard at both levels prevents this.

### Refinement 8.2 — Worker Task Payload Integrity

Celery task payloads carry `workspace_id` as a string argument. The worker must re-validate this:

```
Worker startup check:
1. Load workspace from DB by workspace_id argument
2. Assert workspace exists and is not HARD_DELETED
3. All subsequent queries use this verified workspace_id — never the raw task argument
```

**Assessment: REFINEMENTS APPLIED — CTE both-clause tenant guard, worker payload re-validation.**

## Review Area 10: Enterprise Scalability

### Scenario Analysis

| Scenario | Architecture Behaviour | Assessment |
|---|---|---|
| **1M total folders in workspace** | `(workspace_id, parent_id)` composite index; all list queries are cursor-paginated; no full-table scans | ✅ |
| **100k sibling folders** | Cursor pagination with `(created_at, id)` cursor; single-page query touches ≤100 rows | ✅ |
| **50k descendant deletes** | Streaming BFS at 200 rows/batch × 250 iterations. Redis pipeline 100 keys/batch. Total: ~250 DB round-trips + ~250 Redis pipelines | ✅ (with Review Area 4 refinement) |
| **Depth 10 tree** | Materialized `depth` + `path`; no recursive SQL for reads. BFS worker iterates max 10 outer loops | ✅ |
| **High concurrency (1000 concurrent folder creates)** | No global lock; per-parent uniqueness via DB index; per-parent Redis rate limit 10 creates/sec | ✅ |
| **100 concurrent renames of same folder** | Optimistic lock; only 1 succeeds; 99 receive 409 with `current_version` | ✅ |
| **Multiple cascade workers in flight simultaneously** | Each worker is scoped to its own subtree root; no cross-subtree interference. Redis locks prevent duplicate task dispatch. | ✅ |

### Refinement 10.1 — Distributed Lock for Cascade Operations

Missing: Two separate HTTP requests could both trigger cascade delete for the same folder (race on version check if network retries). Add a Redis distributed lock:

```
Before enqueuing Celery cascade task:
SETNX "lock:ws:{ws_id}:folder:{folder_id}:cascade" "1" PX 300000
If SETNX returns 0: cascade already in progress → return 202 with existing task_id from AuditLog

Lock is released by Celery worker on completion (DEL).
```

**Assessment: REFINEMENT APPLIED — Distributed lock prevents duplicate cascade dispatch.**

## Review Area 11: Security

### Security Matrix

| Threat | Vector | Mitigation |
|---|---|---|
| **Folder enumeration** | Guess sequential or UUID folder IDs | UUIDs are V4 (random, not sequential). 122 bits of entropy. Brute force infeasible. |
| **ID guessing** | Attacker guesses folder UUID of another tenant | Repository always enforces `workspace_id = :ws_id`. Guessed UUID from another workspace returns 404. |
| **Parent spoofing** | Attacker supplies `parent_id` from another workspace | Step 3 validation: `parent.workspace_id == request.workspace_id`. Cross-workspace parent is rejected 422. |
| **Cross-workspace attack** | Attacker modifies `workspace_id` in request body | `workspace_id` is taken from the authenticated JWT token path parameter, never from the request body. |
| **Path traversal** | Attacker uses `../` in folder names to escape scope | Names are stored as raw strings; path traversal via folder name has no OS filesystem effect in this system. Slugs are sanitized. `path` column stores UUIDs, not names. |
| **Soft-delete abuse** | Attacker deletes another user's folders (lacking permission) | RBAC guard at Step 1; MEMBER can only delete; only ADMIN/OWNER can restore. |
| **Restore abuse** | Attacker restores a folder to gain access to its documents | Restore requires FOLDERS_RESTORE (ADMIN/OWNER). Documents in restored folders only visible to users with DOCUMENTS_READ. |
| **Version number forgery** | Attacker sets `version=1` to force overwrite | `UPDATE ... WHERE version=<client_version>` — if version was incremented by a legitimate write, client version is stale → 0 rows → 409. No security bypass possible. |
| **Celery task injection** | Attacker crafts a Celery message directly | Celery broker (Redis) must be network-isolated; not exposed to public internet. Workers re-validate `workspace_id` from DB (Review Area 8). |

### Refinement 11.1 — Rate Limiting on Folder Creation

Add rate limit to prevent a malicious MEMBER from creating 100,000 folders rapidly:

```
Per-user rate limit: 60 folder creates per minute per workspace
Per-workspace rate limit: 500 folder creates per minute
Implementation: Redis sliding window counter
  Key: "rate:ws:{ws_id}:user:{user_id}:folder_create"
  Key: "rate:ws:{ws_id}:folder_create"
  TTL: 60s sliding window
Exceed → 429 Too Many Requests
```

### Refinement 11.2 — Maximum Folders Per Workspace

Without a cap, a runaway script can create millions of folders:

```
Workspace-level folder cap: 100,000 folders (configurable via workspace settings)
Check on CREATE: SELECT COUNT(*) FROM folders WHERE workspace_id=? AND is_deleted=FALSE
If count >= cap: 429 { "error": "workspace_folder_limit_reached", "limit": 100000 }
```

**Assessment: REFINEMENTS APPLIED — Rate limiting and workspace folder cap added.**

### Refinement 13.1 — Restore After Workspace Suspension

```
RESTORE cannot proceed if workspace is SUSPENDED:
Step 1.5 (after RBAC guard, before loading folder):
  Load workspace → if status == SUSPENDED:
    → 409 { "error": "workspace_suspended", "message": "Cannot restore folders in a suspended workspace." }
```

### Refinement 13.2 — Rename of Soft-Deleted Folder

Currently not blocked: an ADMIN could theoretically call `PATCH /folders/{deleted_id}` with `include_deleted=true` knowledge. This must be explicitly blocked:

```
RENAME Step 2 addition:
Assert is_deleted == FALSE → else 404
(Already in spec but must be verified in implementation contract — raise priority)
```

### Refinement 13.3 — Restore When Workspace Suspended Mid-Cascade

```
Cascade restore worker startup:
  1. Re-load workspace from DB
  2. If workspace.status == SUSPENDED:
     → Abort task gracefully (not a failure)
     → Schedule retry in 60s (worker will check again)
     → Do NOT mark task as failed
     → Emit alert: "cascade_restore_paused_workspace_suspended"
```

## Remaining Risks

> [!NOTE]
> These are **known and accepted** residual risks with documented mitigations. They are not blockers.

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Breadcrumb cache stale window (rename) | Medium | Low | Defined as acceptable eventual consistency (max 300s) |
| Cascade worker slow on 50k deletion (100+ DB round-trips) | Low | Medium | BFS streaming; 10ms yield; monitor via Prometheus histogram |
| Redis unavailable during cache invalidation | Very Low | Low | TTL as safety net; DB is authoritative; self-healing |
| Workspace folder cap (100k) too low for enterprise | Low | Medium | Cap is configurable via workspace settings — adjustable without code change |
| Celery DLQ entries require ops intervention | Very Low | Medium | Alert + `POST /cascade-retry` manual recovery API |

## Enterprise Recommendations

1. **Implement BFS streaming delete first.** This is the highest-risk operation and must be validated with a load test at 10,000 folders before production launch.

2. **Instrument Prometheus metrics from day one.** `folder_cascade_deleted_duration_seconds` histogram will reveal actual cascade performance in production.

3. **The folder stats endpoint** (`/folders/{id}/stats`) should be treated as a lazy-computed, non-cached endpoint. Do not attempt to pre-aggregate these values.

4. **Rate limits and workspace folder caps** must be enforced at the Redis layer before any DB read on the hot create path.

5. **All future document-access repositories** must use the `LEFT JOIN` document visibility rule. Consider creating a shared `DocumentQueryBuilder.base_visible_query(session, workspace_id)` utility to enforce this centrally.

6. **Celery queue isolation:** The `high` priority `folders.cascade_soft_delete_subtree` queue must have dedicated worker processes to prevent starvation by lower-priority tasks.
