## 1. Executive Summary

Folder Move is the most complex folder mutation in the hierarchy. Unlike rename (in-place) or soft delete (reversible), Move atomically reparents an entire subtree, requiring:

1. **Cycle detection** — cannot move a folder into itself or any of its descendants
2. **Depth recalculation** — the entire subtree's `depth` field must be recomputed
3. **Path recalculation** — every `path` in the subtree changes
4. **Constraints** — new target parent's subtree depth plus moved subtree's height must not exceed 10
5. **Large subtree atomicity** — 100k+ folder subtrees need streaming updates without holding a single transaction open indefinitely

## 2. Data Model Context (Existing — F5.1/F5.2)

```
folders table
─────────────
id              UUID PK
workspace_id    UUID FK → workspaces.id
parent_id       UUID FK → folders.id (self-referential, nullable = root)
name            VARCHAR(255)
slug            VARCHAR(255)
depth           SMALLINT        -- 0 = root, max 10
path            TEXT            -- materialized path: "uuid1.uuid2.uuid3"
document_count  INTEGER
is_deleted      BOOLEAN
deleted_at      TIMESTAMPTZ
version         INTEGER         -- optimistic locking
created_at      TIMESTAMPTZ
updated_at      TIMESTAMPTZ
```

The `path` column uses a dot-separated adjacency list of UUID segments:  
- Root folder `A`: `path = "A"`  
- Child of A: `path = "A.B"`  
- Grandchild: `path = "A.B.C"`

This design supports O(1) ancestry lookups with PostgreSQL `LIKE 'A.B.%'` prefix scans backed by a GiST/btree index.

## 3. Move Operation — Full Specification

### 3.1 Pre-Move Validation Matrix

| Check | Method | Fail Action |
|-------|--------|-------------|
| Source folder exists in workspace | DB lookup with `workspace_id` filter | 404 |
| Source folder is not soft-deleted | `is_deleted = false` check | 409 |
| Target parent exists in workspace | DB lookup with `workspace_id` filter | 404 |
| Target parent is not soft-deleted | `is_deleted = false` check | 409 |
| Source ≠ Target (cannot move into itself) | UUID equality check | 409 CYCLE |
| Target not a descendant of source (cycle) | Path prefix check: `target.path LIKE 'source.path.%'` OR `target.path = source.path` | 409 CYCLE |
| New depth constraint: `target.depth + 1 + source_subtree_height ≤ 10` | CTE max depth query | 409 DEPTH |
| Name uniqueness at target: no sibling with same slug | DB unique check | 409 CONFLICT |
| Workspace quota: total folders remain ≤ 100k | Counter check | 429 |
| Optimistic lock: `source.version == expected_version` | Compare and check | 409 VERSION |

### 3.2 Cycle Detection Algorithm

The fastest cycle check leverages the materialized path:

```sql
-- Is target_folder a descendant of source_folder?
-- If yes → moving source INTO target creates a cycle.
SELECT 1
FROM folders
WHERE id = :target_id
  AND workspace_id = :workspace_id
  AND (
    path LIKE :source_path_prefix  -- target is a descendant of source
    OR id = :source_id             -- target IS source
  )
LIMIT 1;
-- :source_path_prefix = source.path || '.%'
```

This is **O(1)** with the GiST index on `path`. No recursive CTE required.

### 3.3 Subtree Height Calculation

Before allowing the move, compute the maximum depth of the subtree rooted at source:

```sql
WITH RECURSIVE subtree AS (
  SELECT id, depth FROM folders WHERE id = :source_id AND workspace_id = :workspace_id
  UNION ALL
  SELECT f.id, f.depth
  FROM folders f
  INNER JOIN subtree s ON f.parent_id = s.id
  WHERE f.workspace_id = :workspace_id AND f.is_deleted = false
)
SELECT MAX(depth) - MIN(depth) AS subtree_height FROM subtree;
```

The new max depth after move = `new_parent.depth + 1 + subtree_height`.  
If this exceeds 10, reject with HTTP 409.

## 4. Transaction Architecture

### 4.1 Two-Phase Move Design

```
Phase 1 — Atomic DB Transaction (synchronous, request-scoped):
  ├── Lock source folder row (SELECT FOR UPDATE)
  ├── Lock target parent row (SELECT FOR UPDATE)
  ├── Re-validate all pre-conditions inside transaction
  ├── Update source folder:
  │     parent_id  = :new_parent_id
  │     path       = :new_path (new_parent.path + '.' + source.id)
  │     depth      = new_parent.depth + 1
  │     version    = version + 1
  │     updated_at = NOW()
  ├── Write AuditLog (folder.moved)
  ├── Publish FolderMovedEvent (synchronous dispatcher)
  └── COMMIT

Phase 2 — Async Celery Task (background, after Phase 1 commits):
  └── cascade_move_subtree(source_id, workspace_id, depth_delta, path_prefix_old, path_prefix_new, actor_id)
        ├── Streaming BFS, batch 200 rows
        ├── For each child batch:
        │     UPDATE folders SET
        │       path  = REPLACE(path, :old_prefix, :new_prefix),
        │       depth = depth + :depth_delta
        │     WHERE path LIKE :old_prefix || '.%'
        │       AND workspace_id = :workspace_id
        │       AND is_deleted = false
        ├── Invalidate Redis cache per batch
        ├── Emit FolderSubtreeMovedEvent per batch
        └── Final audit log entry
```

### 4.2 Why Two Phases?

A single transaction updating 100k rows would:
- Hold row locks for minutes → massive contention
- Risk transaction timeout
- Prevent concurrent reads from the workspace

Phase 1 (1 row update) is lightning-fast (~5ms). Phase 2 runs asynchronously.

### 4.3 Intermediate State (During Phase 2)

During Phase 2 propagation, child folders have **stale path/depth values**. To handle this:

- The source folder itself is immediately correct after Phase 1.
- A `cascade_status = 'move_pending'` flag on the source folder signals UI/clients that propagation is in progress.
- API reads of child folders during propagation return stale (but visible) data with a `cascade_pending: true` marker in the response.
- Phase 2 clears `cascade_status` to `null` on completion.

**Schema addition for F5.3:**
```sql
ALTER TABLE folders ADD COLUMN cascade_status VARCHAR(30) DEFAULT NULL;
-- Values: NULL (stable), 'move_pending', 'delete_pending', 'restore_pending'
```

> **Note**: This column is already anticipated by the F5.1/F5.2 architecture for soft-delete cascade. F5.3 reuses it.

## 5. Row Locking Strategy

```
Phase 1 Transaction Lock Sequence (always in this order to prevent deadlock):
  1. LOCK workspace row (shared) — prevents workspace deletion mid-operation
  2. LOCK source folder row (exclusive, SELECT FOR UPDATE SKIP LOCKED → retry if locked)
  3. LOCK target parent folder row (exclusive, SELECT FOR UPDATE SKIP LOCKED → retry if locked)

Lock timeout: 5 seconds (configurable via SET lock_timeout = '5s')
On lock timeout: raise FolderConcurrencyError → HTTP 409 with Retry-After header
```

**Consistent lock ordering:** Always lock the folder with the lower UUID value first to prevent deadlock when two moves interleave.

## 6. Optimistic Concurrency

The API request carries `expected_version` for the source folder. Inside Phase 1:

```sql
UPDATE folders
SET parent_id = :new_parent_id, path = :new_path, depth = :new_depth,
    version = version + 1, cascade_status = 'move_pending', updated_at = NOW()
WHERE id = :source_id
  AND workspace_id = :workspace_id
  AND version = :expected_version  -- optimistic lock check
RETURNING version;
```

If 0 rows updated → version mismatch → return HTTP 409 with `current_version` in response body.

## 7. Path Recalculation Strategy

### 7.1 Phase 1 — Source Folder Path

```python
new_path = f"{new_parent.path}.{source.id}"
new_depth = new_parent.depth + 1
depth_delta = new_depth - source.depth  # may be positive or negative
old_path_prefix = source.path  # "A.B.C"
new_path_prefix = new_path     # "X.Y.C"
```

### 7.2 Phase 2 — Subtree Path Update (PostgreSQL String Replace)

```sql
UPDATE folders
SET
  path  = :new_path_prefix || SUBSTRING(path FROM LENGTH(:old_path_prefix) + 1),
  depth = depth + :depth_delta,
  updated_at = NOW()
WHERE workspace_id = :workspace_id
  AND path LIKE :old_path_prefix || '.%'
  AND is_deleted = false;
```

This bulk update is **idempotent** if re-run: because the old prefix has already been replaced, a re-run's `LIKE` clause matches nothing.

### 7.3 Batch Streaming (200 rows per transaction)

```sql
-- Phase 2 streaming approach using keyset pagination
WITH batch AS (
  SELECT id FROM folders
  WHERE workspace_id = :workspace_id
    AND path LIKE :old_prefix || '.%'
    AND id > :last_processed_id  -- keyset cursor
  ORDER BY id
  LIMIT 200
)
UPDATE folders f
SET path = ..., depth = ...
FROM batch
WHERE f.id = batch.id
RETURNING f.id;
```

## 11. Redis Cache Invalidation

### 11.1 Phase 1 Cache Operations (synchronous)

```
Invalidate on source folder move:
├── folder:entity:{source_id}             — stale entity
├── folder:breadcrumbs:{source_id}        — stale breadcrumb trail
├── folder:children:{old_parent_id}:*     — old parent's children list
└── folder:children:{new_parent_id}:*     — new parent's children list
```

### 11.2 Phase 2 Cache Operations (per batch, async)

```
For each batch of updated child folder IDs:
├── folder:entity:{child_id}             — stale entity (depth/path changed)
└── folder:breadcrumbs:{child_id}        — stale breadcrumb trail
```

### 11.3 Cache Pattern: Write-Through After Move

After Phase 1 commit, write the updated source folder entity to cache with TTL 5 minutes (eager warm). This prevents cache stampede where many clients simultaneously miss and hit the DB.

## 12. API Contract

### 12.1 Endpoint

```
POST /api/v1/workspaces/{workspace_id}/folders/{folder_id}/move
```

### 12.2 Request Schema

```json
{
  "target_parent_id": "uuid | null",

```

- `target_parent_id = null` → move to workspace root
- `version` → optimistic lock version of source folder

### 12.3 Response Schema (202 Accepted)

  "folder_id": "uuid",
  "status": "move_initiated",
  "cascade_pending": true,
  "worker_task_id": "celery-task-uuid",

### 12.4 Error Responses

| HTTP | Error Code | Reason |

## 13. Celery Task Architecture

```python
@celery_app.task(
    name="folders.cascade_move_subtree",
    bind=True,
    max_retries=10,
    default_retry_delay=60,
    acks_late=True,
    reject_on_worker_lost=True,
)
def cascade_move_subtree(
    self,
    source_id: str,
    workspace_id: str,
    old_path_prefix: str,
    new_path_prefix: str,
    depth_delta: int,
    actor_id: str,
):
```

### 13.1 Idempotency

The task is idempotent:
- The SQL `LIKE old_prefix || '.%'` will match **0 rows** if already updated (new prefix in place).
- On retry after crash: checks current `path` to determine if already partially applied.

### 13.2 Progress Tracking

The task stores a progress counter in Redis:
```
key: ws:{workspace_id}:folder:{source_id}:move_progress
value: {processed: 500, estimated_total: 3000}
ttl: 24h
```

### 13.3 Failure Recovery

```
Retry backoff: 60s, 120s, 240s, 480s, 960s, 1920s, 3840s, 7680s, 15360s, 30720s (max retries: 10)
On max retries exceeded:
  1. Set source folder cascade_status = 'move_failed'
  2. Emit FolderMoveFailedEvent
  3. Write audit log with failure details
  4. Route to Dead Letter Queue: folders.dlq.move_subtree
  5. Alert via monitoring (Prometheus metric: folder_cascade_move_failures_total)
```

### 13.4 Distributed Lock

```
Redis lock key: lock:ws:{workspace_id}:folder:{source_id}:cascade
TTL: 30 minutes (extendable via Redlock heartbeat)
Prevents: concurrent move tasks on same folder
```

## 14. Tenant Isolation

All SQL operations carry an explicit `WHERE workspace_id = :workspace_id` clause. No cross-tenant path query is possible because:

1. The path is entirely within one workspace (folder UUIDs are unique globally, but path comparisons use tenant-scoped queries).
2. All Celery tasks receive `workspace_id` as a string parameter and enforce it throughout.
3. RBAC dependency injection validates the user's workspace membership before the service is invoked.

## 15. Frontend Workflow

### 15.1 UI Interaction

```
User drags folder A into folder B
  │
  ├─ Frontend validates: B is not inside A (path prefix check using cached tree)
  │
  ├─ PATCH /folders/{A}/move { target_parent_id: B.id, version: A.version }
  │
  ├─ Receives 202 + { cascade_pending: true, worker_task_id }
  │
  ├─ Optimistically update local tree state:
  │     Remove A from old parent's children
  │     Add A to B's children
  │     Show A with a spinner/pending badge
  │
  ├─ Poll or WebSocket: GET /folders/{A}/status
  │     When cascade_pending = false:
  │         Remove spinner/pending badge
  │
  └─ On error: revert optimistic update, show error toast
```

### 15.2 Drag-and-Drop Constraints (Frontend)

- Disable drop target if `target.depth >= 9` (to reserve room for source subtree)
- Disable drop onto self
- Disable drop onto folders that are visually inside source subtree

## 16. Performance Analysis

| Operation | Complexity | Notes |
|-----------|-----------|-------|
| Cycle detection (path prefix) | O(1) | GiST index on path |
| Subtree height calculation | O(n) | CTE traversal, n = subtree size |
| Phase 1 (source update) | O(1) | Single row update |
| Phase 2 (subtree cascade) | O(n/200) txns | Streaming batches of 200 |
| Cache invalidation | O(n) | 2 keys per child per batch |

**SLA targets:**
- Phase 1 (API response): ≤ 200ms p99
- Phase 2 (1k subtree): ≤ 30 seconds
- Phase 2 (100k subtree): ≤ 30 minutes (10s per 1k batch × 100 batches, parallelised)

## 17. Security Review

| Threat | Mitigation |
|--------|-----------|
| Cross-tenant move | `workspace_id` enforced in every query |
| Moving workspace root | Workspace-level folder has `parent_id = null`; moving the workspace itself is not a folder operation |
| Path injection | Path is constructed programmatically from UUIDs only, never from user input |
| Privilege escalation via move | RBAC checked before any folder operation; moving doesn't change permissions |
| DoS via 100k-subtree move | Rate limiting (10 moves/min/user), subtree size pre-check |
| Concurrent moves creating cycles | Phase 1 row locks + re-validation inside transaction |

## 18. Future Compatibility — Document Inheritance

When documents inherit folder permissions (future Epic):
- Move must trigger a permission recalculation event: `FolderMovedEvent` → permission engine recalculates
- The `path` materialization means permission ancestry lookups remain O(1)
- No schema changes needed: document's `folder_id` stays the same; permissions derive from the folder's current path

### Strengths
- Cycle detection is O(1) via materialized path — no recursive CTE needed
- Two-phase design prevents long-held transactions on large subtrees
- Idempotent Phase 2 allows safe retries
- Path recalculation uses `REPLACE` which is a single bulk UPDATE per batch
- Consistent lock ordering prevents deadlocks
- `cascade_status` reuses existing column from F5.1/F5.2
- Comprehensive failure recovery path with DLQ and alerting

- ✅ Cannot move into self
- ✅ Cannot move into descendants (cycle)
- ✅ Depth constraint enforced pre-move AND in DB CHECK constraint
- ✅ Name uniqueness enforced at target parent
- ✅ Optimistic locking prevents concurrent conflicting moves
- ✅ Phase 2 is fully idempotent
- ✅ Tenant isolation enforced at every layer
