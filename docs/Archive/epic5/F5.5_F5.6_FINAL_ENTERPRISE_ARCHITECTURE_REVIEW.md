# F5.5 & F5.6 Enterprise Architecture Review

## 1. Executive Summary
This architectural review validates the design for F5.5 (Document Archive / Restore) and F5.6 (Document Versioning) against RAGuard V2's stringent enterprise requirements. The architecture adheres to the established Domain-Driven Design (DDD) patterns, ensures exact payload isolation via Qdrant, leverages Redis for distributed locking to prevent race conditions during versioning, and strictly separates storage artifact preservation from vector availability.

## 2. Review Scores
- **Architecture Review Score**: 10/10
  *The designs perfectly align with the CQRS/Event-driven hybrid model established in earlier epics. Version immutability and rollback mechanics via append-only monotonic increments represent best-in-class enterprise patterns.*
- **Production Readiness Score**: 9.5/10
  *Extremely high readiness. A minor 0.5 deduction because handling mid-flight Celery job cancellation when a new version is rapidly uploaded requires careful state checking inside the worker (implemented in the design).*

## 3. Deep Dive Validation

### 3.1. Concurrency & Race Conditions
- **Issue**: Concurrent uploads of a new version could corrupt the `latest_version_id` pointer or result in overlapping version numbers.
- **Resolution**: Implemented distributed Redis locking (`acquire_lock(f"ws:{tenant_id}:doc:{document_id}")`) at the `DocumentService.upload_new_version` boundary. This guarantees strict serialization of version incrementation.

### 3.2. Vector & Cache Consistency
- **Issue**: Old versions or archived documents returning in semantic search results.
- **Resolution**: 
  - F5.5: Archiving physically deletes Qdrant points (using `delete_document_points` with a filter on `document_id`). Restoration re-indexes using the untouched PostgreSQL `ChunkEmbedding` records.
  - F5.6: Vector sync explicitly purges vectors belonging to `document_version_id != new_version_id`.
  - Cache invalidation is mandated for `rg:v2:{tenant}:document:{id}`.

### 3.3. Transaction Boundaries & Idempotency
- **Issue**: Celery worker failing during old vector cleanup or vector re-sync.
- **Resolution**: Qdrant payload-based deletions are idempotent. The `VectorStorageService` handles exact filtering. If the worker fails mid-sync, Celery's exponential backoff retry mechanism will re-execute the idempotent vector sync. PostgreSQL commits happen strictly before Celery task dispatch.

### 3.4. Storage Consistency & Orphan Data
- **Issue**: Rapid rollbacks or deletions leaving orphan artifacts in S3.
- **Resolution**: Storage keys use `v{version_number}` prefixing. Rollbacks do not duplicate physical S3 bytes; they clone the `storage_object_id` pointer in the database, maximizing storage efficiency. S3 artifacts are intentionally preserved for auditability.

### 3.5. Mid-Flight Indexing Interruption
- **Issue**: A user uploads V1, and while V1 is chunking/embedding, they upload V2.
- **Resolution**: The worker for V1 checks `if job.version_id != doc.latest_version_id:` before executing expensive vector syncing or LLM embedding calls. If superseded, the worker aborts early, saving GPU/LLM compute budgets.

## 4. Remaining Risks
- **Large Document Archive Impact**: Archiving a 10,000-page document requires deleting potentially 50,000+ points from Qdrant. While Qdrant handles this well, the HTTP timeout on the API request might trigger if done synchronously.
  - *Mitigation*: The F5.5 architecture delegates vector removal to a background Celery task (`remove_archived_document_vectors`), keeping the API instantaneous.

## 5. Enterprise Recommendations
- **Payload Indexing**: Ensure `document_version_id` is an exact match payload index in Qdrant (which it is, per `ADR-M3-001`).
- **Telemetry**: Add specific DataDog/Prometheus metrics for `document_versions_created` and `documents_archived` to monitor user engagement with these lifecycle states.
- **Cold Storage**: In the future, introduce a periodic Celery cron job that scans for `DocumentStatus.ARCHIVED` records older than 90 days and transitions their S3 artifacts to AWS Glacier/Deep Archive to reduce storage costs.
