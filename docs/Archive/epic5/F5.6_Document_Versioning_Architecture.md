# F5.6 — Document Versioning Architecture

## 1. Overview
The Document Versioning feature provides immutable, linearly incremented content revisions for documents within a tenant's knowledge base. It guarantees that updating a document does not destroy the history of its previous state, while intelligently cleaning up expensive vector index space in Qdrant to maintain high retrieval accuracy and lower infrastructure costs.

## 2. Database & Entity Architecture

The current implementation already defines `Document` and `DocumentVersion` entities.

### 2.1. Model Enhancements
- `Document` maintains a pointer to `latest_version_id`.
- `DocumentVersion` maintains `version_number` (monotonic integer).
- When a new file is uploaded to replace an existing document, we create a new `DocumentVersion`.
- **Storage Lifecycle tracking**: Add an `is_active_vector` boolean to `DocumentVersion` to explicitly denote which version's vectors currently reside in Qdrant.

## 3. Service & Repository Layer

### 3.1. Document Service: Uploading a New Version
- `upload_new_version(document_id, stream, tenant_id, user_id)`:
  1. Validate document exists and is not locked/archived.
  2. Run validation pipeline (size, virus scan, extension).
  3. Lock the document using a distributed Redis lock (`lock:ws:{tenant_id}:doc:{document_id}`) to prevent concurrent version uploads from causing race conditions.
  4. Fetch the highest `version_number` and increment by 1.
  5. Store the new physical artifact with `get_versioned_path(..., version_number=new)`.
  6. Insert new `DocumentVersion` and update `Document.latest_version_id`.
  7. Insert a new `ProcessingJob` linked to the *new* `version_id`.
  8. Emit `DOCUMENT_VERSION_CREATED` event.
  9. Enqueue `process_document_job`.

### 3.2. Background Indexing & Vector Cleanup
The ingestion pipeline handles the new version exactly like a new document until the final stage (Vector Sync).
- **Old Vector Cleanup**: When the new version's vectors are successfully upserted into Qdrant, we MUST remove the old version's vectors.
- In `VectorStorageService.sync_document_vectors`, add logic:
  - After successfully syncing vectors for `version_id`, query for any older `DocumentVersion` IDs for this document that are still marked as synced.
  - Delete their points from Qdrant using a payload filter on `document_version_id != new_version_id`.
  - Update their `VectorIndexMetadata` to reflect they are no longer in Qdrant.
- This prevents duplicate semantic hits across versions.

## 4. Rollback Functionality
- `rollback_to_version(document_id, target_version_id, tenant_id)`:
  1. Acquire distributed lock on the document.
  2. Validate target version belongs to document.
  3. Do NOT delete the current version; instead, create a NEW version (e.g., `v3`) that clones the `storage_object_id`, `content_hash`, and metadata of the `target_version_id` (e.g., `v1`).
  4. This ensures monotonic version history (1 -> 2 -> 3(reverted to 1)).
  5. Enqueue the new version (v3) for vector sync. The old vectors (from v2) will be cleaned up automatically during v3's sync phase.
  6. Emit `DOCUMENT_ROLLED_BACK`.

## 5. Metadata Inheritance
- When uploading a new version, any user-applied key-value metadata tags on the Document level (F5.7 feature) remain unaffected.
- Auto-extracted metadata (word count, page count, language) on the Document aggregate will be updated upon completion of the new version's processing job.

## 6. Storage Object Versioning
- S3 objects are written to canonical paths: `documents/{tenant_id}/{document_id}/v{version_number}/original/{filename}`.
- Older physical objects are **retained** in S3, providing strict audit trails. If compliance dictates cleanup, an asynchronous S3 lifecycle policy or a separate retention worker can prune old S3 objects, but the database `DocumentVersion` record remains intact (with a potential `storage_purged=True` flag in the future).

## 7. Event Architecture
- **`DOCUMENT_VERSION_CREATED`**: Fired upon initialization of the new version upload.
- **`DOCUMENT_ROLLED_BACK`**: Fired when a rollback is triggered.
- **`OLD_VECTORS_CLEANED_UP`**: Fired by the vector storage service after purging old version vectors.

## 8. Concurrency & Idempotency
- **Concurrent Uploads**: Prevented via Redis distributed lock (`acquire_lock(f"ws:{tenant_id}:doc:{document_id}")`).
- **Upload during Indexing**: The lock also prevents initiating a new version upload while a processing job is actively writing to the database, though the Celery worker operates asynchronously. The Celery worker updates `latest_version_id` metrics. If a new version is uploaded while the old one is indexing, the old job should ideally be aborted. We can implement a cancellation check in the worker by verifying `job.version_id == doc.latest_version_id`. If they differ, the worker can safely abort (skip Qdrant sync) to save compute.

## 9. API Architecture
- `POST /v1/documents/{document_id}/versions` (Upload new version)
- `POST /v1/documents/{document_id}/versions/{version_id}/restore` (Rollback)
- `GET /v1/documents/{document_id}/versions` (List versions)
- `GET /v1/documents/{document_id}/versions/{version_id}/compare` (Future: Diffing)

## 10. Frontend Architecture
- A "Version History" panel in the Document Details view.
- Upload dropzone supports "Upload New Version" button when viewing a specific document.
- Rollback button available next to older versions, prompting a confirmation dialog.
- Status indicators for older versions show "Archived/Superseded".

## 11. Security Model & RBAC Matrix
- **Security Model**: Strict `tenant_id` verification on all version queries and operations.
- **RBAC Matrix**:
  - `OWNER`, `ADMIN`: Can upload new versions and rollback.
  - `MEMBER`, `ENGINEER`, `ANALYST`: Can upload and rollback if they possess `DOCUMENT_UPDATE` permission.
  - `VIEWER`, `EXTERNAL`: Denied from modifying versions; can only view active versions.

## 12. Performance & Scalability
- **Performance**: Uploading a version is instantaneous on the API side as chunking/embedding is delegated to Celery.
- **Scalability**: Vector DB size is strictly controlled by purging old version vectors, reducing RAM usage and ensuring search latency remains low.

## 13. Failure Recovery & Multi-Tenancy
- **Failure Recovery**: 
  - If embedding fails, Celery retries. 
  - If a rollback fails mid-flight, the old version remains intact as the active version.
- **Multi-Tenancy**: All DB updates, S3 keys, and Qdrant operations include `tenant_id` scoping to prevent cross-tenant data corruption.

## 14. Observability & Monitoring
- **Observability**: Structured logs injected with `tenant_id`, `document_id`, and `version_id`. Audit logs record the timestamp and `user_id` performing the version upload or rollback.
- **Monitoring**: Datadog metrics tracking `document.version_created.count` and `document.rollback.count`. Monitor Qdrant point count drops after old version vector cleanup.

## 15. Future Extensibility
- **Compare Versions (Diffing)**: Future capability to run text diffs on `normalized_text_path` of two different versions.
