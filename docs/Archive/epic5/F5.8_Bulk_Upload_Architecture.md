# F5.8 Bulk Upload Architecture (Async Batch Jobs)

## 1. Overview
F5.8 establishes a robust, highly concurrent, asynchronous bulk upload pipeline. It allows users to drag-and-drop or select hundreds of documents simultaneously. The system relies heavily on Celery for orchestration, Object Storage (S3) for blob management, and Redis for rate-limiting, progress tracking, and batch coordination.

## 2. Core Concepts

### 2.1 Batch Job Definition
A "Bulk Upload" is abstracted as a single `BulkBatch` entity which logically groups multiple `ProcessingJob` records. 
- A `BulkBatch` possesses a `status` (PENDING, PROCESSING, COMPLETED, PARTIAL_FAILURE, FAILED).
- It provides a unified progress percentage (`completed_jobs / total_jobs`).

### 2.2 Upload Strategy: Direct-to-S3 (Presigned URLs)
To avoid bottlenecking the API web servers and exhausting memory/bandwidth, files will **NOT** be streamed through the FastAPI application.
1. Client requests a batch of `Presigned POST URLs` from the API.
2. **Security Constraint**: The API generates URLs with strict `content-length-range` boundaries and short-lived expirations (max 15 minutes) to prevent Denial of Wallet attacks against the storage bucket.
3. Client uploads files directly to the S3 bucket using the presigned URLs.
4. Client notifies the API that uploads are complete, triggering the ingestion pipeline.

## 3. Pipeline Architecture

The pipeline leverages Celery tasks and RabbitMQ/Redis message brokering.

### 3.1 Flow Chart
1. **API Initiation**: API creates `BulkBatch`, `Document`, and `DocumentVersion` records (Status: `UPLOADED`).
2. **Dispatch**: API queues a `dispatch_bulk_upload_job` Celery task.
3. **Validation & AV Scan**: Worker retrieves blobs from S3, verifies signatures/magic bytes, and performs ClamAV (or equivalent) scanning.
4. **Quarantine**: If a virus is detected, the `Document` is marked `QUARANTINED`, moved to a quarantine S3 bucket, and processing halts for that file.
5. **Extraction & Chunking**: Valid documents proceed to OCR/Extraction, yielding text chunks.
6. **Embedding & Vector Ingestion**: Chunks are embedded and stored in Qdrant.
7. **Finalization**: `Document` status transitions to `PROCESSED`. `ProcessingJob` marked `COMPLETED`.

## 4. Resilience & Error Handling

### 4.1 Retry Strategy & Idempotency
- Celery tasks utilize `acks_late=True` and exponential backoff.
- Database operations are strictly idempotent, relying on UPSERT logic and state-machine preconditions (e.g., `WHERE status = 'PROCESSING'`).

### 4.2 Partial Failures
If Document A fails extraction, Document A is marked `FAILED`, but Documents B-Z in the same `BulkBatch` continue processing independently. The `BulkBatch` will conclude with a `PARTIAL_FAILURE` status.

### 4.3 Dead Letter Queue (DLQ)
Tasks that exceed `max_retries` (default: 3) are routed to a Dead Letter Queue (DLQ).
**DLQ Management**: The administrative backend will provide a dedicated API (`GET /api/v1/admin/dlq` and `POST /api/v1/admin/dlq/{task_id}/replay`) to list stalled messages and manually push them back to the active queue for reprocessing.

## 5. Throttling, Quotas & Prioritization

### 5.1 Rate Limiting & Quotas
- **Workspace Quotas**: Evaluated immediately at the presigned-URL generation step. If the batch exceeds the workspace's storage or document count limits, the request is rejected with `HTTP 402 Payment Required` or `HTTP 403 Forbidden`.
- **Redis Token Bucket**: API limits the number of concurrent batch uploads per tenant to prevent noisy-neighbor issues.

### 5.2 Queue Prioritization
- Standard uploads go to the `ingestion_default` queue.
- Enterprise tenants or high-priority synchronous single-file uploads can be routed to an `ingestion_high_priority` queue.

## 6. Observability & User Feedback

### 6.1 Progress Tracking
- WebSockets or Server-Sent Events (SSE) will stream real-time progress to the frontend.
- **Aggregation Strategy**: To prevent PostgreSQL lock contention and deadlocks when tens of thousands of tasks finish concurrently, progress is tracked using high-throughput atomic Redis `INCR batch_progress:{id}` counters. A background reconciler periodically flushes this aggregated state to the PostgreSQL `BulkBatch` entity.

### 6.2 Cancellation Support
- Users can cancel a `BulkBatch`. This marks pending jobs as `CANCELLED`.
- Running Celery tasks will check a Redis flag (`bulk_cancel:{batch_id}`) at boundary steps (e.g., before starting OCR) to abort execution gracefully and avoid wasted compute.

### 6.3 Audit Logging
- Events such as `EVENT_BULK_BATCH_STARTED`, `EVENT_BULK_BATCH_COMPLETED`, and `EVENT_DOCUMENT_QUARANTINED` are emitted for compliance tracking.
