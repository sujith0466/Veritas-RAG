# F5.7 Metadata Management Architecture (Key-Value Tagging)

## 1. Overview
F5.7 introduces flexible, type-safe, key-value metadata tagging for Documents. This allows enterprise tenants to classify, search, and filter documents based on domain-specific attributes (e.g., `department: HR`, `contract_value: 50000`, `is_active: true`) while adhering to workspace isolation and strict RBAC validation.

## 2. Core Entities & Database Design

### 2.1 Entity Extension
Rather than introducing an anti-pattern Entity-Attribute-Value (EAV) table, we will leverage PostgreSQL's native `JSONB` capabilities directly on the `Document` and `DocumentVersion` entities.

We will introduce a `user_metadata` column to the `Document` model:
```python
user_metadata: Mapped[dict[str, Any]] = mapped_column(
    JSONB(none_as_null=True), default=dict, nullable=False
)
```
*(Note: `metadata_json` already exists on `DocumentVersion` for extraction/system metadata. `user_metadata` will strictly hold user-defined tags).*

### 2.2 PostgreSQL Indexing Strategy
To support highly performant metadata filtering (e.g., `WHERE user_metadata @> '{"department": "HR"}'`), we will employ a **GIN (Generalized Inverted Index)** on the `user_metadata` column.
- Index type: `GIN (user_metadata jsonb_path_ops)`
- Benefits: Optimized for `@>`, `?`, `?&`, and `?|` containment operators, supporting highly selective queries on specific keys and values.

## 3. Metadata Specification

### 3.1 Typed Metadata
Metadata values will support primitive JSON types:
- `String`
- `Number` (Integer, Float)
- `Boolean`
- `Date` (represented as ISO-8601 Strings, validated at the API layer)

### 3.2 Reserved System Keys
Keys starting with double-underscores (e.g., `__raguard_source`, `__ingestion_id`) are reserved for system use and rejected by the API layer during validation.

### 3.3 Validation Rules
- **Key Format**: Regex `^[a-zA-Z0-9_-]+$` (No spaces or special characters other than hyphens and underscores).
- **Max Keys**: 100 per document to prevent JSONB bloat.
- **Max Key Length**: 64 characters.
- **Max Value Length**: 512 characters (for strings).
- **Duplicate Prevention**: Keys are unique per document (Standard JSON object behavior). Updating a key overwrites the existing value.

## 4. API & Service Layer (CQRS)

### 4.1 Endpoints
- `PUT /api/v1/workspaces/{workspace_id}/documents/{document_id}/metadata` (Full overwrite)
- `PATCH /api/v1/workspaces/{workspace_id}/documents/{document_id}/metadata` (Partial update/merge)
- `DELETE /api/v1/workspaces/{workspace_id}/documents/{document_id}/metadata/{key}` (Remove specific key)

**Concurrency Control**: All `PATCH` and partial updates will utilize row-level database locking (`SELECT ... FOR UPDATE`) nested within the Redis `acquire_lock` mechanism to prevent lost-update race conditions during concurrent JSONB mutations.

### 4.2 Search & Filtering
The `GET /api/v1/workspaces/{workspace_id}/documents` endpoint will be extended with query parameters:
- `?meta.department=HR`
- `?meta.contract_value[gt]=10000`

### 4.3 Redis Cache Strategy
Document queries are cached using the existing L1/L2 Redis caching strategy. Metadata updates will emit a cache invalidation event for the specific `ws:{workspace_id}:doc:{document_id}` cache key, forcing a DB read on the next request.

## 5. Security & RBAC Integration
- Action: `document:update` required to modify metadata.
- Action: `document:read` required to view metadata.
- Multi-tenancy: Validated via the URL `workspace_id` parameter matching the active tenant context.

## 6. Audit Logging & Event Publishing
Every metadata mutation will generate an event and audit log via the existing `DocumentEventLog` pipeline.
- `EVENT_DOCUMENT_METADATA_UPDATED`: Includes the key-value diff.

## 7. Vector Synchronization (Qdrant)
Because metadata acts as a retrieval filter, the PostgreSQL database acts as the source-of-truth, and Qdrant acts as a read-model projection.
Whenever a document's `user_metadata` is updated, an asynchronous Celery task (`sync_document_metadata_to_vectors_job`) is immediately queued. This task will `upsert` the new metadata payload into Qdrant for all vector chunks associated with the document, ensuring search consistency.
