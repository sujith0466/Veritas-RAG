## 1. Architecture Overview & Cross-Feature Coherence

The three features form a **linear pipeline** with strict sequential dependencies:

```
F5.8 BulkBatch Upload
         │
         ▼
F6.1 ProcessingJob Created & Enqueued
         │
         ▼
F6.2 Extraction Worker (VALIDATING → EXTRACTING → OCR → PROCESSED)
         │  Artifact: text.txt + extraction.json → S3
         ▼
F6.3 Chunking Worker (CHUNKING → CHUNKED)
         │  Artifact: DocumentChunk records → PostgreSQL
         ▼
Epic 7: Embedding Worker (EMBEDDING → EMBEDDED → VECTOR_SYNC → READY)
```

**Pipeline Coupling:** Each stage is decoupled via:
1. **Celery task queues** (F6.1 queue topology)
2. **PostgreSQL ProcessingJobStep** records as durable checkpoints
3. **S3 artifact keys** as stage hand-off contracts
4. **EventDispatcher** for in-process signaling

This design is correct and resilient. Each stage can fail and resume independently.

## 3. Race Condition Analysis

### RC-001: Duplicate Job Processing (CRITICAL — MITIGATED)
**Scenario:** Celery `acks_late=True` means if a worker crashes after processing but before ack, the task is re-delivered. Two workers could process the same job concurrently on different pods.

**Mitigation:**
1. **Distributed Redis lock** (`SET NX PX 600000`) — only one worker can hold the lock.
2. **Idempotency key** — second worker finds key in Redis and skips.
3. **Job status check** — worker checks `job.status NOT IN {COMPLETED, DLQ, CANCELLED}` before starting.

**Verdict:** ✅ Triple-protected. No race condition.

### RC-002: Simultaneous Cancellation & Processing (HIGH — MITIGATED)
**Scenario:** Admin cancels job at exact moment worker transitions from CLAIMED to RUNNING.

**Mitigation:**
- Worker polls `cancel_signal` Redis key **at step boundaries** (not mid-step).
- Cancellation transitions through `CANCELLATION_REQUESTED` state, never direct to `CANCELLED`.
- Worker always completes the current atomic DB write before checking cancel flag.
- DB transaction ensures consistent state.

**Verdict:** ✅ Properly bounded. No data corruption possible.

### RC-003: Stale Lock After Worker OOM Kill (HIGH — MITIGATED)
**Scenario:** Worker is OOM killed while holding Redis lock. Lock TTL = 600s. New jobs blocked for up to 10 minutes.

**Mitigation:**
- Worker heartbeat every 30s extends lock TTL → 600s.
- Separate `StaleJobMonitor` service (scheduled every 5min) detects workers with expired heartbeats (`raguard:worker:heartbeat:{worker_id}` TTL expired) and force-releases their locks.
- `task_reject_on_worker_lost=True` returns task to queue.

**Verdict:** ✅ Maximum lock orphan window = 5 minutes. Acceptable for enterprise SLA.

### RC-004: Chunk Sequential Linking Race (MEDIUM — MITIGATED)
**Scenario:** Two concurrent retry attempts of the same chunking job create duplicate chunk records with conflicting `previous_chunk_id` / `next_chunk_id` pointers.

**Mitigation:**
- Idempotency key at chunk step level prevents concurrent chunk processing.
- Unique constraint `(document_version_id, content_hash)` prevents duplicate chunk creation.
- Chunking job lock scoped to `raguard:{tenant_id}:job:{job_id}:lock:chunking`.

**Verdict:** ✅ Safe.

### RC-005: Priority Queue Starvation (MEDIUM — MITIGATED)
**Scenario:** Continuous stream of CRITICAL priority jobs starves LOW priority jobs indefinitely.

**Mitigation:**
- LRU escalation: LOW priority jobs older than 4 hours are promoted to NORMAL priority.
- Escalation implemented via Celery Beat scheduled task that scans `processing_jobs WHERE priority=0 AND scheduled_at < NOW() - INTERVAL '4 hours'`.
- Separate worker pools per priority queue — LOW queue workers cannot be fully preempted.

**Verdict:** ✅ Anti-starvation policy defined.

## 4. Deadlock Analysis

### DL-001: PostgreSQL Session Deadlock on Job Update (HIGH — MITIGATED)
**Scenario:** Two workers updating `processing_jobs` and `processing_job_steps` for overlapping jobs, causing lock contention.

**Mitigation:**
- `SELECT ... FOR UPDATE SKIP LOCKED` pattern when claiming jobs.
- Consistent lock ordering: always lock `processing_jobs` before `processing_job_steps`.
- Short DB transactions (< 500ms) with AsyncSession.

**Verdict:** ✅ Low risk with proper ordering.

### DL-002: Redis + PostgreSQL Deadlock (MEDIUM — MITIGATED)
**Scenario:** Worker holds Redis lock, waits for DB connection. DB operation holds connection, Redis lock TTL expires. New worker acquires lock, starts job. First worker DB operation commits — two workers complete the same step.

**Mitigation:**
- DB connection pool sizing sufficient (20 connections per worker, pool_max_overflow=10).
- Redis lock TTL (600s) >> max DB operation time (< 30s).
- Idempotency key prevents duplicate completion even if both workers finish the step.

**Verdict:** ✅ Idempotency is the final safety net.

### DL-003: Celery Canvas Circular Dependency (LOW — N/A)
**Scenario:** Pipeline creates circular Celery task chains.

**Verdict:** ✅ Not applicable — pipeline is strictly linear (F6.2 → F6.3 → F7). No circular chains.

## 5. Queue Bottleneck Analysis

### QB-001: Single `ingestion` Queue Overload (HIGH — MITIGATED)
**Root Cause:** All three pipeline stages (extraction, chunking, embedding) share the `ingestion` queue in the current implementation.

**Architecture Resolution:**
- F6.1 introduces **dedicated priority sub-queues**: `ingestion.critical`, `ingestion.high`, `ingestion.normal`, `ingestion.low`.
- F6.2 extraction and F6.3 chunking tasks are routed independently via `task_routes`.
- Dedicated worker pools for each queue prevent head-of-line blocking.

**Verdict:** ✅ Queue isolation achieved.

### QB-002: Large File Extraction Blocking Queue (HIGH — MITIGATED)
**Scenario:** A 500MB PDF takes 15 minutes to OCR, blocking the ingestion worker for all other jobs.

**Mitigation:**
- File size tiers: Files > 100MB routed to `ingestion.low` queue (dedicated slow workers).
- Streaming extraction (page batches) — worker remains responsive to heartbeat.
- Celery time limit: `soft_time_limit=900s, time_limit=1200s` — task killed if too slow.

**Verdict:** ✅ Large files isolated to dedicated slow worker pool.

### QB-003: DLQ Backpressure (MEDIUM — MITIGATED)
**Scenario:** DLQ fills up with thousands of permanently failed jobs, consuming Redis memory.

**Mitigation:**
- Redis DLQ entries TTL = 7 days (auto-expiry).
- PostgreSQL DLQ records are permanent (audit requirement).
- DLQ purge Celery Beat task runs every 24h: archives old DLQ entries to S3.
- DLQ depth alert: PagerDuty if `ingestion.dlq` depth > 100.

**Verdict:** ✅ Bounded.

## 6. Worker Starvation Analysis

### WS-001: Chunking Workers Starved by Extraction (MEDIUM — MITIGATED)
**Scenario:** Extraction tasks consume all worker threads, leaving chunking tasks waiting in queue.

**Mitigation:**
- Extraction and chunking tasks routed to **separate Celery queues**: `ingestion.extract` vs `ingestion.chunk`.
- Each queue has **dedicated worker pool** with separate concurrency settings.
- Kubernetes HPA scales each worker pool independently based on queue depth.

**Verdict:** ✅ Independent scaling achieved.

### WS-002: Semantic Chunking CPU Starvation (LOW — ACCEPTED)
**Scenario:** Semantic chunking (embedding-based sentence similarity) is significantly slower than recursive chunking, starving other chunk jobs.

**Mitigation:**
- Semantic chunking routed to dedicated `ingestion.chunk.semantic` sub-queue.
- Separate (smaller) worker pool.
- Workspace tier gate: Semantic chunking restricted to Enterprise plan workspaces.

**Verdict:** ✅ Risk accepted and bounded to Enterprise tier.

## 7. Redis Failure Scenarios

### RF-001: Redis Broker Failure (CRITICAL — MITIGATED)
**Scenario:** Redis becomes unavailable. All Celery task submission fails. Pipeline halts.

**Mitigation:**
- Redis Sentinel / Redis Cluster in production (HA configuration).
- Celery broker failover: Configure `CELERY_BROKER_TRANSPORT_OPTIONS` with multiple sentinel hosts.
- Fallback: PostgreSQL-based polling queue (via `django-celery-results` pattern adapted to FastAPI).
- Circuit breaker: If Redis unavailable > 60s, API returns 503 for new upload requests.

**Verdict:** ✅ HA Redis required as infrastructure prerequisite.

### RF-002: Redis Memory Exhaustion (HIGH — MITIGATED)
**Scenario:** Millions of idempotency keys + lock keys exhaust Redis memory.

**Mitigation:**
- Idempotency keys TTL = 24h (auto-expiry).
- Lock keys TTL = 600s.
- Celery result backend TTL = 24h.
- Redis `maxmemory-policy = allkeys-lru` as safety valve.
- Redis memory alert: PagerDuty at 80% utilization.

**Verdict:** ✅ TTLs bound memory usage.

### RF-003: Redis Lock Loss During Network Partition (MEDIUM — ACCEPTED)
**Scenario:** Network partition between worker and Redis. Worker continues processing without lock. Another worker acquires the lock. Two workers process the same job.

**Mitigation:**
- Idempotency key is the secondary protection: whichever worker completes first wins; second worker finds key and skips.
- PostgreSQL unique constraints on chunk content_hash prevent duplicate DB writes.
- This is an accepted risk for the non-distributed Redis (Redlock would add complexity).

**Verdict:** ⚠️ Accepted risk. Idempotency provides eventual consistency. For extreme HA: Redlock with 3 Redis nodes.

## 8. Celery Failure Scenarios

### CF-001: Worker Process Crash Mid-Step (HIGH — MITIGATED)
**Scenario:** Worker crashes between writing text artifact to S3 and updating `DocumentVersion.extracted_text_path` in DB.

**Mitigation:**
- `task_reject_on_worker_lost=True` returns task to queue.
- Retry checks S3 artifact existence before re-extracting.
- If artifact exists in S3 but DB not updated: Resume step, update DB, skip extraction.
- `extracted_text_path` write is idempotent (same path written on retry).

**Verdict:** ✅ S3 artifact acts as durable checkpoint.

### CF-002: Celery Beat Scheduler Failure (MEDIUM — MITIGATED)
**Scenario:** Celery Beat fails. Scheduled tasks (stale job monitor, DLQ purge, anti-starvation escalation) stop running.

**Mitigation:**
- Celery Beat runs on dedicated pod with separate health check.
- Kubernetes restart policy: Always.
- Beat tasks are idempotent (safe to run multiple times after recovery).

**Verdict:** ✅ Kubernetes handles Beat process liveness.

### CF-003: Celery Result Backend Unavailability (LOW — MITIGATED)
**Scenario:** Redis result backend unavailable. Task results cannot be stored.

**Mitigation:**
- Task results are not relied upon for pipeline progression — pipeline state is in PostgreSQL (ProcessingJob, ProcessingJobStep).
- Celery `ignore_result=False` but result backend failure is non-fatal to pipeline.
- `result_expires=86400` limits accumulation.

**Verdict:** ✅ PostgreSQL is the source of truth, not Redis result backend.

## 9. Memory Leak Analysis

### ML-001: Large File Stream Not Closed (HIGH — MITIGATED)
**Scenario:** `BinaryIO` stream from S3 not closed after extraction, leaking file handles and memory.

**Mitigation:**
- All stream reads use `async with storage.get_stream(...) as stream:` context manager.
- Explicit `stream.close()` in `finally` blocks.
- Page-batch processing for large files (generator pattern, not full load).

**Verdict:** ✅ Context managers enforced in design.

### ML-002: Chunk Batch Accumulation (MEDIUM — MITIGATED)
**Scenario:** All 10,000 chunks for a large document accumulated in memory before bulk insert.

**Mitigation:**
- Batch size = 500 chunks. Each batch is inserted and memory freed before next batch.
- Generator-based chunk iteration from `split_text()`.

**Verdict:** ✅ Streaming batch pattern prevents OOM.

### ML-003: Celery Worker Memory Growth Over Time (LOW — MITIGATED)
**Scenario:** Worker processes accumulate memory over many tasks.

**Mitigation:**
- `worker_max_tasks_per_child=1000` — worker process recycled after 1000 tasks.
- `worker_max_memory_per_child=512000` (KB) — worker recycled at 512MB.

**Verdict:** ✅ Bounded by worker recycling policy.

## 10. Duplicate Processing & Exactly-Once Guarantees

### Exactly-Once at Step Level:
| Mechanism | Scope | Guarantee |
|-----------|-------|-----------|
| Redis Distributed Lock | Per-job | At-most-once concurrent processing |
| Redis Idempotency Key | Per-job per-step | Exactly-once step execution |
| PostgreSQL `unique (doc_version_id, content_hash)` | Per-chunk | Exactly-once chunk creation |
| S3 artifact check before re-extraction | Per-extraction | Idempotent re-runs |
| ProcessingJobStep status check | Per-step | Skip already-completed steps on resume |

**Overall Guarantee:** The system achieves **at-least-once delivery** (Celery default) with **idempotency at every step** to achieve **effectively exactly-once processing** without the overhead of distributed transactions.

**Verdict:** ✅ Industry-standard approach. Matches Kafka + exactly-once semantics pattern.

### IG-001: Extraction Artifact Written, DB Not Updated (MITIGATED)
- Covered by: S3 key check on retry + idempotent DB write.

### IG-002: Chunk Records Inserted, CHUNKING_COMPLETED Not Emitted (MITIGATED)
- Covered by: Event emission is the final step; retry replays from step start; chunk dedup prevents duplicate inserts.

### IG-003: ProcessingJobStep Written, Celery Next Task Not Enqueued (MITIGATED)

### IG-004: Cancellation Signal Set After Job Already Completed (MITIGATED)
- Covered by: Final job status check before acting on cancel signal.

**Verdict:** ✅ All identified idempotency gaps are closed.

## 13. Scaling Issues

### SI-001: PostgreSQL `processing_jobs` Table Growth (HIGH — MITIGATED)
**Scenario:** At 1M docs/day, `processing_jobs` grows by 1M rows/day. Query performance degrades.

**Mitigation:**
- Monthly partitioning by `created_at`.
- Composite index on `(tenant_id, status, created_at)`.
- Archival: Jobs older than 90 days moved to cold storage table.

**Verdict:** ✅ Partitioning plan defined.

### SI-002: `document_chunks` Table at Billions of Rows (HIGH — MITIGATED)
**Scenario:** 1M docs × 20 chunks = 20M chunks/day. 30-day retention = 600M rows.

**Mitigation:**
- Monthly partitioning by `created_at`.
- Composite index: `(tenant_id, document_version_id)`.
- Knowledge Health worker (Epic 12) archives orphan chunks.

**Verdict:** ✅ Partitioning plan defined.

### SI-003: Horizontal Worker Scaling Coordination (MEDIUM — MITIGATED)
**Scenario:** Adding more Celery workers increases DB connection pool pressure.

**Mitigation:**
- PgBouncer connection pooler sits between workers and PostgreSQL.
- `DB_POOL_SIZE` configurable per worker type.
- Max 20 workers per queue at system design limit without PgBouncer scaling.

**Verdict:** ✅ PgBouncer already integrated (F5.8).

## 14. Disaster Recovery Gaps

### DR-001: Redis Complete Data Loss (HIGH — MITIGATED)
**Scenario:** Redis cluster loses all data (no persistence configured).

**Mitigation:**
- Enable Redis AOF persistence in production.
- Pipeline state is in PostgreSQL — Redis loss means lock/idempotency key loss only.
- Recovery: PENDING/QUEUED jobs re-enqueued by StaleJobMonitor after detecting no active workers.
- RPO: < 5 minutes (StaleJobMonitor interval).

**Verdict:** ✅ PostgreSQL is the authoritative state store.

### DR-002: S3 Artifact Loss (CRITICAL — MITIGATED)
**Scenario:** S3 bucket loses normalized text.txt artifacts.

**Mitigation:**
- S3 versioning enabled on artifact bucket.
- S3 cross-region replication for disaster recovery.
- Pipeline re-runs extraction from original uploaded file (original is also in S3 with WORM policy from Epic 1).

**Verdict:** ✅ Two-layer S3 protection (WORM original + versioned derived artifacts).

### DR-003: PostgreSQL Data Loss (CRITICAL — MITIGATED)
**Scenario:** PostgreSQL loses `processing_jobs` or `document_chunks` data.

**Mitigation:**
- PostgreSQL continuous WAL archiving + PITR (Point-in-Time Recovery).
- Daily backups to S3.
- Processing is re-runnable: Source files in S3 allow full pipeline re-execution.

**Verdict:** ✅ Standard PostgreSQL HA practices.
