**Feature:** F6.4 — Embedding Generation Worker  
**Epic:** Epic 6 — Knowledge Processing Pipeline  
**ADR References:** ADR-M2-001, ADR-M2-002, ADR-M2-003, ADR-005  
**Architect:** Principal Engineering Review  
**Date:** 2026-08-04  
**Status:** ARCHITECTURE APPROVED — AWAITING IMPLEMENTATION

---

## 1. Executive Summary

F6.4 establishes the **Embedding Generation Worker** as the fourth stage of the RAGuard document ingestion pipeline. It consumes `DocumentChunk` records produced by F6.3 (Text Chunking), vectorizes them using multi-provider batch embedding, persists `ChunkEmbedding` records into PostgreSQL, and emits canonical domain events to trigger F6.5 (Qdrant Vector Indexing).

The foundation **already exists** in `backend/modules/embedding/`. This design **does not invent new infrastructure** — it specifies how the existing `EmbeddingService`, `EmbeddingManager`, `CeleryEmbeddingWorker`, `EmbeddingRepository`, and provider stack integrate correctly into the `ProcessingJob` pipeline, adds the missing enterprise controls (distributed locking, rate limiting, cancellation, cost tracking), and addresses every principal-engineer-level concern.

## 3. Pipeline Position in ProcessingJob Lifecycle

```
[F6.1] ProcessingJob Created (PENDING)
    ↓
[F6.2] OCR/Extraction Worker → DocumentVersion + extracted text
    ↓
[F6.3] Chunking Worker → DocumentChunk[] (is_embedded=False)
    ↓ CHUNKING_COMPLETED event triggers
[F6.4] *** Embedding Generation Worker ***
    ↓
[F6.5] Vector Indexing Worker → Qdrant upsert
```

The `CHUNKING_COMPLETED` event (emitted by F6.3) must trigger the embedding pipeline. This is handled by the pipeline listener (`backend/tasks/listeners.py`).

## 4. End-to-End Embedding Pipeline Flow

### 4.1 Trigger Mechanism

```
CHUNKING_COMPLETED event
  → EventDispatcher handler (pipeline listener)
    → EmbeddingService.initiate_embedding_job()
      → Creates EmbeddingJob (status=PENDING)
        → process_embedding_batch_task.delay(job_id, tenant_id)
          → Celery "embeddings" queue
```

The listener must NOT block on the Celery dispatch — it fires and forgets.

### 4.2 Celery Task Execution

```
process_embedding_batch_task (queue="embeddings", max_retries=3, acks_late=True)
  → asyncio.run(_async_process_embedding_task())
    → AsyncSession factory
      → acquire_lock(f"embedding:{job_id}", timeout=600)
        → CeleryEmbeddingWorker.execute_batch()
          → EmbeddingService.process_embedding_batch()
```

### 4.3 EmbeddingService.process_embedding_batch() — Detailed Flow

```
1. LOAD JOB
   job = repository.get_job_by_id_and_tenant(job_id, tenant_id)
   → Guard: job must exist, tenant must match → prevent cross-tenant access

2. CANCELLATION CHECK
   if job.status == "CANCELLED": return early (idempotent exit)
   if ProcessingJob.cancelled_at is set: update EmbeddingJob status → CANCELLED, return

3. ARCHIVE AWARENESS CHECK
   if Document.status == "ARCHIVED": skip embedding, log warning, return

4. UPDATE JOB STATUS → PROCESSING

5. RESOLVE PROVIDER
   EmbeddingManager(provider_name=job.provider, model_name=job.model_name)

6. RATE LIMIT CHECK (per tenant, per provider)
   RateLimiter.check_limit(tenant_id, "embedding", provider, batch_size, limit, window)
   → Raises RateLimitExceeded → triggers Celery retry with countdown

7. BATCH LOOP (while True):
   a. get_unembedded_chunks(tenant_id, document_version_id, batch_size)
   b. IF empty → break

   c. IDEMPOTENCY FILTER (Zero-call):
      hashes = [c.content_hash for c in chunks]
      existing = repository.filter_existing_content_hashes(hashes, tenant_id, provider, model)
      new_chunks = [c for c in chunks if c.content_hash not in existing]
      skip_chunks = [c for c in chunks if c.content_hash in existing]

   d. Fast-path for cached: mark_chunks_as_embedded(skip_chunks)

   e. FOR new_chunks:
      texts = [c.content for c in new_chunks]
      result = await manager.vectorize_batch(texts, batch_size=batch_size)
      → EmbeddingBatchResult { embeddings, tokens_consumed, provider_metadata }

   f. PERSIST ChunkEmbedding records (bulk insert)

   g. mark_chunks_as_embedded(new_chunks)

   h. update_job_progress(processed_delta, tokens_delta)

   i. TOKEN COST TRACKING:
      token_cost = result.tokens_consumed * cost_per_token_for_provider
      → Stored in EmbeddingJob.step_metrics JSONB (or dedicated cost field)

   j. PARTIAL BATCH RECOVERY:
      On sub-batch failure: increment failed_chunks
      Continue to next sub-batch (do not abort entire job)

   k. PROGRESS EVENT: dispatch EMBEDDING_PROGRESS

8. UPDATE JOB STATUS → COMPLETED
9. dispatch EMBEDDING_COMPLETED event
   → This event triggers the F6.5 vector sync listener
```

## 5. Provider Abstraction & Fallback Strategy

### 5.1 Provider Resolution

The `EmbeddingProviderFactory` resolves providers from a **thread-safe singleton registry**:
- `openai` → `OpenAIEmbeddingProvider`
- `cohere` → `CohereEmbeddingProvider`  
- `local` → `LocalEmbeddingProvider`

### 5.2 Provider Fallback Chain

F6.4 introduces a **fallback chain** concept at the `EmbeddingManager` layer:

```python
PRIMARY: openai (text-embedding-3-large, 1536-dim)
  ↓ on RateLimitExceeded or TimeoutError
SECONDARY: cohere (embed-multilingual-v3.0, 1024-dim)
  ↓ on failure
TERTIARY: local (BAAI/bge-large-en-v1.5, 1024-dim)
  ↓ on failure
FAILED: emit EMBEDDING_FAILED, update job → FAILED, DLQ
```

**Critical Constraint:** Fallback dimension must be tracked per `EmbeddingJob`. The `ChunkEmbedding.dimension` and `EmbeddingJob.model_name` must reflect the actual provider used, not the intended one. This is essential for Qdrant collection routing in F6.5.

### 5.3 Version Awareness

Before any batch is initiated:
- Query `DocumentVersion` to confirm it is the `latest` and not `ARCHIVED`
- If a newer version exists, skip embedding (stale document version guard)

## 6. Distributed Locking

### 6.1 Lock Scope

```python
lock_name = f"embedding:job:{job_id}"
timeout = 600  # 10 minutes — max job execution time
acquire_timeout = 5  # seconds to wait before failing fast
```

This prevents two Celery workers from processing the same `EmbeddingJob` simultaneously — a real risk during retry storms.

### 6.2 Lock Placement

```python
async with acquire_lock(f"embedding:job:{job_id}", timeout=600):
    # Entire batch processing loop executes here
    await worker.execute_batch(...)
```

If `LockAcquisitionError` is raised, the task returns immediately without retry — another worker already holds the job.

## 7. Rate Limiting

### 7.1 Provider-Level Rate Limiting

Each embedding provider has API rate limits. F6.4 enforces these via the existing `RateLimiter`:

```python
# OpenAI: ~3,000 RPM for embeddings API
await RateLimiter.check_limit(
    tenant=tenant_id,
    domain="embedding",
    action=f"provider:{provider}",
    entity_id=tenant_id,
    limit=PROVIDER_RATE_LIMITS[provider],
    window_seconds=60
)
```

On `RateLimitExceeded`:
- The Celery task **does not fail** — it retries with `countdown = 60s` (aligned to rate limit window)
- `EmbeddingJob.status` remains `PROCESSING`

### 7.2 Tenant Token Quota

```python
if max_token_quota:
    metrics = await repository.get_tenant_metrics(tenant_id)
    if metrics["total_tokens_consumed"] >= max_token_quota:
        raise TokenQuotaExceededError(...)
```

This check runs at job initiation and can also be applied per-batch for long-running jobs.

## 8. Timeout & Cancellation Handling

### 8.1 Provider Timeout

Each provider call is wrapped with `asyncio.timeout`:

```python
async with asyncio.timeout(PROVIDER_TIMEOUT_SECONDS[provider]):
    result = await manager.vectorize_batch(texts, batch_size)
```

Default timeouts: `openai=30s`, `cohere=20s`, `local=60s`.

On `asyncio.TimeoutError`:
- Treated as `RECOVERABLE` → Celery retry with jittered backoff
- Error logged: `EMB_006 — Provider timeout`

### 8.2 Job Cancellation

```python
# At the top of execute_batch and between batch iterations:
job = await repository.get_job_by_id_and_tenant(job_id, tenant_id)
if job.status == "CANCELLED":
    logger.info("embedding_job_cancelled", job_id=job_id)
    return  # Clean exit, no retry
```

Additionally, the pipeline listener handles `DOCUMENT_ARCHIVED` events to cancel in-flight embedding jobs.

## 10. Partial Batch Recovery

If a sub-batch within a large document fails:

```
Batch 1 (chunks 0-99): SUCCESS → persisted
Batch 2 (chunks 100-199): PROVIDER_TIMEOUT
  → increment failed_chunks by 100
  → Continue to Batch 3
  → At end: EmbeddingJob.status = PARTIAL_COMPLETE
    → OR: Re-queue failed chunk IDs for retry in next task execution
```

The `partial_complete` sentinel triggers a subsequent Celery retry task that retries ONLY the failed sub-batch, identified by `EmbeddingJob.failed_chunks > 0`.

## 11. Idempotency

F6.4 implements **three levels** of idempotency:

| Level | Mechanism | Guard Against |
|---|---|---|
| **Job-level** | `ProcessingJob.idempotency_key` (unique) | Duplicate job creation on double-publish |
| **Chunk-level** | `content_hash` filter in `filter_existing_content_hashes()` | Re-processing identical content |
| **DB-level** | `UNIQUE(tenant_id, chunk_id)` on `chunk_embeddings` | Concurrent worker race on same chunk |

## 12. Retry Strategy

| Error Type | Severity | Strategy |
|---|---|---|
| API rate limit exceeded | RECOVERABLE | Retry after 60s (rate limit window reset) |
| Provider timeout | RECOVERABLE | Jittered backoff (base=5s, max=300s) |
| Network/connection error | RECOVERABLE | Jittered backoff, max 3 retries |
| Invalid API key | FATAL | No retry, DLQ immediately |
| Token quota exceeded | FATAL | No retry, alert tenant |
| Dimension mismatch | FATAL | No retry, requires config fix |

Jittered backoff formula (existing in `CeleryEmbeddingWorker`):
```python
exponential = min(max_seconds, base_seconds * (2 ** retry_count))
jitter = random.uniform(1.0, 5.0)
countdown = round(min(max_seconds, exponential + jitter), 2)
```

---

## 13. Dead Letter Queue (DLQ)

After `max_retries=3` exhausted:
1. `EmbeddingJob.status → FAILED`
2. `ProcessingJob.status → FAILED`
3. `ProcessingJob.dlq_reason` = error message
4. `ProcessingJob.dlq_at` = now()
5. Task is routed to `jobs.dlq` queue
6. `EMBEDDING_FAILED` event dispatched
7. Admin alert triggered (Phase 4 monitoring)

## 18. Failure Recovery

### Scenario: Worker Crash Mid-Job

1. `EmbeddingJob.status = PROCESSING`
2. Celery `acks_late=True` + `task_reject_on_worker_lost=True` → task re-queued automatically
3. Distributed lock expires (timeout=600s)
4. New worker picks up task → acquires lock → checks `EmbeddingJob.status`
5. `PROCESSING` status → resumes from last committed batch position
6. Idempotency filter skips already-committed chunks

### Scenario: Redis Failure

1. Lock acquisition fails → worker cannot proceed
2. Task raises exception → Celery retries with backoff
3. If Redis is recovered within retry window, processing resumes
4. If Redis fails permanently: DLQ after max retries

## 21. Security Controls

| Control | Implementation |
|---|---|
| **API key isolation** | Per-tenant API keys from settings/vault, never logged |
| **Cross-tenant** | All queries filter by `tenant_id` |
| **Token exposure** | Embedding vectors never returned to API layer directly |
| **Audit trail** | All job state transitions logged with `tenant_id` |
| **DLQ access** | Only platform admins can inspect/requeue DLQ tasks |

## 22. Horizontal Scalability

- Celery `embeddings` workers are stateless — scale horizontally
- Distributed lock prevents duplicate processing for the same job
- Sub-batch size (`batch_size=100`) is tunable per worker capacity
- Provider sub-batching in `EmbeddingManager` handles large documents

## 23. Open Design Decisions

| Decision | Recommended Approach |
|---|---|
| Fallback dimension mismatch | Track per-job `actual_dimension` field; F6.5 must route to correct collection |
| Cost budget enforcement | Implement hard budget cap in tenant settings (Phase 3) |
| Partial completion retry | Use `failed_chunk_ids JSONB` array in `EmbeddingJob` for targeted re-processing |
| Progress visibility | Expose `EmbeddingJob` status via existing `GET /api/v1/embeddings/{job_id}` endpoint |
