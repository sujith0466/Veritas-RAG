# Architecture Document: F6.3 — Text Chunking Worker (Epic 6)

## Document Control
**Project:** RAGuard V2
**Epic:** Epic 6 - Data Ingestion & Pipeline
**Component:** F6.3 - Text Chunking Worker
**Role:** Text processing, structural splitting, tokenization, and domain entity generation

---

## 1. Executive Summary
F6.3 represents the text chunking worker within the RAGuard V2 ingestion pipeline. It acts as the bridge between raw extracted text artifacts (produced by the F6.2 Extraction worker) and the downstream embedding/vectorization pipeline (Epic 7). This worker receives normalized text, applies intelligent chunking strategies tailored to the document's structure and MIME type, and produces structured, doubly-linked, deduplicated chunk records in PostgreSQL. By employing robust parent-child lineage tracking and advanced token estimation, F6.3 ensures that generated chunks are optimized for retrieval-augmented generation (RAG) at enterprise scale, handling millions of documents per day with stringent multi-tenant isolation.

## 2. Feature Scope
The Text Chunking Worker encompasses the following deliverables:
- **Chunking Strategies:** 
  - Recursive chunking (general prose)
  - Semantic chunking (sentence-boundary-aware via lightweight embeddings)
  - Markdown chunking (heading-hierarchy-aware)
  - Code chunking (function/class boundary-aware)
  - Table chunking (row-by-row linearization)
  - Paragraph chunking (double-newline splits)
  - Sentence chunking (fallback logic)
- **Context Preservation:** Configurable sliding window overlap for semantic continuity.
- **Token Estimation & Validation:** Fast heuristics (4 chars/token) alongside accurate `tiktoken` integrations.
- **Metadata Extraction:** Precise tracking of page numbers, section paths, and applied strategies.
- **Lineage Tracking & Graph Construction:** Parent-child relationships for hierarchical splits and a doubly-linked sequential graph (`previous_chunk_id`, `next_chunk_id`).
- **ChunkRelationship Edges:** Edges for parent_child, sequential, table_cell, and cross_ref associations.
- **Deduplication:** Intra-version deduplication using SHA-256 content hashing.
- **State Lifecycle & Batch Processing:** Robust chunk state management, bulk persistence, worker orchestration via Celery, and comprehensive caching.
- **Observability:** Granular events and operational metrics for pipeline monitoring.

## 3. Chunking Pipeline Architecture

The chunking worker operates as an asynchronous, event-driven pipeline driven by domain events.

### 3.1 Pipeline Flow
The execution flow is structured into sequential stages triggered upon the completion of text extraction:

1. **F6.2 Completion Event:** Worker triggered by `PROCESSING_JOB_STEP_COMPLETED` (step: extraction).
2. **Stage 1: Input Resolution**
   - Retrieve `ProcessingJob` by `job_id`, verifying `version_id`, `tenant_id`, and `priority`.
   - Read `DocumentVersion.extracted_text_path`.
   - Stream the normalized `text.txt` artifact from the `LocalStorageProvider` / S3 abstraction.
3. **Stage 2: Strategy Selection**
   - Analyze MIME type from `DocumentVersion`'s `metadata_json`.
   - Utilize `SplitterStrategyFactory.get_splitter(mime_type, strategy_override)` to instantiate the appropriate `BaseChunkSplitter`.
   - Resolve parameters (e.g., `max_chars`, `overlap_chars`) via workspace feature flags or task arguments.
4. **Stage 3: Text Splitting**
   - Execute `splitter.split_text()`, returning a collection of `ChunkDTO` objects.
   - Perform post-split token estimation and generate SHA-256 `content_hash` for each chunk.
5. **Stage 4: Hierarchy & Lineage Construction**
   - Establish parent-child structural boundaries (e.g., mapping a Markdown H1 header to its subordinate paragraphs).
   - Construct the doubly-linked sequential chain.
   - Formulate `ChunkRelationship` entities.
6. **Stage 5: Deduplication & Quota Check**
   - Execute deduplication logic against existing chunks for the same version via `content_hash`.
   - Validate against the workspace chunk generation quota.
7. **Stage 6: Batch Persistence**
   - Bulk insert `DocumentChunk` entities into PostgreSQL in batches of 500.
   - Bulk insert corresponding `ChunkRelationship` records.
   - Transition `Document.status` to `CHUNKED`.
8. **Stage 7: Chunk Artifact (Optional)**
   - Serialized `chunks.json` uploaded to a versioned storage path for large document auditing and debugging.
9. **Stage 8: Event Emission**
   - Emit `CHUNKING_COMPLETED` domain event.
   - Emit `PROCESSING_JOB_STEP_COMPLETED`, queuing the F7 Embedding task.

## 4. Strategy Selection Logic

Strategy assignment relies on content characteristics, explicit overrides, and workspace defaults.

### 4.1 MIME Type → Strategy Mapping
| MIME Type | Primary Strategy | Fallback |
|-----------|------------------|----------|
| `text/plain` | `recursive` | `paragraph` |
| `text/markdown` | `markdown` | `recursive` |
| `application/pdf` | `recursive` | `sentence` |
| `application/vnd.openxmlformats-officedocument.wordprocessingml.document` | `recursive` | `paragraph` |
| `application/vnd.ms-powerpoint*` | `paragraph` | `recursive` |
| `application/vnd.ms-excel*` | `table` | `recursive` |
| `text/html` | `markdown` | `recursive` |
| `text/x-python` / `text/x-java` / `text/x-cpp` | `code` | `recursive` |
| Default | `recursive` | `paragraph` |

### 4.2 Strategy Override
- The Celery task accepts a `strategy_override` parameter (sourced from API input or workspace routing configs).
- A workspace feature flag (`chunking_strategy_default`) can globally dictate default behavior.
- Any requested strategy is validated against the `SplitterStrategyFactory`. Invalid selections automatically gracefully degrade to the MIME-mapped default.

### 4.3 Parameter Resolution
Parameters dictates sizing boundaries. Resolution priority is evaluated highest to lowest:
1. **Per-request override:** Explicit parameters in the API payload.
2. **Workspace configuration:** Tenant-level settings (`chunking_max_characters`, `chunking_overlap`).
3. **Strategy defaults:** Encapsulated in the `StrategyInfoDTO`.
4. **System defaults:** Hardcoded fallbacks (`max_characters=1000`, `overlap_characters=200`).

## 5. Chunking Strategies (Detailed Design)

All strategies extend `BaseChunkSplitter`.

### 5.1 Recursive Character Splitter (`recursive`)
- **Mechanism:** Iteratively attempts to split text using a hierarchical list of separators: `['\n\n', '\n', '. ', ' ', '']`.
- **Functionality:** Ensures natural boundary preservation (paragraph → sentence → word) until the segment fits within the character limit.
- **Overlap:** Implements a sliding window, prepending the last `N` characters of the preceding chunk.
- **Use Case:** PDFs, plain text, and general prose.

### 5.2 Semantic Splitter (`semantic`)
- **Mechanism:** Identifies boundaries based on sentence termination and drops in semantic similarity.
- **Functionality:** Employs sentence tokenizers (NLTK or spaCy) and computes cosine similarity between adjacent sentences using a lightweight, local embedding model (e.g., `e5-small-v2`).
- **Thresholds:** Configurable `similarity_drop_threshold` (default `0.7`).
- **Use Case:** Complex research papers and academic documents where structural boundaries do not align with thematic boundaries.

### 5.3 Markdown Splitter (`markdown`)
- **Mechanism:** Parses hierarchical markdown structures (H1 → H2 → H3 → paragraphs).
- **Functionality:** Ancestor headings are prepended to descendant chunks to maintain context. Populates `section_path` (e.g., `['H1: Introduction', 'H2: Background']`).
- **Preservation:** Code blocks remain unsplit; extracted tables are delegated to the Table Splitter.
- **Use Case:** Wikis, documentation, HTML, and Markdown files.

### 5.4 Code Splitter (`code`)
- **Mechanism:** AST (Abstract Syntax Tree) parsing to isolate functional boundaries (methods, classes, modules).
- **Functionality:** Requires `ast` for Python or `tree-sitter` for other languages. Guarantees functions are never split mid-block and preserves associated docstrings. Populates `section_path` appropriately.
- **Use Case:** Source code repositories and scripts.

### 5.5 Table Splitter (`table`)
- **Mechanism:** Processes structured tabular data extracted via `XLSXExtractor` or HTML parsing.
- **Functionality:** Linearlizes data row-by-row (e.g., `Column1: val1 | Column2: val2`). The header row is prepended to every chunk as continuous context. Generates `ChunkRelationship` entries of type `table_cell`.
- **Use Case:** Spreadsheets and document-embedded tables.

### 5.6 Paragraph Splitter (`paragraph`)
- **Mechanism:** Simple delimiter-based splitting on double newlines (`\n\n`).
- **Functionality:** Falls back to single newline (`\n`) if a paragraph violates the `max_characters` threshold. Maintains blank line context via overlap configuration.

### 5.7 Sentence Splitter (`sentence`)
- **Mechanism:** Tokenizes text into discrete sentences using NLTK `sent_tokenize` or regex.
- **Functionality:** Bundles consecutive sentences until `max_characters` is reached. Includes the last `K` sentences from the preceding chunk for the sliding window.

## 6. Sliding Window Overlap
Context preservation is managed via a sliding window configuration.
- **Implementation:** Appends the final `overlap_characters` of `chunk[i]` to the beginning of `chunk[i+1]`.
- **Purpose:** Safeguards semantic meaning that may bridge chunk boundaries, improving RAG retrieval accuracy.
- **Edge Cases:** If `overlap_characters` exceeds the size of the preceding chunk, the entire preceding chunk is used.
- **Exclusions:** Explicitly disabled for Code chunks (breaks syntax) and Table chunks (redundant with prepended headers).
- **Tracking:** Stored internally as `overlap_start_index` to facilitate precise deduplication.

## 7. Token Estimation

Effective RAG relies on strict compliance with embedding model token limits.

### 7.1 Fast Estimation
- **Method:** `estimate_token_count(text) = ceil(len(text) / 4.0)`
- **Usage:** Pre-split sizing and real-time quota evaluations where performance supersedes precision.

### 7.2 Accurate Estimation
- **Method:** Integration with `tiktoken` utilizing the `cl100k_base` encoding (GPT-4 / text-embedding-3 compatible).
- **Usage:** Applied post-split for definitive validation. Stored persistently in `DocumentChunk.token_count`.
- **Fallback:** If a chunk inadvertently breaches the 8192 token limit, the recursive strategy is aggressively re-applied on the offending chunk.

### 7.3 Token Budget Enforcement
- **Limits:** Hard limit of 8192 tokens per chunk, though workspaces typically configure lower operational thresholds (e.g., 512 or 1024).
- **Oversized Handling:** A warning domain event is dispatched if parameters predictably cause token overflow, and chunks are automatically re-split to fit boundaries.

## 8. Chunk Metadata Design

### 8.1 DocumentChunk Entity Fields
- `id`: UUID4 (BaseModel).
- `tenant_id`, `document_id`, `document_version_id`: Security and isolation scopes.
- `chunk_index`: 0-indexed sequential identifier within the document version.
- `content`: The explicit string data.
- `content_hash`: SHA-256 string representing the content.
- `strategy_used`: String enum representing the specific algorithm.
- `token_count` / `character_count`: Numerical sizing metrics.
- `parent_chunk_id`: UUID4 reference for hierarchical structure.
- `previous_chunk_id` / `next_chunk_id`: UUID4 references forming a doubly-linked list.
- `page_numbers`: JSONB list containing spanned pages.
- `section_path`: JSONB list containing navigational hierarchy.
- `metadata_json`: JSONB column for extended attributes.
- `is_embedded`: Boolean flag (default `False`).

### 8.2 metadata_json Extended Schema
```json
{
  "strategy_version": "1.0",
  "split_params": {
    "max_characters": 1000,
    "overlap_characters": 200
  },
  "extraction_method": "native",
  "language": "en",
  "has_overlap": true,
  "overlap_chars": 200,
  "has_tables": false,
  "has_code": false,
  "quality_score": 0.95
}
```

### 8.3 Chunk Lineage
- **Hierarchical:** Driven by `parent_chunk_id`. H1 chunks encapsulate overarching thematic context, while child paragraphs detail specifics.
- **Sequential:** Facilitated by `previous_chunk_id` and `next_chunk_id`, enabling the UI/Retrieval pipeline to fetch preceding/succeeding text for expanded context window injection.
- **Cross-Reference:** Graph edges via `ChunkRelationship` allow linking cited fragments (e.g., linking a footnote chunk to the citation point).

## 9. Content Hash Deduplication
- **Algorithm:** `SHA-256(content.strip())`
- **Scope:** strictly bounded within the same `document_version_id` to prevent cross-document data leakage.
- **Versioning Benefits:** When a new version of a document is uploaded, identical text blocks yield identical content hashes. If a match is detected against a prior version, the pipeline can flag `is_embedded=True` by re-linking the existing vector, vastly reducing downstream API costs.
- **Database Architecture:** Facilitated via a unique composite constraint on `(document_version_id, content_hash)`.

## 10. Batch Persistence
- **Execution:** Uses SQLAlchemy `bulk_insert_mappings` limiting payloads to 500 chunks per batch to balance memory pressure and connection time.
- **Reference Resolution:** `previous_chunk_id` and `next_chunk_id` are linked within the application logic prior to batch execution. The final chunk of Batch *N* is dynamically linked to the first chunk of Batch *N+1*.
- **Transactionality:** Each batch is wrapped in a dedicated DB transaction. Failure triggers a rollback of all batches for that document, leveraging the job's idempotency key to ensure safe retries.
- **Relationships:** `ChunkRelationship` records are subsequently bulk inserted only after all `DocumentChunk` entities are committed.

## 11. Chunk State Lifecycle
Chunk state is reflected logically or stored in `metadata_json['chunk_state']`.

| State | Description | Trigger |
|-------|-------------|---------|
| `PENDING` | Created and persisted; vectorization pending. | Post-batch persistence. |
| `EMBEDDED` | Content successfully vectorized and stored in Qdrant. | Post Epic 7 completion. |
| `INVALIDATED` | Rendered obsolete by a newer document version. | Upon F6.1 new version. |
| `ORPHANED` | Document deleted; chunk awaiting physical purge. | Upon Document soft deletion. |
| `PURGED` | Physically removed from RDBMS and Vector DB. | Knowledge Health cleanup. |

## 12. Worker Orchestration

### 12.1 Celery Configuration
- **Task Module:** `backend.modules.chunking.workers.tasks.process_document_chunking_task`
- **Queue Configuration:** Runs on the `ingestion` queue with standard priority routing.
- **Parameters:** `tenant_id`, `document_id`, `version_id`, `strategy_override`, `max_characters`, `overlap_characters`.

### 12.2 Execution Flow
1. Acquire Redis distributed lock via Redlock: `raguard:{tenant_id}:job:{job_id}:lock:chunking`.
2. Inspect idempotency token: `raguard:{tenant_id}:job:{job_id}:step:chunking`.
3. Assert `ProcessingJob` state verifies `EXTRACTION_COMPLETED`.
4. Stream extracted artifact from `LocalStorageProvider` / S3.
5. Execute stages 1-8 of the Chunking Pipeline.
6. Persist `ProcessingJobStep`: `step_name='chunking'`, `status=RUNNING`.
7. **Success:** Update step to `COMPLETED`, dispatch `CHUNKING_COMPLETED`, and queue downstream F7 task.
8. **Failure:** Delegate to F6.1 retry policy (exponential backoff / DLQ).
9. Release Redis lock.

### 12.3 Worker Concurrency Model
- Due to the CPU-intensive nature of textual AST parsing and tokenization, chunking utilizes process-based concurrency (threads or pre-forked workers), specifically avoiding `asyncio`.
- Configured with 4 prefork processes per node.
- `acks_late=True` and `prefetch_multiplier=1` to ensure worker crashes don't silently swallow large jobs.
- Strict memory guardrails (e.g., 256MB max footprint per job) to prevent OOM termination.

## 13. Cache Strategy

### 13.1 Strategy Configuration Cache
- **Key:** `raguard:{tenant_id}:chunking:config`
- **Content:** Aggregated workspace parameters.
- **TTL:** 300 seconds.
- **Invalidation:** Triggers upon configuration update events.

### 13.2 Chunk Count Cache
- **Key:** `raguard:{tenant_id}:doc:{doc_id}:chunk_count`
- **TTL:** 60 seconds.
- **Purpose:** O(1) retrieval for quota validations and UI progress bars.

### 13.3 Chunk Content Cache (Read Path)
- **Key:** `raguard:{tenant_id}:chunk:{chunk_id}:content`
- **TTL:** 3600 seconds (L2 cache).
- **Purpose:** Reduces PostgreSQL I/O during high-volume RAG retrieval. Limited to chunks under 10KB.

### 13.4 Explicit Cache Exclusions
- **Vectors:** Never cached in Redis; exclusively managed by Qdrant.
- **Hashes:** Deduplication hashes bypass cache to guarantee strict transactional consistency during pipeline runs.

## 16. Performance at Scale
- Designed for throughput handling 1M documents daily (approx. 20K chunks/minute).
- PostgreSQL optimization includes monthly partitioning on the `document_chunks` table by `created_at`.
- High-efficiency indices on `(tenant_id, document_version_id)` support localized querying.
- Purging operations are deferred to asynchronous Epic 12 Knowledge Health workers.

## 17. Multi-Tenant Isolation
- Strict Row-Level Security (RLS) enforcement at the DB layer via the mandated `tenant_id` on all `BaseModel` entities.
- All repository operations internally enforce `tenant_id` conditions.
- Redis keys are strictly namespaced.
- Feature flags and quotas are resolved exclusively within the bounded context of the tenant.

## 18. Security
- Complete absence of PII within unstructured metadata fields.
- Worker isolation guarantees no memory-level leakage between disparate tenant jobs.
- Deduplication relies on computationally irreversible SHA-256 hashes.

## 19. Integration with Downstream (Epic 7)
- The pipeline architecture utilizes an `EventDispatcher` listener.
- Upon receiving `CHUNKING_COMPLETED`, the listener constructs the payload (`tenant_id`, `document_id`, `version_id`, `chunk_ids`) and dispatches the Epic 7 Embedding Celery task.
- `ProcessingJob.current_step` iterates to `embedding`.

## 20. Failure Scenarios

| Scenario | Severity | Resolution |
|----------|----------|------------|
| Missing `text.txt` artifact from S3. | FATAL | Sent to DLQ; marked with `EXTRACT_003`. |
| Empty extracted text payload. | FATAL | Sent to DLQ; Document status set to `FAILED`. |
| Unrecognized strategy requested. | WARNING | Fallback to `recursive`; log emitted. |
| Database batch insert collision/timeout. | RECOVERABLE | Exception triggers Celery `retry` (exponential backoff). |
| Workspace chunk quota exceeded. | FATAL | Sent to DLQ; marked `CHUNK_QUOTA_001`; alert sent to tenant admin. |
| Hard token limit exceeded during split. | RECOVERABLE | Intercepted during evaluation; automatic recursive sub-splitting applied. |
