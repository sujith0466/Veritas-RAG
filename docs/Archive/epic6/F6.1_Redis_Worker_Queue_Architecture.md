# F6.1 — Redis Worker Queue Setup Architecture

## 1. Executive Summary
Feature F6.1 establishes the enterprise-grade asynchronous processing foundation for the Knowledge Processing Pipeline in RAGuard V2. As documents arrive asynchronously via the F5.8 BulkBatch feature, they require deterministic, fault-tolerant, and scalable processing. This architecture document defines the Redis-backed worker queue system, leveraging and extending the existing `ProcessingJob` entity and Celery infrastructure established in Epics 1-5. The design guarantees robust job execution with strict multi-tenancy, distributed locking, and robust retry capabilities to handle varying load profiles and transient failures gracefully.

## 2. Feature Scope & Objectives
F6.1 delivers a comprehensive background job processing subsystem. The specific objectives and deliverables include:
- **ProcessingJob Lifecycle Management**: Enhancing job tracking with granular step-level metrics and auditable state transitions.
- **Redis Queue Topology**: Structured prioritization and isolation of workloads.
- **Celery Queue Definitions**: Mapping domain tasks to specific prioritized queues.
- **Retry Policy & Exponential Backoff**: Intelligent retry mechanisms for transient failures.
- **Dead Letter Queue (DLQ)**: Isolation and manual review capabilities for permanently failed jobs.
- **Idempotency**: Ensuring exactly-once processing semantics for steps to handle duplicate deliveries.
- **Distributed Locking**: Preventing race conditions and concurrent processing conflicts across workers.
- **Job Priority & Worker Concurrency**: Fair resource allocation based on workload criticality.
- **Queue Monitoring & Metrics**: Deep observability into system throughput, queue depth, and bottlenecks.
- **Failure Recovery**: Predictable recovery mechanisms for worker, broker, and database failures.
- **Cancellation & Resume Support**: Allowing user-driven job cancellation and resumption from checkpoints.

## 3. Existing Infrastructure Reuse

## 5. Job State Machine
The core FSM managing the lifecycle of a `ProcessingJob`:

**Primary Flow:**
`PENDING` → `QUEUED` → `CLAIMED` → `RUNNING` → `COMPLETED`

**Failure & Retry Flow:**
`RUNNING` ↘ `FAILED` → `RETRY_SCHEDULED` → `QUEUED` (up to max_retries)
`RUNNING` ↘ `FAILED` → `DLQ` (after max_retries exhausted or FATAL error)

**Cancellation Flow:**
`RUNNING` / `QUEUED` → `CANCELLATION_REQUESTED` → `CANCELLED`

**Resume Flow:**
`PAUSED` → `RESUMING` → `RUNNING`

### Transitions Details:
- **PENDING → QUEUED**: Triggered by API/Scheduler. DB status updated. Job enqueued to Celery.
- **QUEUED → CLAIMED**: Triggered by Celery Worker picking up task. Sets `claimed_at`, `claimed_by_worker`. Lock acquired in Redis.
- **CLAIMED → RUNNING**: Triggered by worker starting first step. Emits `PROCESSING_JOB_STEP_STARTED`.
- **RUNNING → COMPLETED**: Triggered by worker finishing final step. Emits `PROCESSING_JOB_COMPLETED`, unlocks Redis.
- **RUNNING → FAILED**: Triggered by exception. Sets error code. Emits `PROCESSING_JOB_FAILED`.
- **FAILED → RETRY_SCHEDULED**: Evaluated by worker error handler if retryable. Sets `scheduled_at`.
- **FAILED → DLQ**: Evaluated by worker if max retries exceeded or FATAL. Moved to DLQ queue.
- **RUNNING → CANCELLATION_REQUESTED**: Triggered by API polling cancel signal.
- **CANCELLATION_REQUESTED → CANCELLED**: Worker cleans up and finalizes cancellation.

## 6. Redis Queue Topology

### 6.1 Celery Queue Definitions
Extending existing `celery_app.py` topology:
- `ingestion.critical`: Priority 3 jobs, concurrency 4 (Reserved for urgent, user-facing requests).
- `ingestion.high`: Priority 2 jobs, concurrency 8.
- `ingestion.normal`: Priority 1 jobs, concurrency 16 (Default processing).
- `ingestion.low`: Priority 0 jobs, concurrency 4 (Bulk background processing).
- `ingestion.dlq`: Dead letter jobs for manual review, concurrency 1.
- `ingestion.retry`: Scheduled retries awaiting re-enqueue, concurrency 2.

### 6.2 Redis Key Namespace
- `raguard:{tenant_id}:job:{job_id}:lock` — Distributed lock (TTL 600s)
- `raguard:{tenant_id}:job:{job_id}:idempotency` — Idempotency token (TTL 24h)
- `raguard:{tenant_id}:job:{job_id}:cancel_signal` — Cancellation flag (TTL 300s)
- `raguard:{tenant_id}:queue:priority` — Sorted set for priority scheduling
- `raguard:worker:heartbeat:{worker_id}` — Worker liveness (TTL 60s)
- `raguard:metrics:queue:{queue_name}:depth` — Queue depth counter
- `raguard:metrics:queue:{queue_name}:throughput` — Processing rate
- `raguard:dlq:{job_id}` — DLQ entry metadata

### 6.3 Distributed Locking Strategy
- **Acquisition**: `SET NX PX` (atomic)
- **Key**: `raguard:{tenant_id}:job:{job_id}:lock`
- **TTL**: 600 seconds (max job processing time for a single step).
- **Refresh**: Worker heartbeats every 30s extend TTL.
- **Release**: `finally` block in task ensures cleanup.
- **Fencing token**: Job version counter to prevent stale-lock split-brain issues.

## 7. Retry Policy & Exponential Backoff

### 7.1 Error Classification
- **RECOVERABLE**: Network timeout, DB transient, Redis blip, S3 transient → RETRY.
- **FATAL**: Corrupt file, schema violation, auth failure, missing entity → DLQ immediately.
- **PARTIAL**: Step partially succeeded, can resume from checkpoint → RESUME.

### 7.2 Exponential Backoff Formula
```python
retry_delay = min(BASE_DELAY * (2 ** retry_count) + jitter, MAX_DELAY)
```
- `BASE_DELAY` = 60 seconds
- `MAX_DELAY` = 3600 seconds (1 hour)
- `jitter` = random.uniform(0, BASE_DELAY)
- **Max retries per step**: 3 (configurable per step type)
- **Max total job retries**: 5

### 7.3 Per-Step Retry Limits
| Step | Max Retries | Error Codes → FATAL |
|------|-------------|--------------------|
| validation | 1 | CORRUPT, MIME_UNSUPPORTED |
| extraction | 2 | EXTRACT_001 |
| ocr | 3 | None (always retryable) |
| normalization | 2 | None |
| chunking | 3 | None |

## 8. Dead Letter Queue (DLQ)
- **Trigger**: max_retries exhausted OR FATAL error.
- **Entry**: Written to `ingestion.dlq` Celery queue AND PostgreSQL `processing_jobs.status=DLQ`.
- **Metadata**: reason, original_queue, all prior retry attempts, stack trace.
- **Review API**: `GET /api/v1/admin/dlq` — List DLQ entries with filtering.
- **Retry**: `POST /api/v1/admin/dlq/{job_id}/retry` — Re-enqueue with reset retry_count.
- **TTL**: Redis DLQ entries expire after 7 days. PostgreSQL records are permanent.
- **Multi-tenant isolation**: DLQ entries strictly scoped by `tenant_id`.

## 9. Idempotency
- **Idempotency Key**: `SHA-256(document_id + version_id + step_name)`
- **Mechanism**: Redis `SET NX` with TTL=24h before processing each step.
- **Hit**: If key exists → skip step, return cached result.
- **Coverage**: Prevents duplicate Celery task delivery (acks_late scenario), network retries, API duplicate submissions.
- **Content-hash**: Document content_hash checked before creating new ProcessingJob to avoid re-processing identical documents.

## 10. Job Priority Architecture
- **Levels**: CRITICAL(3), HIGH(2), NORMAL(1), LOW(0)
- **Source**: `BulkBatch.priority` field, user plan tier, workspace feature flag.
- **Routing**: `task_routes` in `celery_app` map to priority queues.
- **Worker sizing**: CRITICAL workers never preempted, LOW workers can be suspended.
- **Anti-Starvation**: LOW priority jobs escalated to NORMAL after 4 hours of waiting.

## 11. Worker Concurrency Model
- **Pools**: Per-queue Celery worker pools (separate OS processes).
- **Prefetch**: Multiplier set to 1 (`acks_late` requires prefetch=1 for exactly-once safety).
- **Heartbeat**: 30s intervals, registered in Redis.
- **Graceful shutdown**: `SIGTERM` triggers `task.request.called_directly` check, completes current step before terminating.
- **Memory limits**: 512MB per ingestion worker. OOM killer triggers task rejection which returns task to queue safely.

## 13. Cancellation & Resume

### 13.1 Cancellation Flow
1. API receives `DELETE /api/v1/jobs/{job_id}`
2. Service writes cancel signal to Redis: `raguard:{tenant_id}:job:{job_id}:cancel_signal`
3. Running worker polls cancel signal at step boundaries.
4. On detection: finish current atomic DB operation, set status=`CANCELLATION_REQUESTED`.
5. Worker transitions job to `CANCELLED`, emits `PROCESSING_JOB_CANCELLED` event.
6. Redis lock released.

### 13.2 Resume Flow
1. API receives `POST /api/v1/jobs/{job_id}/resume`
2. Service reads last `ProcessingJobStep` with status=`COMPLETED` to determine `resume_from_step`.
3. Sets `job.resume_from_step`, `job.status=QUEUED`.
4. Re-enqueues to appropriate priority queue.
5. Worker skips completed steps (checks `ProcessingJobStep` records), starts from `resume_from_step`.

## 16. Security
- **Multi-tenant isolation**: All job operations scoped strictly to `tenant_id` at the DB layer via RLS. Redis keys are heavily namespaced.
- **RBAC**: Only `ADMIN` or `OWNER` roles can access DLQ management and trigger global cancellations.
- **Transport**: Worker-to-Redis TLS encryption enforced.
- **Data Minimization**: Job payloads contain no PII — only UUIDs and operation metadata.
- **Auditing**: DLQ access and job mutations are logged to the `ProcessingJobAuditLog`.

## 17. Performance Considerations at Scale
Designed for millions of documents:
- **Horizontal Worker Scaling**: Kubernetes HPA dynamically scales worker pods based on queue depth metrics.
- **PostgreSQL Optimization**: `processing_jobs` table partitioned by `created_at` (monthly) and indexed on `tenant_id` for fast multi-tenant queries.
- **Redis Cluster**: Utilized for >1M concurrent jobs to shard locking and queue keys.
- **Batching**: DB writes for step metrics use 5-second flush intervals to reduce transaction overhead.
- **Anti-starvation**: LRU escalation for low-priority queues ensures throughput.
- **DLQ Purge Job**: Scheduled every 24h to archive DLQ entries older than 7 days to S3 cold storage.

## 18. Failure Scenarios & Recovery
1. **Worker process OOM**: `task_reject_on_worker_lost=True` ensures the job is explicitly rejected and returned to the queue, rather than silently lost.
2. **Redis broker failure**: Celery with persistence enabled falls back to PostgreSQL polling if broker becomes unavailable.
3. **PostgreSQL connection pool exhaustion**: Triggers exponential backoff on DB operations, avoiding complete worker crashes.
4. **S3 unavailable**: Extraction step fails with `RECOVERABLE` classification → automatically enters retry backoff loop.
5. **Stale lock (worker died holding lock)**: A separate health monitor detects expired heartbeats and force-releases locks, allowing tasks to be claimed by healthy workers.
6. **Network partition during acks_late**: Task may be re-delivered, but the `idempotency_key` strictly prevents duplicate work execution.
