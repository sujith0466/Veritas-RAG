## 1. Architectural Summary

The architecture specifications for F6.4 and F6.5 have been reviewed and approved. These designs successfully complete the asynchronous Knowledge Processing Pipeline (Epic 6) by connecting the existing chunking output to the vector storage foundation.

Crucially, **no new foundational architecture is required**. The designs correctly leverage the existing `ProcessingJob` framework, Celery task queues, Redis distributed locks, and the `EmbeddingProviderFactory` / `VectorStorageService` abstractions already present in the codebase.

## 2. Key Approvals & Strengths

### F6.4 (Embedding Generation Worker)
- **Zero-Call Idempotency:** The use of `content_hash` filtering before provider invocation correctly prevents duplicate API calls and reduces billing costs during retry storms.
- **Provider Sub-Batching:** The `EmbeddingManager` handles the provider-agnostic sub-batching logic (`batch_size=100`), correctly decoupling the Celery task scale from the provider API limits.
- **Cost Tracking:** The design correctly identifies `EmbeddingJob.step_metrics` as the location for storing token consumption and estimated costs per tenant.
- **Rate Limit Resilience:** Relying on the Redis `RateLimiter` to throw `RateLimitExceeded` for Celery countdown retries is the correct enterprise pattern for handling 429s without failing the job.

### F6.5 (Qdrant Vector Indexing)
- **Payload Integrity:** The strict enforcement of `tenant_id`, `document_id`, `document_version_id`, and `content_hash` via `VectorPointDTO` Pydantic validation guarantees multi-tenant isolation at the schema level.
- **Idempotent Upsert:** Combining `VectorIndexMetadata.status` guards with Qdrant's native UUID-based idempotent upserts ensures exact-once indexing semantics.
- **Memory Safety:** The design correctly enforces batched streaming of upserts (`VECTOR_UPSERT_BATCH_SIZE = 500`) with `wait=True` to prevent OOM kills on massive documents.
- **Version Lifecycle:** The invocation of `cleanup_old_versions_vectors()` after successful indexing guarantees that vector searches only return the active document version.

## 3. Discovered Codebase Divergences & Remediation Required

During the architectural audit, several existing codebase divergences were discovered that **must be addressed during implementation**.

### Divergence 1: Pipeline Listener Hardcoded Provider
**Issue:** `backend/tasks/listeners.py` currently hardcodes the embedding provider and model when listening to the `CHUNKING_COMPLETED` event:
```python
provider="local", model_name="all-MiniLM-L6-v2"
```
**Required Fix:** The listener must be updated to resolve the tenant's configured embedding provider from the `tenant_id` context (or `app_settings`), rather than hardcoding.

### Divergence 2: Collection Naming Strategy
**Issue:** `backend/vector_db/client.py` currently generates collections per-tenant:
```python
def collection_name(self, tenant_id: str) -> str:
    return f"{self.collection_prefix}_{tenant_id}"
```
While this works for small-scale deployments, it will cause collection exhaustion at enterprise scale. 
**Required Fix:** F6.5 implementation should refactor this to a dimension-based shared collection (e.g., `raguard_knowledge_1536`), as payload-level isolation is already strictly enforced by the `tenant_id` KEYWORD index.

### Divergence 3: Lock Acquisition Signature
**Issue:** `ProcessingJobService.claim_job` passes a Redis client instance to `acquire_lock`, but `cache/locks.py`'s `acquire_lock` signature expects `(lock_name, timeout, acquire_timeout, retry_delay)`.
**Required Fix:** Align the calling signature in `ProcessingJobService` to match the infrastructure definition.

### Divergence 4: Queue Contention
**Issue:** Both Chunking and Vector Sync use the `"ingestion"` queue.
**Recommendation:** While acceptable for Milestone 1, prepare to route Vector Sync to a dedicated `"indexing"` queue in Celery's `task_routes` to prevent slow Qdrant upserts from starving fast text extraction tasks.

The architecture for Epic 6 (F6.4 and F6.5) is robust, highly resilient, and strictly enforces the non-negotiable multi-tenant security requirements of RAGuard V2.
