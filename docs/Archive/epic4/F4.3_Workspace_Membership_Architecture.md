# F4.3 — Workspace Membership Management
## Enterprise Architecture & Design Blueprint

**Program:** RAGuard V2  
**Epic:** Epic 4 (User & Role Management)  
**Status:** Architecture Blueprint (Architect Reviewed)  

---

## 1. High-Level Architecture
Workspace Membership Management acts as the operational core for tenant access control. It maintains the lifecycle of `WorkspaceMember` entities, enabling Administrators and Owners to list, search, filter, update roles, and suspend/remove users. It strictly enforces Multi-Owner redundancy and prevents destructive operations on the final Owner.

---

## 2. Database & Entity Design

### Modifications Required
The existing `WorkspaceMember` model requires augmentation to support enterprise lifecycle tracking and status metrics.

**New Fields for `WorkspaceMember`:**
- `status`: String Enum (`ACTIVE`, `SUSPENDED`)
- `last_active_at`: DateTime (Nullable) - Updated via background asynchronous queue to avoid write-heavy locking on auth operations.
- `metadata`: JSONB (For custom attributes, titles, or SSO mappings).
- `invited_by_user_id`: UUID (Nullable) - Ties back to the original inviter for audit trails.
- `joined_at`: DateTime - Tracks when the invitation was accepted or user was provisioned.

**Alembic Migration Required:** `f4_3_workspace_membership_extensions`
- Add `status`, `last_active_at`, `metadata`, `invited_by_user_id`, `joined_at` columns.
- Update `is_deleted` (already present from `BaseModel`) logic for soft removals.
- Indexes: `(workspace_id, status)`, `(workspace_id, role)`.

## 3. Core Lifecycle & Workflows

### Member Status Flow
1. **PENDING:** Represented by the `WorkspaceInvitation` entity.
2. **ACTIVE:** Provisioned upon invitation acceptance. Full access per RBAC.
3. **SUSPENDED:** Administratively frozen. Tokens are flushed via Redis; no data deleted. Cannot access workspace, but retains history.
4. **REMOVED (Soft Delete):** `is_deleted = True`. Association is severed. User loses access, active sessions flushed. Audit logs and document attribution remain intact.

### Owner Protections (Workspace-Level Locking)
The system must guarantee at least one `ACTIVE` `OWNER` exists.
- **Rule:** If a workspace has `COUNT(role = 'OWNER' AND status = 'ACTIVE' AND is_deleted = false) == 1`:
  - The last Owner cannot change their own role.
  - The last Owner cannot be suspended or removed.
  - They cannot leave the workspace.
- **Concurrency Implementation:** To avoid multi-owner race conditions (e.g. two admins deleting two owners concurrently), a transaction must acquire a lock on the `Workspace` entity itself (`SELECT FOR UPDATE ON workspaces`) prior to validating the owner count, ensuring serialized mutation of owner roles.

## 4. API Design & Search/Filtering

**1. List / Search Members**
`GET /api/v1/workspaces/{workspace_id}/members`
- **Query Params:** `cursor` (keyset pagination identifier), `size`, `search` (email/name prefix), `role` (filter), `status` (filter).
- **Performance Implementation:** Keyset (cursor-based) pagination implemented over `(created_at, id)` to guarantee sub-10ms response times for workspaces with 50,000+ members, avoiding the offset penalty.
- **Response:** Paginated list of members joining `users` table for profile data and `WorkspaceMember` for membership metadata.

**2. Update Member Role**
`PATCH /api/v1/workspaces/{workspace_id}/members/{member_id}/role`
- **Validation:** Actor must have `ADMIN` or `OWNER` privileges. Cannot elevate someone to `OWNER` unless actor is `OWNER`. Cannot demote the last `OWNER`.

**3. Suspend / Restore Member**
`POST /api/v1/workspaces/{workspace_id}/members/{member_id}/suspend`
`POST /api/v1/workspaces/{workspace_id}/members/{member_id}/restore`
- **Action:** Flushes all active Redis sessions for this user within this workspace.

**4. Remove Member (Soft Delete)**
`DELETE /api/v1/workspaces/{workspace_id}/members/{member_id}`
- **Action:** Sets `is_deleted = true`. Flushes sessions.

**5. Bulk Operations**
`POST /api/v1/workspaces/{workspace_id}/members/bulk`
- **Audit Requirement:** Logs must represent a single `BULK_OPERATION` parent audit event linked to multiple individual child events to prevent spamming the audit log while maintaining granular traceability.

---

## 5. Caching & Performance Strategy

- **Session Caching:** A user's `WorkspaceMember` role and status are embedded directly in the JWT or cached in Redis under `user:{id}:workspace:{ws_id}:context` for ultra-fast middleware authorization checks.
- **Cache Invalidation:** When a role is updated or a user is suspended, the backend immediately deletes the Redis context key and publishes an invalidation event.
- **Search Indexes:** Trigram index (`pg_trgm`) on `users.email` and `users.full_name` combined with `workspace_id`.

---

## 6. Audit & Domain Events

**Domain Events Dispatched:**
- `WORKSPACE_MEMBER_ROLE_UPDATED`
- `WORKSPACE_MEMBER_SUSPENDED`
- `WORKSPACE_MEMBER_RESTORED`
- `WORKSPACE_MEMBER_REMOVED`
  - *Data Integrity Cleanup:* When `REMOVED` is fired, an asynchronous subscriber in the Document Service checks for user-assigned documents/API keys and executes tenant-configured fallback reassignments (e.g., transferring ownership to an Admin).

**Audit Log:**
All member state changes log the actor, target, old state, and new state.

---

## 7. Multi-Tenant Isolation & Security Review
- **Strict Tenant Scoping:** The `workspace_id` from the URL path must exactly match the JWT's authorized scopes. Repository queries unconditionally inject `workspace_id == current_ws_id`.
- **Privilege Escalation Prevention:** A user cannot update a role to a level higher than their own.
- **Session Flush:** Suspension/Removal guarantees immediate revocation by communicating with the Redis Session Store. JWTs rely on the fast-path Redis check (F2.3 architecture) to lock out the user on their very next API call.
