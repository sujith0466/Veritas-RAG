# F4.4 — RBAC Permission Enforcement
## Enterprise Architecture & Design Blueprint

**Program:** RAGuard V2  
**Epic:** Epic 4 (User & Role Management)  
**Status:** Architecture Blueprint (Architect Reviewed)  

---

## 1. High-Level Architecture
The RBAC (Role-Based Access Control) engine is a foundational security boundary that protects all platform endpoints and services. It evaluates a user's role against a deeply granular, hierarchical Permission Matrix covering 16+ core categories. It enforces authorization at both the API boundary (FastAPI Dependency Injection) and the Service Layer, utilizing ultra-fast Redis caching to minimize database roundtrips.

---

## 2. Role Definitions

### 2.1 Workspace Roles (Tenant-Scoped)
1. **OWNER:** Complete administrative and billing control. Cannot be removed if they are the last owner. Can delete the workspace.
2. **ADMIN:** High-level operational control (settings, users, documents). Cannot manage billing or delete the workspace.
3. **MEMBER:** Standard contributor. Can interact with Chat/RAG, upload documents, and view analytics. Cannot manage users or settings.
4. **VIEWER:** Read-only access. Can execute RAG queries and view dashboards, but cannot mutate data or documents.

### 2.2 Platform Roles (Global-Scoped)
1. **PLATFORM_ADMIN:** God-mode. Full access to all workspaces and platform configuration.
2. **PLATFORM_SUPPORT:** Read-only access to diagnostics, logs, and feature flags across tenants for debugging.
3. **PLATFORM_AUDITOR:** Strictly read-only access to compliance and security audit logs across tenants.

---

## 3. Permission Categories & Matrix Design

Permissions are formatted as `category:resource:action` (e.g., `documents:file:create`).

| Category | Example Permissions | Owner | Admin | Member | Viewer |
| :--- | :--- | :---: | :---: | :---: | :---: |
| **Workspace** | `workspace:delete`, `workspace:archive` | ✅ | ❌ | ❌ | ❌ |
| **Settings** | `settings:branding:update` | ✅ | ✅ | ❌ | ❌ |
| **Users** | `users:member:remove`, `users:role:update` | ✅ | ✅ | ❌ | ❌ |
| **Invitations** | `invitations:send`, `invitations:revoke` | ✅ | ✅ | ❌ | ❌ |
| **Documents** | `documents:file:upload`, `documents:delete` | ✅ | ✅ | ✅ | ❌ |
| **Chat & RAG** | `chat:session:create`, `rag:query:execute` | ✅ | ✅ | ✅ | ✅ |
| **Billing** | `billing:subscription:update` | ✅ | ❌ | ❌ | ❌ |
| **Audit Logs** | `audit:logs:read` | ✅ | ✅ | ❌ | ❌ |
| **API Keys** | `apikeys:generate`, `apikeys:revoke` | ✅ | ✅ | ❌ | ❌ |

*(Additional categories: Chunks, Embeddings, Feature Flags, Analytics, Integrations, etc., follow the same hierarchical escalation).*

## 4. Implementation Design

### 4.1 In-Memory Permission Pre-Computation
- **Performance Implementation:** To avoid recursively parsing hierarchical permissions dynamically on every API request, the permission inheritance tree (Role -> List of strings) is resolved once on application startup into an immutable flat dictionary/set matrix (`Set[str]`). Membership lookup executes in `O(1)` time.

### 4.2 Universal Authorization Dependency (API Layer)
FastAPI's dependency injection system guarantees that no endpoint goes unprotected.

```python
# API Endpoint Example
@router.post("/documents")
async def upload_document(
    file: UploadFile,
    auth: AuthorizationContext = Depends(require_permissions("documents:file:upload"))
):
    # Endpoint execution
```

### 4.3 Service Authorization Layer
For operations triggered internally or via background workers, the Service layer uses decorators or explicit checks to prevent bypass.

```python
# Service Method Example
@authorize("users:member:remove")
async def remove_member(self, context: UserContext, member_id: UUID):
    # Logic
```

### 4.4 Explicit Deny & Inheritance
- **Explicit Deny:** A user who is `SUSPENDED` receives an absolute explicit deny, overriding any role permissions.
- **Inheritance:** `OWNER` inherits all `ADMIN` permissions; `ADMIN` inherits `MEMBER`; `MEMBER` inherits `VIEWER`.

### 4.5 Redis Permission Caching & Race Condition Mitigation
- **The Problem:** Querying the DB for a user's role on every API request is a major bottleneck.
- **The Solution:** The user's role and status are cached in Redis under `auth:user:{user_id}:workspace:{workspace_id}` with a short `SETEX` TTL (e.g., 15 minutes).
- **Invalidation Race Mitigation:** When a membership role changes, a Pub/Sub event is broadcast across the cluster, and the Redis cache key is force-deleted. The next request reconstructs the cache. The short TTL acts as an upper-bound failsafe against network partition cache drift.

## 5. Security & Multi-Tenant Isolation
- **Resource-Based Authorization:** Permissions are strictly evaluated *within the context of a specific workspace*. A user may be an `OWNER` in Workspace A, but a `VIEWER` in Workspace B. The authorization engine mandates the `workspace_id` parameter.
- **Context-Bound API Key Degradation:** API Keys generated by a user inherit the creator's workspace role at execution time. If the creator is demoted from `ADMIN` to `VIEWER`, the API Key immediately degrades to `VIEWER` privileges, securing automated workflows against privilege drift.

---

## 6. Frontend Integration
The frontend application receives the user's evaluated role during login and workspace selection.
- **Permission Guards:** React components utilize an `<Authorized require="documents:file:upload">` wrapper to conditionally render UI elements (hiding buttons the user cannot click).
- **Route Protection:** React Router guards reject navigation to unauthorized pages (e.g., Settings) and redirect to a `403 Forbidden` page.

---

## 7. Future-Proofing & Extensibility
- **ABAC Compatibility:** The engine design allows for future Attribute-Based Access Control (e.g., "User can only edit documents *they* uploaded").
- **Custom Roles:** The matrix is decoupled from hardcoded enums at the evaluation level, allowing a future Epic to introduce `Custom Role` definitions (mapping arbitrary permission strings to a custom role ID).
