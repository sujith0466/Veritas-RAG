# F8.5 — SSE Timeout Handling Architecture (504 Fallback)

## 1. Executive Summary
Feature F8.5 addresses network reliability and provider latency during long-running LLM streaming. Currently, if an LLM provider (like V1 Engine) hangs mid-stream or fails to connect, the `LLMProviderManager` handles it based on retry loops, but the client experiences a hung connection or an abrupt drop. F8.5 establishes a strict timeout hierarchy and graceful fallback mechanisms for streaming requests.

## 2. Feature Scope & Objectives
*   **Strict Timeouts:** Implement read and connect timeouts on all outbound SSE provider calls.
*   **Mid-Stream Abort Handling:** Gracefully handle streams that hang after yielding partial data.
*   **Client Communication:** Send explicit error events to the client instead of silently dropping the connection.
*   **Fallback Activation:** If the primary provider times out before generating the first chunk, trigger fallback to the secondary provider.

## 3. Existing Infrastructure Reuse
*   `backend/ai/manager.py`: `LLMProviderManager.stream()` failover logic.
*   `backend/ai/providers/v1_engine/client.py`: httpx timeout configuration.
*   `backend/modules/generation/services/streaming_generation_service.py`: Error chunk yielding logic.

## 4. Architectural Design

### 4.1. Timeout Definitions
*   **Connection Timeout:** 5.0 seconds. If a provider cannot be reached, fail fast.
*   **Time-To-First-Token (TTFT) Timeout:** 10.0 seconds. If connected, but no data is received within this window, abort and failover.
*   **Inter-Token Timeout (Read Timeout):** 15.0 seconds. If the stream hangs mid-generation for more than 15s, abort.

### 4.2. Failover Logic (Pre-Stream vs. Mid-Stream)
The `LLMProviderManager` already differentiates between pre-stream and mid-stream failures using the `chunks_yielded` counter.

*   **Pre-Stream (chunks_yielded == 0):**
    *   If TTFT timeout occurs, catch `httpx.ReadTimeout`.
    *   Record failure in in-memory metrics.
    *   Move to the next provider in the `priority_list` (e.g., OpenRouter -> Gemini).
*   **Mid-Stream (chunks_yielded > 0):**
    *   If Inter-Token timeout occurs, the system **cannot** seamlessly failover because the client already has half an answer from Model A. Splicing Model B's output is architecturally unsound.
    *   Action: Raise `V1EngineStreamAbortError` or `LLMProviderException`.

### 4.3. Client-Facing Error Reporting
When a mid-stream timeout occurs and bubbles up to `StreamingGroundedGenerationService`, it currently yields a generic error message string.
We will standardize this via the F8.3 SSE Bridge:

```python
yield SSEMessageDTO(
    event="error",
    data='{"code": 504, "message": "The AI provider timed out mid-generation.", "retry_after": 5}'
).to_sse_string()

yield SSEMessageDTO(event="done", data="{}").to_sse_string()
```
This allows the frontend client to display the partial text alongside a UI warning: *"Generation was interrupted due to a network timeout."*

### 4.4. V1 Engine Client Enhancements
The `V1EngineClient` utilizes `httpx.AsyncClient`. The timeouts are configured via `httpx.Timeout`.
In the `_producer()` task, we will explicitly catch `httpx.ReadTimeout` and `httpx.ConnectTimeout`.

## 5. Circuit Breaker Integration
*   Timeout events MUST count as failures in the `CircuitBreakerEngine`.
*   If a provider hits the `failure_threshold` (e.g., 5 timeouts in 60 seconds), the circuit trips to `OPEN`.
*   Subsequent requests will immediately failover without waiting for the timeout, protecting system resources and improving user experience during provider outages.

## 6. Observability
*   Emit `AI_WRAPPER_REQUEST_FAILED` with the specific timeout phase (e.g., `error_type: "ttft_timeout"` vs `error_type: "inter_token_timeout"`).
*   Ensure these metrics propagate to the Prometheus monitoring endpoints.
