## 1. Executive Summary

Epic 8 delivers the **AI Platform Layer** — the final orchestration tier that sits between the RAGuard V2 REST API and all AI inference providers. It consists of two tightly coupled features:

| Feature | Component | Role |
|---------|-----------|------|
| **F8.1** | `AIWrapperService` | Canonical AI orchestration entry point: workspace validation, namespace binding, context injection, prompt governance, streaming orchestration, resilience, and observability |
| **F8.2** | `V1EngineClient` + `V1EngineProvider` | Production-hardened mTLS HTTP client for the RAGuard V1 internal AI Engine; plugs into `LLMProviderManager` as a first-tier inference provider |

Together, these features resolve the primary architectural debts of the prior `ChatOrchestrator` design:
- **Fragmented orchestration** → replaced by a single, deterministic 14-step lifecycle in `AIWrapperService`
- **Missing multi-tenant namespace binding** → resolved by `NamespaceResolver` with Redis cache
- **No internal engine client standard** → resolved by `V1EngineClient` with mTLS, signing, pooling, and circuit breaking
- **No unified retry/confidence loop** → resolved by `RetryStateMachine` + `ConfidenceEngine` integration in F8.1

Neither F8.1 nor F8.2 introduces breaking changes to any existing interface, database schema, or middleware contract.

## 4. End-to-End Request Flow

### 4.1 Full 14-Step Lifecycle (Streaming Path)

```text
Frontend POST /api/v1/ai/stream
  │
  ├─ [MIDDLEWARE] CORS → CorrelationID → JWT → Security → Logging
  │
  ├─ Step 1:  Request Validation & RBAC Gate
  │           • Validate AIWrapperRequest schema (Pydantic)
  │           • JWT tenant_id override of request body tenant_id
  │           • Query max 2000 chars; control chars stripped
  │
  ├─ Step 2:  Workspace Validation (6-check gate)
  │           • Workspace exists + ACTIVE
  │           • User in WorkspaceMember
  │           • ≥1 READY document in KB
  │           • ai_enabled feature flag = true
  │           • Per-tenant + per-user rate limit check (Redis)
  │
  ├─ Step 3:  Conversation Context Loading
  │           • ChatRepository: last 5 messages for session_id
  │           • Token budget check: history ≤ 20% of max_answer_tokens
  │           • Query enhanced with prior user turn for retrieval
  │
  ├─ Step 4:  Qdrant Namespace Binding
  │           • Redis cache check: raguard:{tenant_id}:namespace:binding
  │           • Cache miss: NamespaceResolver constructs + validates collection
  │           • NamespaceBinding stored with TTL=300s
  │
  ├─ Step 5:  Query Preprocessing
  │           • PromptGuard.sanitize_query()
  │           • Optional: QueryRewriter (if retry loop active)
  │
  ├─ Step 6:  Hybrid Retrieval (timeout: 5s)
  │           • RetrievalOrchestrator with resolved namespace
  │           • Dense + sparse fusion via FusionEngine
  │
  ├─ Step 7:  Confidence Evaluation (timeout: 1s)
  │           • ConfidenceEngine.evaluate(retrieval_results)
  │           • Score ≥ 85 → PROCEED; 70-84 → CLARIFY; < 70 → RETRY
  │
  ├─ Step 8:  Retry/Rewrite Loop (max 3 iterations)
  │           • RetryStateMachine: RETRYING → QueryRewriter → Step 6
  │           • Abort if improvement delta < 2.0 or score < 40
  │
  ├─ Step 9:  Prompt Construction
  │           • System template + workspace variables + custom instructions
  │           • Evidence block: [1] chunk1... [N] chunkN
  │           • Token truncation: history first, then evidence if needed
  │           • Grounding instruction injected (immutable)
  │
  ├─ Step 10: Streaming Generation via LLMProviderManager (timeout: 25s)
  │           │
  │           ├─ [Primary] V1EngineProvider → V1EngineClient
  │           │       • mTLS handshake (pool: reuse existing connection)
  │           │       • HMAC-SHA256 signing (method+path+timestamp+body)
  │           │       • Workspace headers: X-Tenant-ID, X-Workspace-ID
  │           │       • W3C traceparent propagation
  │           │       • POST /v1/generate/stream → SSE
  │           │       • Bounded queue (100 items) backpressure
  │           │       • Heartbeat frames silently discarded
  │           │
  │           └─ [Fallback] OpenRouterProvider / GeminiProvider
  │                   • Triggered if V1 circuit OPEN or unavailable
  │
  ├─ Step 11: Citation Extraction + Grounding Check
  │           • CitationExtractor.extract([N] markers)
  │           • PromptGuard.verify_grounding(answer, evidence)
  │           • is_fully_grounded = True/False
  │
  ├─ Step 12: Reliability Scoring
  │           • ReliabilityGateway.score(answer, citations, retrieval)
  │           • Composite 0.0–1.0 reliability_score
  │
  ├─ Step 13: Domain Event Publishing
  │           • EventDispatcher: ai_wrapper.request_completed
  │           • ai_wrapper.retrieval_completed (emitted at Step 6)
  │
  └─ Step 14: Audit Logging
              • LLMAuditService.log(prompt, answer, citations, metadata)
              • PII policy: plaintext stored in audit only; never in app logs
```

### 4.2 V1 Engine Request Flow (F8.2 Detail)

```text
V1EngineClient.stream(request)
  │
  ├─ 1. Circuit Breaker check: v1_engine_client → OPEN? → raise CircuitOpenError
  ├─ 2. Validate tenant_id as UUID (raise InvalidRequestError if invalid)
  ├─ 3. Build headers: X-Tenant-ID, X-Workspace-ID, X-Correlation-ID,
  │      X-Request-ID (uuid4), X-Request-Timestamp, X-Client-Version,
  │      Authorization, traceparent
  ├─ 4. Compute HMAC-SHA256 signature → inject X-Request-Signature
  ├─ 5. OTel span start: v1_engine_client.stream
  ├─ 6. httpx.AsyncClient.stream("POST", "/v1/generate/stream") [mTLS pool]
  │      ├─ Attempt loop (max 4 total):
  │      │     ├─ Send request
  │      │     ├─ Response 200: Parse SSE, yield V1EngineStreamChunk
  │      │     ├─ Response 429: Read Retry-After, sleep, retry
  │      │     ├─ Response 5xx: Exponential backoff, retry
  │      │     ├─ ConnectError: Backoff, retry → CircuitBreaker.record_failure()
  │      │     ├─ TLS Error: raise V1TLSError (non-retryable)
  │      │     └─ Auth Error (401/403): raise V1AuthenticationError (non-retryable)
  │      └─ All retries exhausted → raise V1EngineUnavailableError
  ├─ 7. OTel span end with outcome attribute
  └─ 8. CircuitBreaker.record_success() / record_failure()
```

## 6. Composite Resilience Model

### 6.1 Three-Tier Failover Chain

```text
Tier 1: V1EngineProvider (RAGuard V1 Internal Engine)
    ↓ [CircuitOpenError / V1EngineUnavailableError / V1TLSError]
Tier 2: OpenRouterProvider (External — OpenRouter API)
    ↓ [LLMProviderException / Circuit OPEN]
Tier 3: GeminiProvider (External — Google Gemini API)
    ↓ [All providers exhausted]
Error: AI_010 (AllProvidersDown) → HTTP 502
```

### 6.2 Retry State Machine

```text
INITIAL
  ↓ (Step 6: Retrieval)
RETRIEVED
  ↓ (Step 7: Confidence evaluation)
CONFIDENCE_EVALUATED
  ├─ Score ≥ 85 (PROCEED)    → GENERATING → COMPLETED
  ├─ Score 70-84 (CLARIFY)   → GENERATING (with clarification prefix) → COMPLETED
  ├─ Score < 70 (RETRY)      → RETRYING (QueryRewriter → back to RETRIEVED)
  │     Retry budget: 3 attempts
  │     Abort if: score < 40 OR improvement delta < 2.0
  └─ Score < 40 (ABORT)      → ABORTED (emit error chunk)
```

### 6.3 Timeout Hierarchy

| Level | Scope | Duration | On Trigger |
|-------|-------|----------|------------|
| L1 — Retrieval | Steps 6-7 | 5s | Raise AI_009 |
| L1 — Confidence | Step 7 only | 1s | Skip retry, proceed |
| L1 — Generation | Step 10 | 25s | Yield timeout chunk |
| L2 — Wall Clock | Steps 1-14 | 35s | Yield timeout chunk |
| L3 — Watchdog | Token silence | 10s | Abort stream |

### 6.4 Circuit Breaker Matrix

| Circuit Key | Engine | Threshold | Recovery | On OPEN |
|-------------|--------|-----------|----------|---------|
| `retrieval` | RetrievalOrchestrator | Epic 7 defaults | Epic 7 defaults | Skip retrieval |
| `v1_engine_client` | V1EngineClient | 5 failures / 60s | 30s HALF_OPEN | Failover to cloud |
| `openrouter` | OpenRouterProvider | Epic 7 defaults | Epic 7 defaults | Failover to Gemini |
| `gemini` | GeminiProvider | Epic 7 defaults | Epic 7 defaults | AI_010 error |

## 7. Unified Security Posture

### 7.1 Five Security Pillars

#### Pillar 1: Identity & Authorization
- JWT validation by `JWTAuthenticationMiddleware` (unchanged)
- `tenant_id` extracted exclusively from JWT claim — never from request body
- `WorkspaceMember` table checked on every AI request (Step 2)
- `ai_enabled` feature flag enforced per-workspace

#### Pillar 2: Transport Security
- Internal V1 Engine: mTLS (TLS 1.3), both parties authenticate with certificates
- External providers (OpenRouter, Gemini): HTTPS (TLS 1.3, existing pattern)
- All Redis connections: TLS (existing `backend/core/config/` settings)

#### Pillar 3: Payload Integrity
- HMAC-SHA256 signing on all V1 Engine calls (method + path + timestamp + body hash)
- 60-second replay window enforced server-side
- Dual-key rotation window (300s) for zero-drop key rotation

#### Pillar 4: Prompt Injection Prevention
- `PromptGuard.sanitize_and_format_evidence()` applied to all retrieved chunks
- Known injection patterns stripped (role-switching, instruction override)
- Query length hard-capped at 2,000 characters
- Control characters stripped from all inputs

#### Pillar 5: Multi-Tenant Isolation
- Qdrant namespace: `raguard_knowledge_{tenant_id}` — constructed from JWT, not user input
- Redis keys: `raguard:{tenant_id}:...` — namespaced on all cache operations
- V1 Engine headers: `X-Tenant-ID` validated as UUID before injection
- PostgreSQL: All queries include `tenant_id` filter

### 7.2 PII & Audit Policy

| Data | Application Logs | Redis | LLMAuditService DB |
|------|-----------------|-------|-------------------|
| User query (plaintext) | SHA-256 only | Never stored | ✅ Encrypted at rest |
| Generated answer | Never | Never | ✅ Encrypted at rest |
| Evidence block | Never | Never | ✅ Encrypted at rest |
| Assembled system prompt | Never | Never | ✅ Encrypted at rest |
| Citation metadata | Safe (IDs only) | Never | ✅ Stored |

## 14. Open Questions for User Decision

> [!IMPORTANT]
> The following items require explicit user decisions before implementation can begin. No assumptions have been made.

### Q1: V1 Engine Availability
**Question:** Is the RAGuard V1 AI Engine already deployed and reachable at an internal Kubernetes service address?

- **Option A:** Yes — provide `V1_ENGINE_BASE_URL` and mTLS certificate paths
- **Option B:** Not yet — F8.2 should be implemented with `V1_ENGINE_ENABLED=false` by default; V1 Engine client remains dormant until manually enabled
- **Impact:** Affects startup negotiation behavior and integration test scope

### Q2: ChatOrchestrator Migration Timing
**Question:** Should `ChatOrchestrator.stream_chat()` be refactored to delegate to `AIWrapperService` immediately in Epic 8, or should it remain independent until a dedicated migration sprint?

- **Option A:** Migrate immediately — single implementation, dual entry points
- **Option B:** Leave `ChatOrchestrator` independent — `AIWrapperService` is a net-new path only
- **Impact:** Affects implementation scope and test coverage

### Q3: Namespace Resolver Scope
**Question:** Should `NamespaceResolver` support multi-collection workspaces (one workspace → multiple Qdrant collections), or is the 1:1 mapping `raguard_knowledge_{tenant_id}` the final design?

- **Option A:** 1:1 (current design) — simpler; tenant = collection
- **Option B:** 1:N — workspace can have a dedicated sub-collection (per workspace, not per tenant)
- **Impact:** Significant schema and resolver complexity difference

### Q4: Rate Limiter Defaults
**Question:** The architecture specifies 60 requests/minute per tenant and 20 requests/minute per user as defaults. Are these the correct production limits for your use case?

- Provide: Desired tenant-level and user-level rate limit values
- **Impact:** `RateLimiter` configuration only; no architecture change

### Q5: Semantic Chunking in Retry Loop
**Question:** During the `QueryRewriter` retry loop, should the rewritten query trigger a full re-retrieval (current design), or should semantic re-ranking of the existing result set be attempted first (cheaper but less accurate)?

- **Option A:** Full re-retrieval (current design) — accuracy-first
- **Option B:** Re-rank existing results first, fall back to re-retrieval if still low confidence — cost-optimized
- **Impact:** `RetryStateMachine` implementation and latency budget
