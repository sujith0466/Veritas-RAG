# F8.2 V1 Internal API Client Architecture

## 1. Executive Summary

F8.2 delivers the `V1EngineClient` — a production-hardened enterprise HTTP client for communicating with the RAGuard V1 AI Engine (internal service). It is the transport layer underneath `AIWrapperService` (F8.1). It implements mutual TLS (mTLS), connection pooling, retry policy, circuit breaking, streaming support, distributed tracing, request signing, workspace propagation, health checking, and version negotiation. It abstracts all V1 Engine communication behind a clean interface, enabling F8.1 to remain provider-agnostic.

## 2. Feature Scope

This architecture encompasses the following deliverables:
- **mTLS Client Integration**: Certificate-based mutual authentication for internal service-to-service communication.
- **Connection Pool Management**: High-performance HTTP/2 connection pooling with persistent keepalive tuning.
- **Intelligent Retry Engine**: Granular retry strategies with jittered exponential backoff based on HTTP status codes.
- **Resiliency Integration**: Deep integration with the existing `CircuitBreakerEngine` to prevent cascading failures.
- **Request Cryptographic Signing**: HMAC-SHA256 signature injection to prevent replay attacks and ensure request authenticity.
- **Streaming Response Handler**: Robust SSE (Server-Sent Events) parser for real-time generative responses with mid-stream abort detection.
- **Health and Version Negotiation**: Active health probing and semantic capability negotiation on startup.
- **Context Propagation**: Transparent injection of workspace, tenant, and W3C trace contexts.
- **Provider Abstraction**: A `V1EngineProvider` implementation that seamlessly fits into the existing `LLMProviderManager` failover priority list.

## 3. Why a Dedicated Internal Client

The existing `OpenRouterProvider` uses `httpx.AsyncClient` but is fundamentally unsuited for the V1 Engine internal communications due to the following architectural gaps:

| Gap | Existing OpenRouterProvider | V1EngineClient Requirement |
|-----|---------------------------|-----------------------------|
| mTLS | Not supported | Mandatory for internal mesh |
| Request signing | Static Bearer token only | HMAC-SHA256 payload signing |
| Workspace propagation | Not implemented | `X-Tenant-ID`, `X-Workspace-ID` required |
| Version negotiation | No startup handshake | Semantic capability check on startup |
| Connection pool tuning | Not tuned for internal mesh | 50 max connections, HTTP/2 multiplexing |
| Correlation ID injection | Missing | W3C `traceparent` propagation required |
| Retry semantics | External API rate limits | GPU-backed engine failure patterns |
| Health check integration | None | 30s background polling + circuit integration |

## 4. V1 Engine Protocol Specification

This section defines the complete wire protocol for communication between the V2 Backend and the V1 Engine.

### 4.1 Base URL

- `V1_ENGINE_BASE_URL`: Configured via environment variable.
- **Example**: `https://v1-engine.internal.raguard.svc.cluster.local:8443`
- **DNS**: Internal DNS resolution via Kubernetes service discovery.

### 4.2 Endpoints Consumed

| Endpoint | Method | Description | Streaming |
| :--- | :--- | :--- | :--- |
| `/v1/generate` | POST | Non-streaming text generation | No |
| `/v1/generate/stream` | POST | SSE streaming text generation | Yes |

| `/v1/version` | GET | Engine version & available capabilities | No |
| `/v1/models` | GET | Available models list | No |

### 4.3 Request Headers (Required on Every Call)

| Header | Value | Purpose |
| :--- | :--- | :--- |
| `X-Tenant-ID` | `{tenant_id}` | Workspace isolation and logical partitioning |

| `X-Correlation-ID` | `{correlation_id}` | Distributed tracing and log stitching |

**Non-Streaming JSON:**
```

**Streaming SSE:**
```

```

```

## 5. mTLS Architecture

Security is enforced at the transport layer via Mutual TLS.

### 5.1 Certificate Infrastructure

| Artifact | Environment Variable | Format | Notes |
|----------|---------------------|--------|-------|
| Client certificate | `V1_ENGINE_CLIENT_CERT_PATH` | PEM | Issued by RAGuard internal CA |
| Client private key | `V1_ENGINE_CLIENT_KEY_PATH` | PEM | Stored as Kubernetes Secret |
| CA certificate | `V1_ENGINE_CA_CERT_PATH` | PEM | Used for server cert validation |

- **Certificate validity**: Maximum 90 days; automated rotation via `cert-manager`.
- **Storage**: Kubernetes Secrets mounted as read-only volumes at runtime.

### 5.2 TLS Configuration

| Parameter | Value |
|-----------|-------|
| Minimum TLS version | TLS 1.3 (TLS 1.2 fallback permitted for legacy nodes only) |
| Cipher suites | `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256` |
| Server name validation | Enforced — SAN must match `v1-engine.internal.raguard.svc.cluster.local` |
| Certificate revocation | OCSP stapling checked at connection establishment |
| Client certificate | Presented proactively on every connection |

### 5.3 mTLS Validation Flow

```text
V2 Backend (client)                V1 Engine (server)
    │                                    │
    ├─ ClientHello + Extensions ────────▶│
    │◀─ ServerHello + ServerCert ────────┤
    ├─ Verify ServerCert (CA cert) ──────┤ (internal, no network)
    │◀─ CertificateRequest ──────────────┤
    ├─ ClientCert + CertificateVerify ──▶│
    │                                    ├─ Verify ClientCert (CA cert)
    │◀─ Finished ────────────────────────┤
    ├─ Application data (encrypted) ────▶│
```

### 5.4 Certificate Hot Reloading

To support zero-downtime rotation:
1. A file watcher monitors the certificate and key paths.
2. On file change: A new SSL context is rebuilt in-process.
3. Active connections continue using the old context until completion.
4. All new connections drawn from the pool use the new SSL context.
5. No restart required. No dropped connections.

## 6. Connection Pooling

To minimize TLS handshake latency, a robust connection pool is established at service startup.

| Parameter | Value | Config Variable |
|-----------|-------|----------------|
| Protocol | HTTP/2 multiplexing | — |
| Max connections per host | 50 | `V1_ENGINE_MAX_CONNECTIONS` |
| Max keepalive connections | 20 | `V1_ENGINE_MAX_KEEPALIVE` |
| Keepalive expiry | 60 seconds | Hardcoded |
| DNS cache TTL | 30 seconds | Hardcoded |

**Implementation Pattern:**
- Utilizes `httpx.AsyncClient` configured with `httpx.Limits(max_connections=50, max_keepalive_connections=20, keepalive_expiry=60)`.
- **Singleton client**: One `AsyncClient` instance per event loop — mirrors the existing `AsyncQdrantClient` singleton pattern from `backend/vector_db/client.py`.
- **Lifecycle**: Initialized during FastAPI lifespan `startup` event; gracefully closed during `shutdown` event via `client.aclose()`.

## 7. Retry Policy

A granular retry engine maps V1 Engine responses to specific recovery actions.

### 7.1 Retryable Errors

| HTTP Status | Error Type | Action | Max Attempts |
| :--- | :--- | :--- | :--- |
| 408 | Request Timeout | Retry with backoff | 3 |
| 429 | Rate Limited | Retry after `Retry-After` header | 3 |
| 500 | Server Error | Retry with backoff | 2 |
| 502 | Bad Gateway | Retry immediately, then backoff | 3 |
| 503 | Service Unavailable | Retry after `Retry-After` | 3 |
| 504 | Gateway Timeout | Retry with backoff | 3 |
| Connection Reset | TCP RST | Retry immediately | 2 |
| DNS Failure | NXDOMAIN | **NOT retried** (fatal) | 0 |
| Auth Failure | 401/403 | **NOT retried** (fatal) | 0 |
| TLS Error | Handshake failure | **NOT retried** (cert issue) | 0 |

### 7.2 Backoff Formula

Jittered exponential backoff:
```
delay = min(BASE_DELAY_MS * (2 ** attempt) + jitter, MAX_DELAY_MS)
```

| Parameter | Value |
|-----------|-------|
| `BASE_DELAY_MS` | 500ms |
| `MAX_DELAY_MS` | 10,000ms (10 seconds) |
| `jitter` | `random.uniform(0, BASE_DELAY_MS / 2)` |

**Backoff schedule per attempt:**

| Attempt | Base Delay | Max Jitter | Worst Case |
|---------|-----------|-----------|------------|
| 1 | 500ms | 250ms | 750ms |
| 2 | 1,000ms | 250ms | 1,250ms |
| 3 | 2,000ms | 250ms | 2,250ms |
| 4 (if applicable) | 4,000ms | 250ms | 4,250ms |

### 7.3 Retry Budget

| Parameter | Value | Config Variable |
|-----------|-------|----------------|
| Global retry budget | 3 additional attempts (4 total) | Hardcoded |
| Per-attempt timeout | 10 seconds | `V1_ENGINE_PER_ATTEMPT_TIMEOUT` |
| Total budget timeout | 30 seconds | `V1_ENGINE_TOTAL_TIMEOUT` |
| Streaming credit | 1 credit consumed per aborted stream | Hardcoded |

## 8. Circuit Breaker Integration

The V1 Engine client is fully integrated with the existing `CircuitBreakerEngine`.

- **Reuses**: `backend/modules/reliability/circuit_breaker/engine.py` (EXISTING — zero modifications).
- **Circuit key**: `v1_engine_client` (isolated from all other circuit breakers).
- **Failure threshold**: 5 failures within a 60-second sliding window → transition to **OPEN**.
- **Recovery timeout**: After 30 seconds in OPEN → transition to **HALF_OPEN** for a probe request.
- **On OPEN**: `V1EngineClient` immediately raises `CircuitOpenError` → F8.1 fallbacks to Gemini/OpenRouter via `LLMProviderManager`.
- **Probe success**: HALF_OPEN → CLOSED. Probe failure: HALF_OPEN → OPEN (restart 30s timer).

### 8.1 Circuit State Transitions

```text
CLOSED ─── 5 failures in 60s ──▶ OPEN
OPEN   ─── 30s elapsed ─────────▶ HALF_OPEN
HALF_OPEN ─ probe success ───────▶ CLOSED
HALF_OPEN ─ probe failure ───────▶ OPEN (reset timer)
```

### 8.2 Aggressive Health-Triggered Opening

If `GET /v1/health` returns `"unhealthy"` for 2+ consecutive 30-second checks, the circuit breaker immediately transitions to OPEN without waiting for failure threshold.

## 9. Request Signing

Every request to the V1 Engine is cryptographically signed to ensure authenticity and prevent replay attacks.

### 9.1 Signature Construction

The signature covers:
```
payload = f"{method}\n{path}\n{timestamp}\n{sha256(body)}"
signature = HMAC-SHA256(payload, signing_key)
```

| Element | Value | Notes |
|---------|-------|-------|
| `method` | HTTP verb (`POST`, `GET`) | Uppercase |
| `path` | URL path (e.g., `/v1/generate`) | No query string |
| `timestamp` | Unix epoch seconds | Injected as `X-Request-Timestamp` header |
| `sha256(body)` | SHA-256 hex digest of request body | Empty string if no body |
| `signing_key` | 256-bit symmetric key | From `V1_ENGINE_SIGNING_KEY` env var |

### 9.2 Header Injection

```
X-Request-Signature: HMAC-SHA256={hex_signature}
X-Request-Timestamp: {unix_epoch_seconds}
```

### 9.3 Replay Protection

- V1 Engine rejects any request where `abs(now - timestamp) > 60s`.
- Duplicate `X-Request-ID` values within the 60s window are rejected.

### 9.4 Signing Key Rotation

- New key provisioned via Kubernetes Secret rotation.
- **Dual-key verification window**: 300 seconds during which BOTH old and new keys are accepted server-side.
- After 300s: Old key decommissioned. Zero dropped requests.

## 10. Streaming Support

The client handles long-lived generative SSE streams with backpressure, cancellation, and mid-stream error recovery.

### 10.1 SSE Parsing

```text
async for line in response.aiter_lines():
    if line.startswith("data: "):
        raw = line[6:]
        if raw == "[DONE]": break
        chunk = V1EngineStreamChunk.model_validate_json(raw)
        await queue.put(chunk)
    elif line.startswith("data: {\"type\": \"heartbeat\"}"):
        continue  # Silently discard heartbeat frames
```

### 10.2 Backpressure

- An `asyncio.Queue` bounded at 100 items sits between the SSE parser and the consumer.
- If the queue is full, the producer (`aiter_lines`) pauses via `await queue.put()` natural blocking.
- Prevents memory bloat for slow consumers (e.g., slow frontend connections).

### 10.3 Cancellation Handling

- `asyncio.CancelledError` is caught within the stream generator.
- On cancellation: Underlying `httpx` response stream is explicitly closed via `response.aclose()`.
- A `V1EngineStreamAbortError` is raised to notify the caller.

### 10.4 Mid-Stream Abort Policy

| Scenario | Chunks Emitted | Action |
|----------|---------------|--------|
| Stream drops before first chunk | 0 | Retryable — consume 1 retry credit |
| Stream drops after N>0 chunks | N | Non-retryable — partial response delivered |

Non-retryable mid-stream aborts surface as a final error chunk to the user rather than re-attempting, to avoid duplicate text in the response.

### 10.5 V1EngineStreamChunk DTO

| Field | Type | Description |
|-------|------|-------------|
| `text_delta` | `str` | Incremental text token(s) |
| `is_final` | `bool` | True on last chunk |
| `chunk_index` | `int` | Sequential chunk number |
| `model_used` | `str \| None` | Populated on final chunk only |
| `type` | `str \| None` | `"heartbeat"` for keep-alive frames |

Maps cleanly to the existing `StreamingGenerationChunkDTO` shape consumed by F8.1.

## 11. Health Checking

Active health probing ensures the V1 Engine is available before routing traffic.

### 11.1 Health Check Protocol

- **Endpoint**: `GET /v1/health`
- **Expected response**: `{"status": "healthy"|"degraded"|"unhealthy", "version": "...", "uptime_seconds": 1234, "model_loaded": "..."}`
- **Poll frequency**: Every 30 seconds via a background `asyncio.Task`.
- **Result caching**: Redis at `raguard:v1_engine:health_cache`, TTL=30s.
- **Cache purpose**: Allows synchronous health aggregation at `GET /api/v1/ai/health` without blocking on V1 Engine response.

### 11.2 Health State Machine

```text
                  ┌──────────────────────────────────────┐
                  │         HealthPoller (30s interval)   │
                  └──────────────────┬───────────────────┘
                                     │
                  ┌──────────────────▼───────────────────┐
                  │         V1 Health Response            │
                  ├─────────────────────────────────────┤
                  │  "healthy"   → Update Redis OK        │
                  │  "degraded"  → Update Redis WARNING   │
                  │  "unhealthy" → Count consecutive ≥ 2 │
                  │               → Force OPEN Circuit    │
                  └─────────────────────────────────────┘
```

### 11.3 Health Integration with F8.1

`GET /api/v1/ai/health` (F8.1) aggregates:
1. V1 Engine health (from Redis cache)
2. `LLMProviderManager` cloud provider health
3. Qdrant client health
4. Redis client health

## 12. Version Negotiation

Semantic versioning guarantees compatibility between the V2 Backend and V1 Engine before any traffic is routed.

### 12.1 Startup Negotiation Flow

```text
FastAPI lifespan startup
  → V1EngineClient.initialize()
      ├─ GET /v1/version
      │   → {"version": "1.x.x", "api_version": "v1",
      │       "capabilities": ["streaming", "mTLS", "citations"]}
      ├─ Validate semantic version ≥ V1_ENGINE_MIN_VERSION (default: "1.0.0")
      ├─ Validate required capabilities present: ["streaming", "mTLS"]
      ├─ Store negotiated_version in V1EngineClient._negotiated_version
      └─ On failure: raise V1EngineVersionMismatchError
           → Log critical alert
           → Disable V1 provider in LLMProviderManager
           → Continue startup with cloud providers only
```

### 12.2 Required Capabilities

| Capability | Required? | Notes |
|-----------|----------|-------|
| `streaming` | Yes | F8.1 requires SSE streaming |
| `mTLS` | Yes | Internal security requirement |
| `citations` | No | Optional — grounding enhancement |
| `reranking` | No | Optional — future use |

## 13. Workspace Propagation

Logical isolation and auditing require strict propagation of tenant metadata on every V1 Engine call.

### 13.1 Header Propagation

Every V1 Engine request carries:
```
X-Tenant-ID: {tenant_id}        (from JWT claim, validated as UUID)
X-Workspace-ID: {workspace_id}  (from AIWrapperRequest)
```

### 13.2 Extraction Rules

- `tenant_id`: Extracted from `AIWrapperRequest.tenant_id` (which was itself sourced from the JWT claim, not the user-supplied request body).
- `workspace_id`: Extracted from `AIWrapperRequest.workspace_id`.
- Both values validated as `uuid.UUID` before header injection — any non-UUID value raises `InvalidRequestError`.
- **Never** parsed from the V1 Engine response or any user-provided data.

### 13.3 V1 Engine Server-Side Usage

The V1 Engine uses these headers for:
1. Internal cache key scoping (`raguard_{tenant_id}:...`)
2. Audit log enrichment
3. Request metering and quota enforcement

## 14. Distributed Tracing

End-to-end visibility is maintained across the V2 Backend → V1 Engine microservice boundary.

### 14.1 Trace Context Propagation

- Inbound W3C `traceparent` header from the frontend is extracted by `CorrelationIDMiddleware`.
- Propagated verbatim to V1 Engine via the `traceparent` header on every call.
- Enables end-to-end trace reconstruction in Jaeger across both services.

### 14.2 Span Structure

```text
ai_wrapper.stream_request (F8.1 root span)
  └─ v1_engine_client.stream (F8.2 child span)
       ├─ Event: request_sent {attempt, timestamp}
       ├─ Event: first_byte_received {latency_ms}
       ├─ Event: stream_completed {chunks, total_ms}
       └─ Event: error {error_code, attempt} (on failure)
```

### 14.3 Span Attributes

All V1 Engine spans include:

| Attribute | Value |
|-----------|-------|
| `service.name` | `raguard-v2-backend` |
| `peer.service` | `raguard-v1-engine` |
| `tenant_id` | Tenant identifier |
| `workspace_id` | Workspace identifier |
| `correlation_id` | Request correlation ID |
| `model_requested` | LLM model requested (if known) |
| `attempt_number` | Current retry attempt (0-indexed) |
| `http.method` | `POST` or `GET` |
| `http.url` | Full V1 Engine URL |
| `http.status_code` | Response status |

## 17. Provider Abstraction

The `V1EngineClient` operates behind the existing `LLMProvider` abstraction to remain pluggable within the established failover framework.

### 17.1 V1EngineProvider Interface Implementation

`V1EngineProvider` implements the existing `LLMProvider` ABC:

| Method | Signature | Description |
|--------|-----------|-------------|
| `generate` | `(request: LLMRequest) → LLMResponse` | Non-streaming generation |
| `stream` | `(request: LLMRequest) → AsyncGenerator[LLMResponse]` | SSE streaming generation |
| `health_check` | `() → ProviderHealth` | Returns cached health from Redis |

### 17.2 LLMProviderManager Integration

```text
LLMManagerSettings.priority_list = ["v1_engine", "openrouter", "gemini"]

LLMProviderManager.generate(request):
  ├─ Try v1_engine: V1EngineProvider.generate()
  │     ├─ SUCCESS → return LLMResponse
  │     ├─ CircuitOpenError → next provider
  │     └─ V1EngineUnavailableError → next provider
  ├─ Try openrouter: OpenRouterProvider.generate()
  │     └─ SUCCESS → return LLMResponse (or next)
  └─ Try gemini: GeminiProvider.generate()
        └─ SUCCESS → return LLMResponse (or raise AI_010)
```

### 17.3 ProviderRegistry Registration

```
ProviderRegistry.register("v1_engine", V1EngineProvider)
```

All existing cloud provider registrations remain untouched.

## 19. Failure Scenarios & Mitigations

| # | Failure | Trigger | Client Behavior | Recovery |
|---|---------|---------|-----------------|----------|
| 1 | V1 Engine cert expired | TLS handshake fails | Raises `V1TLSError` (non-retryable) | Circuit OPEN → failover to cloud |
| 2 | V1 Engine pod OOM restart | TCP RST mid-stream | Detects `CancelledError` → retry if 0 chunks, else halt | Kubernetes restarts pod; circuit recovers |
| 3 | Network partition | `httpx.ConnectError` | 3 retries with backoff → circuit OPEN | Manual investigation; traffic on cloud |
| 4 | V1 Engine rate limited | HTTP 429 + `Retry-After: 30` | Pauses per header directive → retries | Succeeds after rate window clears |
| 5 | Signing key rotation gap | HTTP 401 from V1 | `V1AuthenticationError` (non-retryable) | Alert fires; dual-key window prevents gap |
| 6 | Version incompatibility | Startup check fails | Provider disabled → warning alert | Deploy compatible V1 Engine version |
| 7 | Connection pool exhaustion | Concurrency > max | Requests queue until timeout | HPA scales V2 Backend pods; load sheds |

## 21. Security Checklist

| Check | Requirement |
|-------|-------------|
| ☐ mTLS enforced | No plaintext connections permitted under any circumstances |
| ☐ Server cert validated | Against internal RAGuard CA (`V1_ENGINE_CA_CERT_PATH`) |
| ☐ Cert rotation lifecycle | Maximum 90-day validity, automated via cert-manager |
| ☐ Request signing enabled | HMAC-SHA256 with 60-second replay window |
| ☐ Header sanitization | All downstream headers sanitized before V1 forwarding |
| ☐ Tenant ID validated | Strict UUID parse — no raw user string injection permitted |
| ☐ PII logging policy | Query text SHA-256 only; evidence and prompts never logged |
| ☐ Connection pool bounded | Max 50 connections prevents OOM under concurrency spikes |
| ☐ Circuit breaker configured | Prevents upstream cascade on V1 Engine failures |
| ☐ Health check rate-limited | Maximum 1 probe per 30 seconds; cached in Redis |
