# F8.3–F8.6 FINAL ENTERPRISE ARCHITECTURE REVIEW

## 1. Scope of Review
This document provides the final enterprise-grade review of the proposed architecture for RAGuard V2 Epic 8 Batch 2, covering:
*   **F8.3**: SSE Stream Bridge
*   **F8.4**: SSE Recovery (Last-Event-ID)
*   **F8.5**: SSE Timeout Handling
*   **F8.6**: SSE Graceful Cancellation

## 2. Principal Engineer Assessment
**Status:** APPROVED WITH CONDITIONS

The architecture successfully extends the existing production-frozen components (`AIWrapperService`, `V1EngineClient`, `LLMProviderManager`) without requiring a ground-up rewrite. The reliance on native `asyncio.CancelledError` propagation and Redis for ephemeral caching aligns with our existing technology stack and infrastructure patterns.

### Critical Dependencies
*   The system relies heavily on `fastapi.responses.StreamingResponse` and Uvicorn's handling of TCP disconnects.
*   Redis is positioned as the primary state store for chunk recovery.

## 3. Review Dimensions

### 3.1. Security Review
*   **Data Leakage Prevention:** F8.4 Redis caches are strictly namespaced by `tenant_id` (`raguard:{tenant_id}:stream_buffer:{correlation_id}`).
*   **Authentication Boundary:** The SSE bridge (F8.3) validates auth tokens and workspace membership *before* emitting any data, maintaining the strict gates established in F8.1.
*   **Denial of Service (DoS):** F8.6 ensures that disconnected clients immediately release expensive backend LLM connections and CPU resources.

### 3.2. Performance & Memory Leak Analysis
*   **V1EngineClient Backpressure:** The `asyncio.Queue(maxsize=100)` effectively limits memory consumption if the client consumes slowly.
*   **Redis Buffer Pruning:** F8.4 utilizes a strict 300-second TTL on the `stream_buffer` lists to ensure memory is automatically reclaimed.
*   **Connection Leaks:** F8.6 mandates explicit `await response.aclose()` inside the `CancelledError` handler of the producer task. Failure to implement this exact pattern will lead to connection pool exhaustion in `httpx`.

### 3.3. Reliability & Failure Scenarios
*   **Race Conditions in Reconnect:** If a client reconnects (F8.4) exactly as the background stream finishes, the orchestrator must handle the transition from "tailing Redis" to "reading the DB" gracefully.
*   **Split-Brain State:** F8.5 enforces that if `chunks_yielded > 0`, the system **cannot** failover. This prevents a frankenstein answer stitched from Gemini and OpenRouter. It gracefully terminates the stream with an `event: error`.
*   **Circuit Breaker Interaction:** Timeouts in F8.5 correctly feed into `CircuitBreakerEngine.record_failure()`, protecting the V1 Engine from cascading failures.

### 3.4. Deadlock Analysis
*   The `asyncio.Queue.put()` in the producer task could deadlock if the consumer task crashes without cancelling the producer. The architecture mitigates this by enforcing strict `try...finally` cancellation of the producer task within the consumer loop.

## 4. Required Modifications Before Implementation
Before proceeding to implementation, the following issues identified in the codebase audit MUST be addressed:
1.  **Bug Fix Requirement:** The `backend/ai/wrapper/service.py` file is missing `import asyncio`. The `except asyncio.CancelledError:` block will currently raise a `NameError`.
2.  **Bug Fix Requirement:** The `ChatOrchestrator` DI factory in `backend/modules/chat/api/dependencies.py` passes the wrong arguments compared to the class `__init__`.
3.  **V1 Engine Tenant Isolation:** The `V1EngineProvider.generate/stream` methods currently pass `uuid.uuid4()` as dummy workspace/tenant IDs. This must be wired up correctly to support F8.4 Redis namespaces.
