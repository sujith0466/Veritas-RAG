# F8.4 — SSE Recovery Architecture (Last-Event-ID)

## 1. Executive Summary
Feature F8.4 introduces resilience to transient network drops during long-running AI generations. By leveraging the SSE standard `Last-Event-ID` header, the backend will allow clients to reconnect to a dropped stream and resume receiving data without forcing the LLM to restart the entire generation process from scratch.

## 2. Feature Scope & Objectives
*   **Header Parsing:** Intercept and parse the `Last-Event-ID` header in FastAPI routes.
*   **Resume State Management:** Determine what chunks have already been delivered to the client.
*   **Mid-Stream Resumption:** If an LLM stream is active but the client reconnects, attach the client to the ongoing stream. If the LLM does not support mid-stream resumption, utilize a short-lived Redis cache to replay missed chunks.
*   **Idempotency:** Prevent duplicate database records (e.g., `ChatMessage`) if a request is a resumption rather than a new prompt.

## 3. Existing Infrastructure Reuse
*   `backend/modules/chat/api/routes.py`: Endpoint `POST /sessions/{session_id}/stream`.
*   `backend/cache/client.py`: Redis client for ephemeral chunk caching.
*   `backend/ai/wrapper/service.py`: Orchestration layer.

## 4. Architectural Design

### 4.1. The Challenge of LLM Resumption
Modern LLM streaming APIs (including V1 Engine, Gemini, OpenRouter) generally do not allow resuming a stream from a specific token index natively. If a stream is aborted, a new request starts from token 0.
To solve this, we implement a **Redis-backed Chunk Buffer**.

### 4.2. Redis Chunk Buffer Strategy
When `AIWrapperService` streams chunks, it will simultaneously push them to a Redis list keyed by the `correlation_id`.

*   **Key:** `raguard:{tenant_id}:stream_buffer:{correlation_id}`
*   **TTL:** 300 seconds (5 minutes).
*   **Write Path:** Every chunk yielded is appended (`RPUSH`) to the list.

### 4.3. Connection Recovery Flow
When a client drops and reconnects:
1.  Client sends `POST /sessions/{session_id}/stream` with `Last-Event-ID: {correlation_id}-{chunk_index}`.
2.  FastAPI route extracts `Last-Event-ID`.
3.  `ChatOrchestrator` detects the resumption attempt.
4.  It checks Redis for `raguard:{tenant_id}:stream_buffer:{correlation_id}`.
5.  If found:
    *   It retrieves the full list of chunks (`LRANGE`).
    *   It identifies the last received `chunk_index` from the `Last-Event-ID`.
    *   It replays all chunks with an index strictly greater than the `Last-Event-ID`.
    *   **Limitation:** If the original stream was aborted (LLM stopped), the client receives the cached chunks up to the failure point, followed by an `event: error`. If the original stream is still writing to Redis (background task), the orchestrator tails the Redis list (using `BLPOP` or polling) until the terminal `event: done` is reached.

### 4.4. Decoupling Generation from the HTTP Request
To support true reconnection while the LLM is still generating:
*   The `AIWrapperService.stream_request()` execution must be shielded from the client's `asyncio.CancelledError`.
*   If the client disconnects, the LLM generation continues writing to the Redis buffer in the background.
*   When the client reconnects, it attaches to the Redis buffer as a consumer.

*Note: Since the prompt states "Architecture must extend the current implementation—not redesign it", converting the synchronous request-response flow to an async background worker + polling model is too heavy. We will implement the **Replay-Only** variant for F8.4. If the client drops, the LLM stream aborts, but the client can retrieve whatever was successfully cached before the drop.*

### 4.5. Fast-Forward Re-generation (Fallback)
If the Redis buffer has expired, the orchestrator triggers a full re-generation from the LLM. However, it will silently discard chunks until the `chunk_index` matches the `Last-Event-ID`, resuming client delivery from that point forward.

## 5. Security & Isolation
*   Redis keys are strictly namespaced by `tenant_id` to prevent cross-tenant buffer reading.
*   Resumption requires the same authentication and session validation as the initial request.

## 6. Edge Cases & Race Conditions
*   **Stale Resumption:** If a client reconnects with an ID from a previous day, the Redis key will have expired, and a re-generation will be triggered.
*   **Database Idempotency:** `ChatOrchestrator` must check if the user message and assistant message for this `correlation_id` have already been written to prevent double-inserting messages into the `chat_messages` table on reconnect.
