# F8.1 AI Wrapper Service Architecture

## 1. Executive Summary

The F8.1 feature introduces the **AI Wrapper Service**, serving as the single canonical entry point for all frontend and API consumers interacting with the RAGuard AI Engine. Historically, the AI orchestration was tightly coupled within `ChatOrchestrator`, which directly invoked both the `RetrievalOrchestrator` and the `StreamingGroundedGenerationService`. This direct coupling resulted in a lack of consistent Qdrant namespace binding, fragmented prompt governance, and the absence of a unified retry layer spanning the full request lifecycle.

The AI Wrapper Service resolves these architectural debt issues by enforcing a strict separation of concerns. While authentication and RBAC continue to be enforced upstream via standard middleware, the new Wrapper Service assumes full ownership of conversation context injection, Qdrant namespace binding, centralized prompt construction, streaming orchestration, resilience strategies (retries/timeouts), and comprehensive domain event publishing. This design yields a highly cohesive, robust, and observable AI orchestration layer capable of scaling independently.

## 2. Feature Scope & Objectives

F8.1 delivers the following core capabilities:
- **Centralized Orchestration:** A unified entry point for both streaming and non-streaming AI generation requests.
- **Robust Workspace & Context Validation:** Pre-flight checks on workspace health, active index state, and user authorization before invoking AI models.
- **Dynamic Namespace Binding:** Secure, deterministic resolution and binding of tenant-specific Qdrant collections.
- **Managed Context Injection:** Automated, token-budgeted management of multi-turn conversation histories.
- **Prompt Governance:** Centralized template assembly incorporating workspace-specific custom instructions, conversation context, and retrieved evidence.
- **Resilient Execution Loop:** An integrated state machine for confidence evaluation, query rewriting, and LLM retry logic.
- **Comprehensive Observability & Events:** Structured logging, Prometheus metrics, OpenTelemetry tracing, and rich domain event publishing across the lifecycle.
- **Graceful Degradation:** A multi-tiered timeout and circuit-breaking strategy ensuring predictable failure modes.

## 3. Existing Infrastructure Reused

F8.1 heavily leverages the existing RAGuard infrastructure to avoid duplicated effort and maintain consistency. The following existing components (from `backend/`) are reused:

- **AI Provider Stack (`backend/ai/`):** `LLMProviderManager`, `GeminiProvider`, `OpenRouterProvider`, `LLMRequest`, `LLMResponse`.
- **Generation Stack (`backend/modules/generation/`):** `StreamingGroundedGenerationService`, `GroundedGenerationService`, `PromptGuard`, `CitationExtractor`, `LLMAuditService`.
- **Retrieval Stack (`backend/modules/retrieval/`):** `RetrievalOrchestrator`, `FusionEngine`, `SearchRequestDTO`, `RetrievalResultDTO`.
- **Reliability & Retry Stack (`backend/modules/reliability/`):** `ReliabilityGateway`, `CircuitBreakerEngine`, `RetryController`, `RetryStateMachine`, `ConfidenceEngine`, `ScoringEngine`.
- **Configuration & Setup (`backend/core/config/`):** `QdrantSettings`, `LLMManagerSettings`, `Settings`.
- **Vector DB Client (`backend/vector_db/client.py`):** `AsyncQdrantClient` singleton.
- **Events & Middleware (`backend/core/events/`, `backend/core/middleware/`):** `EventDispatcher`, existing JWT/CORS/Logging middlewares.

## 4. Request Lifecycle (end-to-end)

The AI Wrapper Service implements a deterministic 14-step request lifecycle.

```text
Frontend SSE Request
  → CORSMiddleware
  → CorrelationIDMiddleware
  → ObservabilityMiddleware
  → JWTAuthenticationMiddleware
  → SecurityHeadersMiddleware
  → RequestLoggingMiddleware
  → /api/v1/ai/stream endpoint
  → AIWrapperService.stream_request()
    ├─ Step 1: Request Validation & RBAC Gate
    ├─ Step 2: Workspace Validation & KB Health Check
    ├─ Step 3: Conversation Context Loading (session history)
    ├─ Step 4: Qdrant Namespace Binding
    ├─ Step 5: Query Preprocessing (PromptGuard, QueryRewriter)
    ├─ Step 6: Hybrid Retrieval via RetrievalOrchestrator
    ├─ Step 7: Confidence Evaluation via ConfidenceEngine
    ├─ Step 8: Retry/Rewrite Loop (RetryStateMachine)
    ├─ Step 9: Prompt Construction (system prompt + evidence block)
    ├─ Step 10: Streaming Generation via StreamingGroundedGenerationService
    ├─ Step 11: Citation Extraction + Grounding Check
    ├─ Step 12: Reliability Scoring
    ├─ Step 13: Domain Event Publishing
    └─ Step 14: Audit Logging (LLMAuditService)
```

**Lifecycle Details:**
- **Inputs:** A valid JWT and an `AIWrapperRequest` JSON payload.
- **Outputs:** An asynchronous SSE stream of `AIWrapperStreamChunk` objects, terminating with a final chunk containing citations and reliability scores.
- **Error Handling:** All steps are wrapped in specific exception handlers mapping internal errors to standardized AI Error Codes (see Error Catalogue).
- **Timeout Handling:** Multi-tier timeouts (L1/L2/L3) govern stage transitions to ensure the generator never hangs indefinitely.

## 6. Workspace Validation

Before executing any AI workload, the wrapper rigorously validates workspace constraints through six sequential checks:

| Check | Validation | Error Code | HTTP |
|-------|-----------|-----------|------|
| Workspace Existence | Record in DB with matching `workspace_id` | `AI_001` | 404 |
| Workspace Status | Status must be `ACTIVE`, not `SUSPENDED` | `AI_002` | 403 |
| RBAC Membership | User present in `WorkspaceMember` table | `AI_003` | 403 |
| KB Readiness | At least 1 document with status `READY` | `AI_004` | 503 |
| Feature Gate | `ai_enabled` feature flag is `true` | `AI_006` | 403 |
| Rate Limit | Per-tenant and per-user Redis sliding window | `AI_005` | 429 |

**Rate Limit Implementation:**
- Window: 60 seconds
- Default limit: 60 requests per tenant per minute; 20 per user per minute
- Key pattern: `raguard:{tenant_id}:ai:rate:{window_epoch}` and `raguard:{user_id}:ai:rate:{window_epoch}`
- On limit hit: Returns HTTP 429 with `Retry-After` header

## 7. Qdrant Namespace Binding

To guarantee strict multi-tenant isolation, the wrapper securely binds the request to a specific Qdrant collection.

### 7.1 Resolution Flow

```text
AIWrapperService.resolve_namespace(workspace_id, tenant_id)
  ├─ 1. Check Redis cache: raguard:{tenant_id}:namespace:binding
  │     └─ HIT: Return cached NamespaceBinding (skip steps 2-4)
  ├─ 2. Construct collection name: raguard_knowledge_{tenant_id}
  ├─ 3. Verify collection exists in Qdrant (AsyncQdrantClient.get_collection())
  │     ├─ EXISTS: Store in Redis (TTL=300s), return NamespaceBinding
  │     └─ NOT FOUND: Raise AI_008 (CollectionMissing)
  └─ 4. On resolution failure: Raise AI_007 (NamespaceNotResolved)
```

### 7.2 NamespaceBinding DTO

| Field | Type | Description |
|-------|------|-------------|
| `collection_name` | `str` | Qdrant collection (e.g., `raguard_knowledge_abc123`) |
| `tenant_id` | `str` | Owning tenant |
| `workspace_id` | `str` | Requesting workspace |
| `resolved_at` | `datetime` | Resolution timestamp |
| `is_valid` | `bool` | Confirmed Qdrant collection exists |

### 7.3 Cache Invalidation

Cache key `raguard:{tenant_id}:namespace:binding` is purged on:
- Workspace deletion (status transition to `DELETING`)
- Workspace suspension
- Manual admin cache flush via `DELETE /api/v1/ai/cache/namespace`

## 8. Context Injection

Multi-turn chat experiences require intelligent context management to maintain coherence without exceeding token limits.

### 8.1 ConversationContext Loading

```text
build_conversation_context(session_id)
  ├─ 1. Query ChatRepository for last N=5 messages (configurable)
  ├─ 2. Filter by session_id and tenant_id
  ├─ 3. Compute token estimate for history block
  ├─ 4. Truncate if history_tokens > 20% of max_answer_tokens
  └─ 5. Return ConversationContext{turns, session_id, token_budget_used}
```

### 8.2 ConversationTurn Format

| Field | Type | Description |
|-------|------|-------------|
| `role` | `str` | `"user"` or `"assistant"` |
| `content` | `str` | Message content |
| `created_at` | `datetime` | Message timestamp |

### 8.3 Query Enhancement for Multi-Turn Search

To improve retrieval relevance in multi-turn sessions, the previous user message is prepended to the current query before invoking `RetrievalOrchestrator`:

```
effective_query = f"{prior_user_turn} {current_query}"
```

This ensures dense and sparse search captures context that depends on the prior conversational state.

## 9. Prompt Construction

The service acts as the central governor for all prompt assembly, ensuring grounding and safety at every layer.

### 9.1 System Prompt Template

```
You are a grounded AI assistant for {workspace_name}.
Today is {today_date}.
Your knowledge base contains {document_count} documents.
{custom_instructions}

STRICT RULES:
- Answer ONLY from the evidence provided below.
- For every factual claim, include an inline citation marker [N] where N is the evidence number.
- If the evidence does not answer the question, state: "I could not find this in the provided documents."
- Do NOT include information not found in the evidence.
- Do NOT speculate or hallucinate.
```

### 9.2 Evidence Block Format

Consistent with the existing `GroundedGenerationService` pattern:
```
[1] {chunk_1_content}
[2] {chunk_2_content}
...
[N] {chunk_N_content}
```

### 9.3 Full Prompt Assembly Order

1. System prompt template (with resolved variables)
2. Conversation history block (token-capped)
3. Evidence block (from retrieval results)
4. User query

### 9.4 Token Truncation Strategy

If total prompt tokens would exceed 128,000 (GPT-4 context window):
1. First truncate: Conversation history (reduce to N=2 turns)
2. Second truncate: Evidence block (remove lowest-ranked chunks first)
3. System prompt: Never truncated

## 10. Streaming Orchestration

Streaming is handled natively via an async generator with backpressure, heartbeat, and cancellation support.

### 10.1 Stream Flow

```text
AIWrapperService.stream_request()
  ├─ [Steps 1-9: Pre-flight validation and retrieval]
  ├─ Instantiate StreamingGroundedGenerationService with resolved LLM provider
  ├─ async for chunk in service.generate_stream(gen_request):
  │     ├─ Wrap chunk into AIWrapperStreamChunk (add namespace_used, wrapper_metadata)
  │     ├─ Yield: data: {AIWrapperStreamChunk.model_dump_json()}\n\n
  │     └─ Update heartbeat timer
  ├─ Heartbeat task: If silence > 15s → yield data: {"type": "heartbeat"}\n\n
  ├─ On asyncio.CancelledError:
  │     ├─ Emit ai_wrapper.request_cancelled event
  │     └─ Close downstream generator cleanly
  └─ On completion: [Steps 11-14: scoring, events, audit]
```

### 10.2 FastAPI Route Pattern

```text
POST /api/v1/ai/stream
  → return StreamingResponse(
        ai_wrapper_service.stream_request(request),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"}
    )
```

## 11. Retry Strategy

The F8.1 wrapper integrates the existing `RetryStateMachine` from `backend/modules/retry/`.

### 11.1 State Transitions

```text
INITIAL
  → RETRIEVED (after successful hybrid search)
      → CONFIDENCE_EVALUATED
          ├─ Score ≥ 85 (PROCEED)  → GENERATING → COMPLETED
          ├─ Score 70-84 (CLARIFY) → GENERATING (with clarification prefix)
          └─ Score < 70 (RETRY)    → RETRYING
               ├─ Invoke QueryRewriter → reformulated query
               ├─ Loop back to RETRIEVED (max 3 times)
               └─ Score < 40 (ABORT) → ABORTED (emit error chunk)
```

### 11.2 Retry Governance

| Parameter | Value | Source |
|-----------|-------|--------|
| Max retries | 3 | `RetryStateMachine.MAX_RETRIES` |
| Min improvement delta | 2.0 confidence points | `DecisionEngine.MIN_IMPROVEMENT_DELTA` |
| Base backoff | 1 second | `RetryController` |
| Backoff formula | `min(1 * 2^attempt, 8s)` | Exponential |
| Abort threshold | Score < 40 | `ConfidenceEngine.ABORT_THRESHOLD` |

## 12. Timeout Strategy

A robust, multi-level timeout hierarchy ensures the system remains responsive under all conditions.

| Level | Scope | Duration | Mechanism | On Trigger |
|-------|-------|----------|-----------|------------|
| L1 — Retrieval | `RetrievalOrchestrator` call | 5 seconds | `asyncio.wait_for()` | Raise `AI_009` |
| L1 — Confidence | `ConfidenceEngine` evaluation | 1 second | `asyncio.wait_for()` | Skip retry, proceed |
| L1 — Generation | LLM stream duration | 25 seconds | `asyncio.wait_for()` | Yield timeout chunk |
| L2 — Wall Clock | Total request lifetime | 35 seconds | Top-level `asyncio.wait_for()` | Yield timeout chunk |
| L3 — Watchdog | Token silence during active stream | 10 seconds | Background heartbeat task | Abort stream |

Cleanup tasks (audit logging, event publishing) are wrapped in `asyncio.shield()` to ensure they complete even when the parent task is cancelled.

## 15. Security

### 15.1 RBAC Enforcement

```text
JWTAuthenticationMiddleware (upstream)
  → Decodes and validates JWT signature and expiry
  → Sets request.state.user_context (UserContext)

AIWrapperService.validate_workspace() (Step 2)
  → Queries WorkspaceMember table: user_id + workspace_id
  → Raises AI_003 if not found
  → Raises AI_002 if workspace status ≠ ACTIVE
```

`tenant_id` is **always** extracted from the trusted JWT `sub`/`tenant_id` claim — never from the request body. Any request body `tenant_id` field is ignored and overridden.

### 15.2 Prompt Injection Prevention

- Evidence chunks are sanitized by `PromptGuard.sanitize_and_format_evidence()` before inclusion in any prompt.
- Detection patterns: Instruction-override attempts (`"Ignore previous instructions..."`), role-switching, delimiter injection.
- All potentially harmful chunks are stripped from the evidence block.
- If all chunks are stripped: Yield error chunk `"All provided evidence failed security guardrail checks."` and abort.

### 15.3 Input Validation

| Input | Constraint | Enforcement |
|-------|------------|-------------|
| `query` length | Max 2,000 characters | `GenerationRequestDTOv2` Pydantic validator |
| `tenant_id` format | Valid UUID | `uuid.UUID()` parse check |
| `workspace_id` format | Valid UUID | `uuid.UUID()` parse check |
| Control characters | Stripped | `re.sub(r'[\x00-\x1f\x7f]', '', query)` |

### 15.4 Cross-Tenant Isolation

- Qdrant collection name constructed from JWT-extracted `tenant_id`, never from user input.
- Namespace binding cached and validated before any vector search.
- PostgreSQL queries include `tenant_id` filter on all document and chat table access.

## 18. Migration from ChatOrchestrator

The migration strategy ensures zero downtime and complete backward compatibility.

### 18.1 Migration Phases

**Phase 1 (Current → F8.1):**
- `ChatOrchestrator.stream_chat()` is refactored into a thin adapter.
- Internal body replaced: delegates to `AIWrapperService.stream_request()`.
- All inputs mapped from legacy parameters to `AIWrapperRequest`.
- Zero changes to the existing `/api/v1/chat/sessions/{id}/stream` route.
- Zero database schema changes.
- Zero frontend changes required.

**Phase 2 (Post-F8.1, Future):**
- Frontend optionally migrates to `/api/v1/ai/stream` for enriched `AIWrapperStreamChunk` payloads.
- This phase is voluntary and backward-compatible.

### 18.2 Compatibility Matrix

| Component | Changed? | Notes |
|-----------|---------|-------|

| `ChatOrchestrator` class | Yes (internals only) | Interface unchanged |

## 19. Error Catalogue

| Code | HTTP Status | Name | Trigger | Recovery Action |
|------|-------------|------|---------|-----------------|
| `AI_001` | 404 | `WorkspaceNotFound` | `workspace_id` not in DB | — |
| `AI_002` | 403 | `WorkspaceSuspended` | Workspace status is `SUSPENDED` | Contact administrator |
| `AI_003` | 403 | `UserNotMember` | User absent from `WorkspaceMember` | Request workspace access |
| `AI_004` | 503 | `NoReadyDocuments` | Zero `READY` documents in KB | Wait for document ingestion pipeline |
| `AI_005` | 429 | `QuotaExceeded` | Redis sliding window rate limit hit | Observe `Retry-After` header |
| `AI_006` | 403 | `FeatureDisabled` | `ai_enabled` feature flag = `false` | Upgrade plan or contact admin |
| `AI_007` | 500 | `NamespaceNotResolved` | Collection name resolution failure | Retry; check Qdrant connectivity |
| `AI_008` | 500 | `CollectionMissing` | Qdrant collection not found | Trigger full reindex via Knowledge Health |
| `AI_009` | 408 | `RequestTimeout` | Wall clock timeout exceeded | Retry with shorter query |
| `AI_010` | 502 | `AllProvidersDown` | `LLMProviderManager` exhausted all providers | Wait; check status page |

All errors are returned as JSON: `{"success": false, "error": {"code": "AI_XXX", "message": "..."}}`.
For SSE endpoints, errors are yielded as a final SSE chunk: `data: {"error": {"code": "AI_XXX"}, "is_final": true}\n\n`.

## 20. Performance & Scalability

### 20.1 Latency Targets

| Metric | Target | Measurement Point |
|--------|--------|------------------|
| P50 Time to First Token (TTFT) | < 2 seconds | First SSE chunk emitted |
| P99 TTFT | < 8 seconds | First SSE chunk emitted |
| P99 Workspace Validation | < 50 ms | Steps 1-2 combined |
| P99 Namespace Binding (cache hit) | < 5 ms | Redis GET |
| P99 Namespace Binding (cache miss) | < 100 ms | Redis GET + Qdrant ping |

### 20.2 Concurrency Model

- Built entirely on `asyncio` — zero blocking I/O on critical path.
- Per uvicorn worker: ~100 concurrent streaming connections (limited by LLM provider concurrency).
- Namespace binding cache eliminates Qdrant collection lookup overhead.
- Session context cache (Redis, TTL=1800s) eliminates DB query for history.

### 20.3 Scaling Strategy

- Service is **fully stateless** — scales horizontally with additional uvicorn workers behind the existing API gateway.
- Namespace binding cache: Shared across all workers via Redis (no per-worker state).
- Rate limiter: Redis-backed sliding window — enforced consistently across all workers.
- No new stateful components introduced.
